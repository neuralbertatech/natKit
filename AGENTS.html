Project Summary

natKit is a hardware, data, and analysis platform. It started as a platform for BCI and other bio-sensor data, and has been expanding toward a broader IoT-like system where any source that can generate meaningful data is in scope.

The framework can be broken down into three main segments: sensor, processing, and visualization. Data usually flows left-to-right through those stages, but control traffic can also flow right-to-left when a user or service needs to change sensor configuration or trigger remote actions.

The target audience is people who work with and analyze data: academics doing research, engineers building sensing systems, and curious individuals who want to inspect and process their own data.

The core unit of the framework is the channel. A channel is a bundle of related streams that together describe one source of data or one derived processing result. Channels are meant to preserve each stage of data handling instead of mutating prior results in place.

  • A source such as a sensor typically creates one new channel
  • A transform such as filtering or featurization should create a new derived channel
  • Metadata, markers, logs, and control traffic are side facets of the same channel model
  • Immutable Kafka-backed records allow historical replay through the same path as live processing
The rule that matters most is simple: timestamps are the join contract. With NTP-synchronized clocks, payload timestamps should be treated as canonical for channel stitching and sensor fusion. Kafka receive time is diagnostic only.

Architecture

System shape

sensor/device -> gateway/bridge -> Kafka channel streams -> processing workers -> frontend / downstream clients
user / frontend / service -> backend control plane -> gateway/bridge -> sensor/device

The root stack currently revolves around Kafka, Mosquitto, NTP, and bridge services that normalize ingress from device-facing protocols into natKit channel streams. The local development setup is still often single-node, but the intended direction is clustered deployment rather than permanent single-box operation.

Channel lifecycle

A channel is normally created for each source of data, typically a sensor. Each time a channel is transformed, for example by running a band-pass filter on source data, the result should become a whole new channel. That design preserves every step of the data lineage and allows different kinds of processing and analysis to run in parallel over the same upstream history.

Timing ownership

The NTP server is important infrastructure, not an incidental convenience. Temporal accuracy matters when multiple sensors need to be fused or compared. NTP is the current baseline for synchronization, but future workloads will likely need tighter synchronization mechanisms in some environments.

Channels and Streams

natKit works with bundles of related streams, and that bundle should be called a channel. Each stream inside a channel provides a different facet of information about the same source or derived data product.

Facet Role Notes
DATA Primary payload stream Typically raw sensor data or a downstream derivative of earlier source data
META Metadata stream Describes the channel, hardware, sessions, and other cluster-level context
MARKERS Timestamped event annotations Used to indicate that something happened during a given timestamp; some existing code paths still use the singular enum/topic form Marker

There are also extensions to the stream types that can be enabled when a given channel or subsystem needs them.

  • Execution extension: streams used for executing remote commands on other devices
  • Hardware extension: streams for hardware configuration and hardware state
  • Logging extension: streams for logs and heartbeats, including LOGGING_HEARTBEAT traffic that indicates a source is still connected

The purpose of the channel model is to keep these facets separate without losing coherence. Consumers can subscribe only to what they need, while still reconstructing a cohesive stream of information for one source or one processing stage.

Schemas and Records

Data schemas are important because they define how messages are serialized, sent, and then deserialized again. They are one of the central contracts that let firmware, backends, workers, and frontends exchange data coherently.

Topic naming currently follows the natKit convention Type-StreamId-Serialization-Schema. The broader direction is that message types should be rooted in C++ classes in libnatkit-core, with serialization format treated as an implementation detail that can change without changing the higher level record model.

For metadata in particular, the META stream is expected to carry a family of typed records rather than a single hard-coded payload. The intended model is a registry of C++ record types where each metadata structure is associated with an identifier and can be serialized in different formats without changing its conceptual ownership.

Concern Primary schema/topic Notes
Raw source data Data-...-Json-<Schema> Primary channel payloads such as EMG, IMU, EEG, or derived feature/classification outputs
Metadata records Meta-...-Json-MetaRecord Generic metadata carrier; session, hardware, and other channel-scoped records should be rooted in core C++ types
Markers Marker-...-Json-MarkerEventV1 Timestamped annotations for session boundaries, cues, state changes, and other events
Heartbeats and logs LoggingHeartbeat-...-... and related logging extension topics Health and debug traffic for source liveness and operational tracing

Core ownership

  • libnatkit-core should own stream types, topic parsing, schema registration, and record definitions
  • Higher-level libraries should reuse those contracts instead of re-declaring them
  • Timestamp-based stitching and interleaving should be library functionality rather than ad hoc script logic
  • Bindings should expose those same core types into Python, C#, and other environments when needed

Language Strategy

The bulk of the framework is, and should remain, C/C++ for server, backend, and embedded code, and Svelte for frontend interfaces. That is the intended center of gravity for the platform.

Python may continue to exist around ML and workflow glue, but core framework logic should stay in the shared library layer when practical. When other languages are necessary, the preferred approach is bindings instead of duplicated implementations.

  • Use C/C++ for core framework behavior, schemas, transport, processing, and embedded support
  • Use Svelte for operator-facing and browser-facing tools
  • Use Python where it materially helps and does not pull core ownership away from the libraries
  • For Unity/VR and similar integrations, prefer C# bindings into shared code instead of reimplementing the same logic

Frontend

The main live data surface today is frontend/src/StreamViewer/. It is no longer just a passive viewer; it is also part of the control plane for experiment publication, transform creation, and operator workflows around live channels.

The current Stream Viewer has three active tabs:

  • Live: stream list, subscription control, and live sensor views
  • Experiment: browser-owned EMG experiment flow that publishes session metadata and markers
  • Transforms: request derived EMG transform streams from the backend

The browser WebSocket manager lives in frontend/src/StreamViewer/websocket.ts. Stream state orchestration lives in frontend/src/StreamViewer/page.svelte. The browser does not speak Kafka directly; it uses the backend WebSocket layer as its access point into live channel traffic and experiment publication.

The backend port defaults to 7409 and can be overridden with NATKIT_BACKEND_PORT.

In the current local development stack, the ML control plane is a separate service on 8786 rather than part of the Drogon backend process.

The compose override can also start an opt-in standalone ML worker profile that connects back to the control plane over the container network and mirrors a small remote slot inventory for scheduler testing. That override now forwards runtime environment overrides such as NATKIT_ML_CONTROL_PLANE_WORKER_THREADS into the dedicated control plane container, so the stack can run in an external-worker-only mode with zero embedded execution slots while standalone workers mirror the scheduler-visible slot inventory.

The backend direction is to move long-running processing off the browser backend process and onto worker nodes with stable logical thread slots. The current ML control plane is now the first implementation surface for that scheduler model.

The current control plane can also persist slot ownership and job history to a JSON snapshot file or a SQLite state database, exposes embedded worker summaries with heartbeat timestamps and slot capacity rollups, enforces placeholder-principal ownership for job mutation, supports explicit slot release plus safer reassignment rules when active work is present, now requires jobs to target slots already assigned to the submitting principal, and now has an explicit external worker registry plus heartbeat actions so separate worker processes can start appearing in the control-plane summary before slot ownership fully moves out of process. The SQLite-backed state path now also persists scheduler rows through incremental per-row upserts with key-only stale-row probes instead of rereading entire table bodies before each save. External workers can now also mirror slot inventory into the scheduler and claim/report queued ML jobs for those slots through the control plane, and libnatkit/scripts/natkit_ml_worker.py now provides the first standalone runtime for that path, including automatic reconnect with deferred terminal-state replay after transient disconnects plus running-state resync for surviving in-flight jobs after a control-plane reconnect. The remote-worker protocol now also carries a per-process worker session id so the control plane can distinguish a normal reconnect from a true worker-process restart; when that restart happens under the same worker id, the control plane requeues the worker's in-flight jobs for a clean rerun instead of treating them as silently continued execution. Job state now also carries a persisted restart count so those reruns are visible in scheduler payloads and the ML Pipeline UI, and worker plus slot summaries now expose cumulative restart-attempt counts for a coarse instability signal above the per-job detail. Automatic reruns are now bounded by a control-plane restart-attempt cap, and when that cap is exhausted the job is marked failed so the existing ML Pipeline job-status and error-banner flow acts as the current user notification path. The control plane and ML Pipeline frontend now also expose explicit worker drain/resume control so deployment or operator actions can stop new job claims on a worker without forcibly interrupting work that is already running, and worker summaries now report whether a draining worker still has active work attached or is ready to stop cleanly. The control plane now also exposes an explicit wait_worker_drain_ready action so deployment tooling can block on that state instead of polling the worker list manually, and libnatkit/scripts/natkit_ml_worker_operator.py now wraps that worker inspection plus drain/resume flow in a small operator CLI for scripts and manual maintenance work, including repeated-worker maintenance commands for coordinated multi-worker drain or resume operations plus a fail-fast mode that stops on the first hard request error during those coordinated runs. That CLI now also accepts newline- delimited worker-id files so deployment tooling can pass generated worker inventories without expanding long repeated flag lists in shell, and it now also accepts structured JSON worker manifests with optional group filtering for richer rollout metadata handoff. The operator CLI now also writes optional structured result JSON artifacts, including resolved requested worker ids, the subset actually processed before any fail-fast stop, aggregate exit state, and per-worker outcomes, so deployment automation can archive maintenance results without scraping stdout. When the control plane reloads persisted state after a restart, it now also writes back any normalized recovered in-flight job state immediately, so shared SQLite readers see the same recoverable-or-failed view that the restarted control plane is serving from memory. The external-worker protocol now also requires the active worker_session_id on worker heartbeats, slot-inventory sync, job-claim requests, job-state reports, and unregister requests whenever a worker already has a recorded live session, so stale or competing processes cannot keep mutating scheduler state after a newer worker session has taken ownership. The ML Pipeline frontend now also exposes principal-scoped slot counts plus filters for all, mine, claimable, submittable, and active slots. The remaining gap is deployment and shared scheduler-state behavior, plus richer recovery for in-flight work across control-plane restarts, so external workers become the default execution mode rather than an incremental add-on beside the embedded runner. Running ML jobs stop at pipeline checkpoints rather than always running to completion after a stop request.

The Stream Viewer EMG transform path is also starting to adopt that model. It now has explicit local worker-slot capacity, a listable set of active transform workers, and a stop action instead of only spawning detached transform threads with no visible limit. The UI and protocol also expose per-transform slot ids plus lightweight activity data such as frames processed and last-frame timestamps, with the frontend polling live transform state while active work is present. The local worker summary now also reports available slots, heartbeat time, and a coarse worker status.

Example Projects

natVR/, natKit-IMU/, and natMuse/ are all first-class example projects that leverage shared natKit infrastructure.

natVR

natVR/ is the EMG/VR project-local package. It is intentionally separate from shared transport infrastructure so EMG- and Quest-specific assumptions do not leak into generic natKit code too early.

The natVR Python scripts still exist and remain useful for some glue and current workflows, but they are not the preferred long-term home for core ML logic. Since ONNX support has been added to libnatkit, the architectural direction is to move training and classification ownership toward shared library code and bindings rather than growing more Python-only implementations.

Important natVR commands

  • natvr-emg-record: record raw EMG from Kafka to Parquet
  • natvr-emg-capture: cue-driven labeled capture
  • natvr-emg-publish-session: publish metadata and session lifecycle markers
  • natvr-emg-reconstruct: rebuild a historical session from Kafka
  • natvr-emg-featurize: convert source data plus markers into feature windows
  • natvr-emg-calibrate: build normalization profiles
  • natvr-emg-train: train models in the current natVR workflow
  • natvr-emg-classifier: live classifier against Kafka inputs
  • natvr-emg-classify-replay: offline replay classifier
  • natvr-emg-replay-eval: compare replay classification against cue labels
  • natvr-hand-state-bridge: Kafka hand-state to WebSocket bridge

Other example projects

  • natKit-IMU/: IMU-oriented sensing and device work
  • natMuse/: Muse-oriented acquisition and analysis built on the same transport and schema model

Core Workflows

Browser experiment to training data

1. Open Stream Viewer
2. Select an EMG source channel
3. Run the EMG experiment flow
4. Frontend publishes session metadata and marker records into channel side streams
5. Raw EMG remains on its source data stream
6. Reconstruct the session by stitching source data, metadata, and markers on timestamps
7. Featurize or otherwise transform into derived channels or offline artifacts
8. Train, calibrate, classify, or replay against the same immutable record history

Reconstruction flow

Reconstruction is required because the primary source data stream is source-scoped while session and labeling context is carried in metadata and marker side streams. The reconstruction path:

  • reads metadata records for the target session or channel context
  • reads the marker stream for the same context
  • derives the relevant time window from session markers and timestamps
  • scans the source data stream and joins records by producer time
  • trims or interleaves records into a coherent reconstructed view
  • writes outputs that the rest of the processing and training stack can consume

Timestamp alignment rule

Marker stitching, reconstruction, replay, feature labeling, and cross-stream interleaving all align on producer timestamps such as device_ts_us and emitted_at_us. Kafka receive time remains diagnostic only.

Known Constraints

  • Local broker caveat: the current single-broker local stack has consumer-group limitations around __consumer_offsets. Several smoke flows use direct partition assignment.
  • Schema ownership: message types should remain rooted in libnatkit-core, with other languages consuming bindings rather than reimplementing contracts.
  • Channel replay model: immutable Kafka records are a feature. They are what allow live and historical processing to converge on the same execution path.
  • Do not join on Kafka receive time except for diagnostics.
  • Frontend and backend have both grown beyond a passive viewer; the Stream Viewer is now also a control plane for experiment publication and derived stream creation.
  • The framework still uses many single-node components today, but the target is larger: multi-node Kafka clusters storing channels, worker nodes processing channels, and multiple protocol gateways such as MQTT, BLE, cellular, LoRa, or other ingress paths.
  • The intended deployment ceiling is larger than a single lab machine. The framework should eventually scale to environments such as university departments with multiple brokers, workers, and gateways.
