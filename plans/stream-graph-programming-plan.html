natKit - stream graphs - plan - July 3 2026

Stream Graph Programming Plan

Add a node-based graphical programming surface for live and replayable natKit streams. The first usable slice lets an operator place existing streams on a canvas, add transform nodes, connect streams into transforms and transforms into downstream transforms, then materialize those graph edges as derived Kafka channels using the existing descriptor-driven transform worker path.

Scope: Stream Viewer graph tab, graph definition model, backend WebSocket actions, transform orchestration, provenance, and follow-on worker-control-plane migration.

Decision

  • Create a new Stream Viewer graph surface instead of stretching the current form-based Transforms tab.
  • Model streams and transforms as typed graph nodes with descriptor-aware input and output ports.
  • Persist graph definitions as inspectable metadata before trying to build a full visual language runtime.
  • Compile the first graph execution plan into existing create_transform, list_transforms, and stop_transform operations.
  • Keep every transform output as a normal derived channel, with timestamp semantics, schema descriptors, and provenance records intact.
  • Use a RVBBIT-inspired direct-manipulation canvas: right-click palette, drag streams or transform capabilities onto the board, visible lineage, reactive status, and inspectable generated configuration.

Why This Exists

Current state

  • Generic transforms now exist, but composition is still form-driven and one transform at a time.
  • Chaining requires the user to mentally track derived stream ids and feed them back into new transform requests.
  • Active transform state is listable, but lineage is not presented as an editable program.

Target state

  • Operators compose stream processing as a visible directed graph.
  • Graph edges carry typed channel-frame compatibility information.
  • The canvas is both documentation and control surface for live processing.

Constraint

  • The core natKit rule remains unchanged: derived data becomes new immutable channel streams.
  • Graph execution must not hide transform provenance or timestamp behavior.
  • The first slice should reuse the local Stream Viewer transform worker before moving execution into the broader worker scheduler.

RVBBIT-Inspired Interaction Model

RVBBIT describes a reactive canvas where users right-click the board, drag tables or fields into the workspace, connect reactive parameters, inspect generated code, and extend behavior through rules. natKit should adopt the parts that fit stream processing rather than copying the BI-specific SQL and Clojure stack.

RVBBIT idea natKit adaptation
Right-click canvas palette Open stream, transform, marker, and future sink palettes at the cursor.
Drag data items onto a board Drag existing Kafka channel streams into source nodes with live schema and liveness badges.
Reactive flow connections Connect source output ports to transform input ports, then transform outputs into downstream transforms.
Inspectable generated logic Show the graph JSON, transform configs, output stream ids, and provenance records for each node.
Extensible rules Later add graph rewrite rules, recommended next transforms, and domain presets from descriptor capabilities.

Reference: https://github.com/ryrobes/rvbbit

Conceptual Model

source stream node
  output: DATA channel frame
    -> transform node input
      config: transform kind + descriptor mapping + parameters
      output: derived stream id
        -> transform node input
          output: derived stream id
            -> live viewer / downstream subscriber / future sink

The graph is not a separate data plane. It is a control and orchestration layer over normal natKit channels. Each successful transform node produces a derived stream that can be replayed, inspected, subscribed to, and used as another graph input.

Graph Definition V1

Store graph definitions as versioned JSON records. The first implementation should persist these records in a backend-local JSON file so the feature can ship without a database migration. The JSON shape must remain suitable for a later SQLite table or publication as channel metadata.

Backend Storage V1

Use a single JSON file for the first implementation. Suggested default: NATKIT_STREAM_GRAPH_STORE, falling back to ./data/stream_graphs.json relative to the backend working directory. This keeps the feature independent from the auth SQLite work and avoids introducing a migration before the graph model settles. 

{
  "store_version": 1,
  "graphs": [
    { "...": "StreamGraphDefinition" }
  ]
}
  • Read the file on backend startup if it exists.
  • If the file is missing, start with an empty graph list.
  • Write updates atomically: write to a temporary file in the same directory, then rename.
  • Guard the in-memory graph map with the same style of mutex used for active transform workers.
  • Reject malformed store contents instead of silently dropping graphs; return a backend error and leave the in-memory list empty.

Node Types

Node kind First behavior Later behavior
stream_source References an existing stream id and exposes one data output port. Support replay windows, metadata facets, marker facets, and source presets.
transform References a transform capability, validates descriptor compatibility, and materializes a derived output stream. Support multi-input transforms, feature extraction, classifiers, and worker-scheduler placement.
viewer Optional first-slice node or side panel that subscribes to a selected stream or transform output. Become reusable visualization nodes with per-node buffering and chart configuration.
sink Out of scope for the first slice. Record to artifact, export, publish to device control, or bridge into another protocol.

Execution Semantics

  1. The frontend edits graph JSON locally and asks the backend to validate it.
  2. The backend resolves each stream node to current topic information and descriptors.
  3. The backend topologically sorts transform nodes and checks each edge for descriptor compatibility.
  4. For each runnable transform node, the backend derives or reuses an output stream id.
  5. The backend starts transform workers using the existing create_transform path.
  6. Each transform output appears in list_transforms and regular stream discovery.
  7. The graph node status updates from backend execution state: draft, valid, starting, running, stalled, stopped, or error.

A graph run should be idempotent where possible. Re-applying the same graph should reuse already-running transform outputs when the source, transform kind, input mapping, config, and output identifier match.

V1 graph execution should start only transform nodes whose upstream dependency is already a stream id. For a chain, that means the backend walks nodes in topological order and carries a resolved output stream id from each transform node into its downstream transform node. If an upstream transform fails to start, downstream nodes must remain blocked with the upstream node id in their diagnostic message.

Backend Protocol Additions

Action Purpose
list_stream_graphs Return saved graph definitions and high-level run state.
save_stream_graph Persist graph JSON, layout, labels, and UI state after validation.
validate_stream_graph Return node-level compatibility diagnostics without starting workers.
start_stream_graph Compile graph nodes into transform workers and return per-node output stream ids.
stop_stream_graph Stop transform workers owned by a graph run, with an option to stop one branch or the whole graph.
get_stream_graph_status Return node statuses, worker slots, frame counts, errors, and last heartbeat data.

These actions should live beside the current Stream Viewer WebSocket protocol initially. Long-term execution should move to the worker control plane so graph runs can consume shared or dedicated compute slots under the accepted admin-owned compute policy.

Backend Implementation Notes

  1. Add plain structs near the Stream Viewer backend implementation for graph definitions, nodes, edges, diagnostics, and node status.
  2. Use nlohmann::json conversion helpers rather than parsing fields ad hoc inside each handler.
  3. Keep graph store state separate from g_transform_workers; graph status should reference active workers by output stream id.
  4. When starting a transform node, call or extract the same logic used by handleCreateTransform rather than duplicating topic creation and worker startup code.
  5. If extraction is too large for the first patch, implement a private helper such as createTransformFromGraphNode(...) and have both paths converge later.
  6. Add graph_id, graph_run_id, and graph_node_id as optional fields in the transform provenance config or metadata path without breaking existing provenance readers.
  7. Do not auto-subscribe browser clients to every graph output. Let the UI subscribe only to selected node outputs to avoid multiplying live traffic.

Validation Algorithm

  1. Parse the graph and verify graph_version == 1.
  2. Check unique node ids and edge ids.
  3. Check every edge references existing source and target nodes.
  4. Check source and target ports exist on their nodes, using default ports when omitted by older drafts.
  5. Reject cycles with a depth-first search or Kahn topological sort.
  6. Reject transform nodes with zero inputs or more than one input in V1.
  7. Resolve every source stream node against the current stream list and require a DATA topic descriptor.
  8. For transform nodes, resolve the active transform capability by transform_kind.
  9. Use existing descriptor helper logic to find or verify input_mapping_id.
  10. Validate config fields against capability metadata: required fields, numeric minimums, enum options, and defaults.
  11. Derive downstream descriptors from the transform capability output schema so transform-to-transform edges can validate before execution.
  12. Return all diagnostics at once; do not fail validation on the first error unless the graph JSON is structurally unreadable.

Frontend Plan

  1. Add a fourth Stream Viewer tab named Graph.
  2. Add a canvas component with pan, zoom, node drag, selection, edge creation, and context menu support.
  3. Implement a stream palette populated from get_streams, including descriptor names and liveness state.
  4. Implement a transform palette populated from list_transform_capabilities.
  5. Render source nodes with schema, stream id, subscription state, and recent-frame status.
  6. Render transform nodes with configurable fields generated from capability descriptors.
  7. Validate connections immediately and mark incompatible ports before submission.
  8. Add an inspector panel for selected nodes, edges, generated JSON, output stream ids, provenance, and worker state.
  9. Use the existing live viewers as a side panel for whichever graph node output is selected.

The frontend dependency decision should be made during implementation. The current package does not include a graph editor library. Options are a small custom SVG/canvas editor for the first slice, or adding a Svelte-compatible flow editor if it reduces interaction risk.

UI Interaction Details

  • Right-click or toolbar plus button opens a palette at the cursor.
  • Dragging a stream from the palette creates a stream_source node at the drop position.
  • Dragging a transform creates a transform node with config defaults from TransformCapability.config_fields.
  • Dragging from an output port to an input port creates an edge if local validation allows the connection.
  • If the connection is incompatible, show an inline edge preview in an error color and do not commit it.
  • Selecting a transform node opens generated controls for its config fields in the inspector.
  • Start Graph is disabled when backend validation has errors.
  • Stop Graph stops only active transform nodes that belong to the current graph run.
  • Deleting a running node should prompt the user to stop that node's worker before removing it from the graph.
  • The graph tab should poll status while any node is starting, running, or stalled.

Validation Rules

  • Graphs must be directed and acyclic in V1.
  • Every transform input must have exactly one connected upstream data edge.
  • Each transform edge must resolve to a compatible TransformInputMapping.
  • Output identifiers must be deterministic, sanitized, and unique within a graph run.
  • Deleting a node should never delete Kafka history; it only changes the saved graph and optionally stops live workers.
  • Timestamp behavior remains owned by the underlying records and transform worker, not the graph editor.

Execution State Model

Use these states consistently in frontend and backend payloads:

State Meaning
draft Node exists locally and has not been validated by the backend.
valid Node passed validation and is ready to start.
blocked Node cannot start because an upstream node is invalid or failed to start.
starting Backend accepted the graph run and is creating the transform worker.
running Transform worker exists for this node and has an output stream id.
stalled Worker exists but heartbeat or frame activity is stale by existing transform-list logic.
stopped No active worker is attached to this node.
error Validation, startup, config, worker, or storage error attached to this node.

Provenance and Lineage

Graph execution should extend, not replace, existing transform provenance. Each transform node should write provenance that includes:

  • graph_id, graph_run_id, and graph_node_id.
  • Source stream id and upstream node id.
  • Transform kind, input mapping, normalized config JSON, and output stream id.
  • Worker id, thread slot id, start time, and eventual stop reason.

This keeps historical reconstruction possible even if the visual graph is later edited.

Implementation Phases

Phase Deliverable Acceptance criteria
1. Static graph editor Graph tab, canvas, stream nodes, transform nodes, local edges, inspector JSON. User can build and save a draft graph without starting workers.
2. Validation Backend validate_stream_graph plus frontend port diagnostics. Invalid stream-to-transform and transform-to-transform edges are rejected with node-level errors.
3. Live execution start_stream_graph compiles graph transforms into current transform workers. A chain such as raw -> highpass_iir -> rectify -> rms_window runs and exposes each derived stream.
4. Persistence Saved graph definitions and graph run state survive backend restart. Saved graphs reload in the UI with layout, config, and last known output stream ids.
5. Worker scheduler migration Graph run nodes submit jobs or long-running workers through the control-plane scheduler. Graph execution respects shared and dedicated compute slot policy instead of only local transform capacity.

Acceptance Tests

  • Open Stream Viewer and switch to the Graph tab without breaking Live, Experiment, or Transforms tabs.
  • Create a graph with one source node and one highpass_iir transform node.
  • Save the graph, refresh the browser, and confirm layout and config reload.
  • Validate the graph and confirm no diagnostics for a compatible EMG-like source stream.
  • Create an invalid transform node with no input and confirm validation returns a node-level error.
  • Create a chain raw -> highpass_iir -> rectify -> rms_window and start it.
  • Confirm each transform node receives an output stream id and appears in the active transform list.
  • Select each transform output and confirm the existing viewer/subscription path can observe live frames when data is available.
  • Stop the graph and confirm all graph-owned transform workers stop while unrelated transform workers keep running.
  • Restart the backend and confirm saved graph definitions reload without auto-starting workers in V1.

Non-Goals For V1

  • No arbitrary scripting language inside graph nodes.
  • No multi-user collaborative editing.
  • No cycles, feedback loops, or stateful event routing beyond current transform workers.
  • No automatic worker-scheduler migration in the first implementation.
  • No destructive cleanup of Kafka topics when graph nodes are deleted.
  • No generalized multi-input transforms until there is a concrete transform family that needs them.

Open Questions

  • Should saved graph definitions live first in backend SQLite, a local JSON file, or a channel metadata stream?
  • Should graph runs auto-start on backend restart, or reload as stopped definitions that require explicit operator action?
  • Should a transform node expose only one output port in V1, or should it reserve room for multi-output transforms now?
  • Should graph editing be collaborative later, or is a single-operator editing model enough for the first product surface?
  • Should graph nodes eventually support replay windows as first-class inputs, or should replay stay in separate reconstruction tools?

Risks

  • A canvas UI can become expensive quickly; the first slice should prioritize correct graph semantics over decorative behavior.
  • Running graphs can leak worker capacity if stop behavior is not tied cleanly to graph ownership.
  • Persisting only the visual graph without provenance would make historical runs ambiguous after edits.
  • Moving too much runtime logic into frontend graph state would conflict with the core library and worker-node direction.
