Script Nodes: User Code as a Transform

A node whose behavior is user-authored code, evaluated at runtime, that transforms stream data like any other transform. One execution venue: an embedded, sandboxed interpreter inside the C++ transform worker, so a script node is simply a transform whose body you type — same durable Kafka output, same provenance, same recording and training eligibility, same error path. Full-power Python stays a separate, admin-gated worker node rather than a second script runtime.

Runtime chosen by spike (QuickJS) · contract built · embedding next

1. Where this sits

Two pieces of prior work in this repo bear on it directly, and this plan is a continuation of both rather than a new direction.

The architecture was already decided. From the visual-programming rework plan: “Script/worker nodes are the extensibility escape hatch. Hot-path DSP stays compiled C++; arbitrary user processing runs as Python worker nodes on the existing control-plane/worker infrastructure.” That is the design this plan implements. It also matches the standing preference recorded elsewhere — build new platform capability in C++, keep new Python out of the data path — because a script node is user code rather than platform capability, and it runs in its own process rather than the C++ worker's.

The sequencing was deliberately deferred, and is now being reversed. Resolved decision, 2026-07-08: “Script-node sandbox: deferred. Script/worker nodes (Phase 6) move to the end, gated on a separate security review. v1 extensibility is data-driven config over the compiled C++ transform catalog.” Moving it early is a scheduling call and entirely reasonable — but the reason for the deferral (arbitrary code execution on shared compute) does not go away with the schedule. §6 answers it rather than re-deferring it, and the answer is what splits the two runners into different phases: the ClojureScript one is sandboxed by construction and can ship now; the Python one needs process isolation first.

Revised in rev 2: one venue, not two. Rev 1 proposed a browser runner (sandboxed ClojureScript via SCI) alongside a server runner. That is dropped. The browser tier's real selling point was a fast authoring loop — but the debounced restart_stream_graph_node path already built in Phase 7 delivers that at tens of milliseconds on localhost, using the same loop every other transform config edit uses. What the second venue actually bought was a divergence surface (two engines, two nk implementations, two error paths), a semantic wrinkle (a browser script cannot produce a durable channel under ADR-005, so some script nodes would be recordable and others not), and a graph that silently stops working when no tab is open. §7 keeps the good part — a preview action against the same engine — for a fraction of the cost.

3. The contract

A script is a pure function over one canonical channel frame:

stateless:  (fn [frame] frame')
stateful:   (fn [state frame] {:state state' :frame frame'})

frame = {:device_id "exg-01"
         :seq_no 1234
         :device_ts_us 1784308749619698
         :sample_rate_hz 500
         :channels [{:label "ch0" :samples [0.1 0.2 …]} …]}

That is NatSignalFrameDataSchemaV1 — the shape every existing transform already consumes and emits. The Python side is the same function with the same shape as a dict: def process(frame) -> frame.

Why the contract is fixed, and enforced both ways

The whole system is descriptor-driven: connection compatibility, viewer selection, input-mapping auto-pick and the “recommended next” list all read a node's output descriptor. For a script node that descriptor must be known without running the script — otherwise a script node could not be wired up until after it had executed, and editing a script would silently invalidate everything downstream of it.

So: a script consumes a channel frame and produces a channel frame, and it advertises the canonical descriptor statically. It may change channel count, labels and values freely — that is the entire point — but not the kind of thing it emits. A script that returns anything else is a node error, never a frame that reaches downstream consumers: they trust the descriptor, so emitting a malformed frame would relocate the failure somewhere far harder to diagnose. Both runners apply that check on their own side.

A pleasant consequence: because the viewer registry keys off the live frame shape, a script that collapses each channel to one value automatically renders as a feature vector instead of a waveform, with no configuration. That behavior is under test.

The toolkit a script gets

Bare clojure.core, str, set, math, and an nk namespace of frame verbs and the statistics a feature-extraction script reaches for first: map-samples, map-channels, reduce-channels, select-channels, channel-by-label, mean, rms, variance, std, zero-crossings, diff, sum, min-of/max-of, clamp. A per-channel RMS feature extractor is one line: 

(fn [frame] (nk/reduce-channels frame nk/rms))

4. One venue, chosen by measurement SPIKE DONE

spikes/script-runtime/ vendors Lua 5.4.7 and QuickJS, embeds each in a C harness, and measures the three controls plus throughput on realistic frames. Run it with make run. Every result was checked against a C reference implementation; both engines matched exactly.

Lua's count hook fires every N VM instructions and calls into C; QuickJS's handler is polled by the interpreter loop far more cheaply. The interrupt is not optional in production, so Lua's real figure is 0.088 ms/frame — making QuickJS+Float32Array about 9× faster than production-configured Lua on the mid case. This flips the intuition: Lua has the simpler C API and the more proven sandbox, but you pay 76% for the one control you cannot ship without.

What the numbers do and do not decide

Performance is not a feasibility question. Even the slowest configuration measured (QuickJS plain arrays on eeg-wide, 2.77 ms/frame) has ~360× headroom over the ~1 frame/s that case produces. natKit's frame rates are low — an EMG stream at 500 Hz with 50-sample frames is 10 frames/s. Nothing here is close to a bottleneck, so the choice rests on safety cost and ergonomics, not speed.

But the margin matters where headroom shrinks — many script nodes on one worker slot, or per-sample work heavier than RMS (FFT, resampling, convolution). That is where 5–13× is the difference between comfortable and not.

Implementation constraint: samples must cross as Float32Array, never as JS arrays. With plain arrays QuickJS is 3.5–4× slower than Lua — the entire QuickJS case rests on TypedArrays. Construction is one JS_NewArrayBufferCopy + JS_NewTypedArray: a single bulk memcpy instead of n property sets. Get this wrong and the choice was wrong.

Decision: QuickJS with Float32Array samples

  1. Its interrupt is effectively free; Lua's costs 76%, and the interrupt is not optional.
  2. TypedArrays give 5–13× headroom where it matters, and map 1:1 onto the sample buffers natKit already has.
  3. JS is widely known, and the same script would run natively in a browser if a scratch venue is ever wanted after all.

Cost: 820 K vs 220 K of stripped static binary, and a more verbose C API. Lua remains defensible if size or API simplicity dominates — but note the “I want a Lisp” argument does not favour it: Fennel compiles to Lua and inherits the 76% hook tax, whereas squint/cherry compile Clojure-flavoured source to plain JS at zero runtime cost. A Lisp surface is available on both sides and is cheaper on the QuickJS side.

Rejected: embedding CPython

Not a judgement call — a capability gap. CPython has no per-interpreter resource governor and no capability model: import os is always reachable, there is no interrupt, and there is no memory cap. RestrictedPython is AST hardening rather than a security boundary; subinterpreters (PEP 734) isolate state, not capability; the PyPy sandbox was removed years ago. Embedding it would also put the GIL and arbitrary user code inside the process owning the DSP hot path, where one hang or native-extension segfault takes down every unrelated transform sharing it. Python's place is §6's worker node, in its own process.

5. What is already built contract DONE

frontend-cljs/src/main/natkit/script/contract.cljs — the frame schema (malli), the frame verbs, and normalize-result, which is what turns a contract violation into a node error instead of a corrupt frame. Plus runnable starter scripts, so a new node opens with working code rather than a blank editor. 30 of the suite's 97 tests cover it (510 assertions, green).

Honest accounting on the SCI evaluator. natkit.script.sci (~200 lines + tests) was built as the rev-1 browser runner. Under rev 2's single venue it is not a shipping component — it becomes either an optional scratch evaluator or is deleted, and the frame verbs get reimplemented as the JS nk library. What survives is the contract and its enforcement rule, which is where the design thinking was. It also earned its keep as a spike: the measurement that killed it — SCI cannot be interrupted or memory-capped — is precisely the requirement that selected QuickJS.

Three things the tests caught while building the contract

  • Arity cannot be guessed by calling. The first cut tried (f frame) and fell back to (f state frame) on error. Unsound: a wrong-arity call to an SCI fn does not throw, it binds the missing parameter to nil, so a stateful script silently bound state=frame, frame=nil and failed with a baffling message. The same trap exists in JS — Function.length is the check, not a try/catch.
  • A claimed limit that did not exist. The first cut used SCI's :realize-max with a comment saying it bounded (vec (range)). It does not (measured — the test OOM'd the runner). Removed rather than left in to imply protection it does not give. Directly motivated §4's demand for a measured interrupt.
  • (/ 1 nil) is not a runtime error in ClojureScript — it yields NaN, so the user-visible failure is a contract violation, not a stack trace. The JS equivalent behaves the same way, so the error surface carries over.

6. Isolation — the deferral reason, answered

This is what the 2026-07-08 decision was waiting on. Under one venue the answer is short, because §4 measured it rather than asserting it.

For script nodes the question is closed. All three controls are real and verified in-tree: no ambient authority (7/7 host escapes denied — core QuickJS registers no I/O to escape from), interruptible (JS_SetInterruptHandler aborted an infinite loop on a wall-clock deadline), memory-capped (JS_SetMemoryLimit denied a runaway allocation cleanly). Plus JS_SetMaxStackSize for runaway recursion. One JSRuntime per script node, so there is no shared interpreter state and no global lock — which suits the thread-slot model better than a GIL would.

That means a script node needs no entitlement gate: a user cannot reach the host, cannot hang the worker, and cannot exhaust its memory. Blast radius is one node's own budget. What remains is operational hygiene rather than security — pick a sane per-frame time budget and memory cap, surface a budget breach as a node error, and make both configurable.

Python's place: the worker node, not a script runner

Full-power Python (scipy, sklearn, torch) is still worth having, and your VP rework plan already named it separately — “script / worker nodes”, two things. Keeping them apart is what lets script nodes be ungated and safe while Python stays a deliberate, admin-granted capability:

  1. Entitlement gate (already built). ADR-004 gives admin-owned shared/dedicated slots plus a per-user shared_compute_access flag. Gate worker-node submission on it and default to a dedicated slot naming the submitting user. Real control, zero new code.
  2. Resource limits on the child. RLIMIT_CPU, RLIMIT_AS, a wall-clock kill, no network by default. Bounds the blast radius of an accident, the common case.
  3. Container isolation. The requirement — not a nicety — once non-admin users can submit. natKit already ships a control-plane image, so this is packaging.

Calibration: on a single-operator lab machine (1) + (2) is proportionate, because a Python worker node is no more powerful than editing a transform and rebuilding. It stops being proportionate the moment someone other than the admin can submit one.

7. Editor surface

  • A code editor on the node. CodeMirror 6 with @codemirror/lang-javascript. rvbbit uses CM5 + react-codemirror2; CM6 is the current line.
  • A preview action — this is what replaces rev 1's browser venue. The inspector sends the script plus one captured frame over the existing WebSocket; the backend evaluates it once in the same QuickJS configuration the worker uses and returns the output frame (or the error). You get “try it before you wire it” for one new WS action, with zero divergence risk, no second engine and no frame-feeding plumbing.
  • Live editing rides the loop that already exists. A debounced config edit on a running graph triggers restart_stream_graph_node, restarting just that node and its downstream — the Phase-7 path, live-verified, identical to editing any transform's config.
  • Inline result on the node card — output shape, elapsed ms, or the error message with its phase. rvbbit's flow nodes show their value inline and it is the right idiom: a script node's whole point is the feedback loop.
  • A budget readout — time and memory used against the node's configured caps, so approaching a limit is visible before it trips.
  • No stateful toggle needed: arity comes from Function.length.

9. Open decisions

Two of rev 1's four are now closed by measurement. Defaults in bold.

  1. CLOSED — Runtime: QuickJS with Float32Array samples, per the §4 spike. Lua measured as a viable alternative that loses on the mandatory-interrupt tax.
  2. CLOSED — Venue: one, embedded. The browser runner is replaced by a preview action against the same engine.
  3. Default budgets: 50 ms per frame and 64 MB per script node, both overridable per node. Generous next to the measured 0.010 ms/frame, and low enough that a breach means a genuine bug. Worth a sanity check against the widest board you expect.
  4. Clojure surface (S4): defer — ship JS, add squint later if the appetite is real. It is purely additive and the engine is indifferent.
  5. Python worker node (W1) at all? Yes, eventually — it is the scipy/sklearn reach a sandboxed interpreter will never give you. But it is now genuinely optional rather than load-bearing, and it carries the isolation obligations in §6 that script nodes no longer do.
  6. Stateful script state: in-memory per run. The JSContext persists across frames, so state is just an object. Checkpointing it across restarts is possible (the worker infra already checkpoints job cancellation) but unmotivated.

10. Acceptance

S3: a user drops a script node on a running graph, types frame => ({channels: frame.channels.map(c => ({label: c.label, samples: [rms(c.samples)]}))}), hits preview and sees the output frame, wires it up, and the downstream viewer plots a per-channel feature vector live — having switched from waveform to feature-vector rendering on its own, because the frame shape changed. A syntax error shows inline on the node and stops the script rather than the graph. An infinite loop trips the time budget, marks the node error with the reason, and leaves every other node running.

And the property that makes it a transform rather than a special case: its output is a durable Kafka channel that a viewer taps, an experiment records, and a train node consumes — indistinguishable downstream from a compiled C++ transform, carrying a provenance record that names the script.
