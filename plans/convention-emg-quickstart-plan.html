Convention EMG Quick-Start

Stand up natKit at a convention with three EXG Pill EMG channels, run a 1–5 minute gesture-training session entirely from the Visual Programming page, train a classifier on that session, and go straight to live classifying — then save the person as a profile so they can walk up later and resume in one click. Data is explorable live at every pipeline stage, the training session is replayable, the ESP32 can reach us over WiFi/MQTT or a serial backup, and the target is 80–90% accuracy after the initial session.

Design captured — ready to sequence

The core insight: most of this is already built

Across the prior VP-rework, experiments-and-time, and topic-aware-channels efforts, natKit already has: the EXG Pill → MQTT → bridge → Kafka ingest path, a data-driven node catalog, an experiment/record node with a finger-counting protocol default, Hudgins feature transforms (mav/rms/zc/ssc/wl) plus sliding_window and combine, a train node that runs the LDA/SVM/RF pipeline with validation accuracy, an LDA live-classify transform in C++, descriptor-driven per-stage viewers (live data exploration), a timeline/DVR strip with backend re-run replay, and an experiment library that discovers recorded runs. This plan is therefore 90% integration and productization, not greenfield build — with three genuine gaps (serial ingest, profiles, and the train/serve accuracy skew) and one guided-flow layer that stitches the parts into a walk-up convention experience.

The one hard technical problem is accuracy in the live path (see the Accuracy section). Everything else is wiring, persistence, and UX.

The accuracy linchpin: train/serve parity

This is the single change that determines whether the live number matches the reported validation number. The training pipeline (natVR) and the live path (C++) currently extract features differently:

  • Normalization skew. Training normalizes features per session via a calibration profile (baseline.build_dataset(normalize=True)) and filters to phase=="hold" windows before fitting. The stored means/variances therefore live in normalized space. The C++ transformLdaClassify feeds raw window features — the model is being scored against inputs in the wrong space. This alone can gut live accuracy even when validation reports 90%.
  • Feature-order skew. Training emits a fixed per-channel order [mav, rms, zc, ssc, wl] (vector_to_flat_features). Live order depends on how the user hand-wires the combine inputs; nothing enforces it. A permuted vector scores garbage, and the only guard is a silent length check (wrong length → no output at all).
  • SVM/RF not deployable. Only LDA loads live (.joblib models can't be read by C++). For v1, classification is LDA-only; training may still evaluate SVM/RF for comparison.

The fix (Phase 2) — DECIDED: collapse the live classification path into one self-contained transform, emg_gesture_classify, that consumes raw EMG frames and internally reproduces the exact training pipeline: window (window_ms/hop_ms) → Hudgins features in the canonical order → per-feature normalization → LDA score → predicted_class + confidence.<label>. All of it — window params, feature list & order, normalization stats, LDA params — is driven by a single extended model bundle written by the trainer, so parity holds by construction. The granular mav/rms/… transforms stay for data exploration, but they are no longer the classification path.

Deferred by decision (not v1): the non-collapsed path — classification built from composable granular feature transforms wired on the canvas, with parity enforced across a multi-node pipeline rather than inside one node. It is a real future goal (it keeps the feature pipeline inspectable and editable), but solving parity across arbitrary user wiring is the harder problem. v1 ships the collapsed node; the composable version is a later effort once the collapsed path is proven.

Phasing

Ordered so the highest-risk correctness work (accuracy parity) lands before the productization that depends on it. Phases 0–2 are the technical spine; 3–5 are the walk-up experience; 6 is accuracy instrumentation and tuning.

Phase 0 — Verify & commit the existing golden path harden

Goal

Establish a known-good, end-to-end EMG → record → train → classify run against the live stack, and commit the large body of uncommitted VP work so this effort builds on a clean baseline. Nothing new is built — this de-risks everything downstream.

Work

  • Bring up the full stack (docker-compose.yml + docker-compose.dev.yml); confirm the 3-channel EMG stream appears in the stream list and plots live.
  • Hand-build the current best-effort live pipeline once (source → sliding_window → mav/rms/zc/ssc/wl → combine → lda_classify) and measure the skew: record a short session, train, paste the model path, observe live accuracy vs. reported validation accuracy. This quantifies the Phase 2 problem before fixing it.
  • Commit the outstanding VP branch work (experiments-and-time + topic-aware-channels are implemented but uncommitted per .claude/state.md).

Acceptance

A documented baseline live-accuracy number for a hand-wired LDA pipeline, and a committed tree.

Phase 1 — Serial backup ingest new

Goal

Let an ESP32 that can't use WiFi still reach natKit over USB serial, with zero backend or schema change.

Decision — serial → MQTT (not serial → Kafka)

The standard path is MQTT → bridge → Kafka. If the serial shim republishes the identical JSON frames onto the same MQTT topics (natKit/sending/emg/raw/emg.raw.<device_id>), then the bridge, topic naming, stream discovery, and everything downstream are byte-for-byte identical to the WiFi path. Choosing Kafka directly would mean re-implementing the bridge's schema_version→canonical-topic translation and the FNV-1a stream-id hashing outside the bridge — strictly more surface, more drift risk. So: serial → MQTT.

Work

  • Firmware serial-output mode: add a build flag (e.g. NATVR_TRANSPORT=serial) that writes the same newline-delimited serialize_frame_json frames to USB serial instead of (or in addition to) the MQTT publish. Reuses the existing serializer at natVR/firmware/main/main.cpp — only the sink changes.
  • Host serial→MQTT shim: a small Python entrypoint (revive the shape of the deprecated exg-pill-producer.py, but publishing to MQTT not Kafka): read pyserial lines, validate each against exg-pill-emg-data-v1.schema.json, publish verbatim to the MQTT broker on the standard topic. Package under natVR as natvr-serial-bridge.
  • Compose/dev wiring & docs: document running the shim on the convention laptop; note it needs the USB device and the MQTT host. Optional compose service (host-networked) for the laptop case.

Acceptance

An ESP32 in serial mode produces a stream indistinguishable in Kafka/stream-list from the WiFi path; a viewer plots it; the Quick-Start flow works over either transport with no graph change.

Fallback if firmware serial is out of scope for v1: the shim can instead read the existing CSV/ADC serial format and construct ExgPillEmgDataSchemaV1 JSON host-side (the deprecated producer already parsed CSV) — keeps firmware untouched at the cost of the shim owning frame assembly.

Phase 2 — Guaranteed-parity live classifier accuracy linchpin

Goal

Make live accuracy equal reported validation accuracy, and eliminate the hand-wired feature pipeline as a source of error.

Work

  • Extended model bundle (trainer side). When the pipeline selects a model, serialize a self-describing bundle alongside lda-model.json that includes: window_ms, hop_ms, sample_rate_hz, the ordered feature list ([mav, rms, zc, ssc, wl] per selected channel), the per-feature normalization stats (mean/std or the calibration profile actually applied in baseline.build_dataset), the channel selection, the class labels, and the LDA params. Written by natVR/src/natvr/select_model.py / model.py and copied to /models/<job_id>/ by persist_selected_model_artifact.
  • Self-contained C++ inference transform emg_gesture_classify. One transform that takes raw EMG frames and internally does window → Hudgins (reusing the existing reduceWindow, already ported from features.py) → normalize (new, from the bundle) → LDA score (reuse transformLdaClassify's math). It reads the bundle path from one config field. Parity is guaranteed because the same bundle drives windowing, order, and normalization. Add to buildTransformCapabilitiesJson / the node catalog.
  • Kill the manual model-path paste. On a completed train job, thread the persisted model_path from the train node directly into the downstream classify node's config (auto-fill, editable). Frontend: submitTrainJob / handleMlControlPlaneMessage (VisualProgramming/page.svelte) already receive report.model_path; wire it to the connected classify node instead of only displaying it.
  • Keep granular transforms for exploration. mav/rms/… stay in the catalog as taps a user can view; they are simply not the classification path anymore.

Acceptance

A model trained on a recorded session, dropped into emg_gesture_classify, classifies the same replayed session within a small delta of the reported validation accuracy (parity proven), and a fresh live session on the trained gestures produces stable predictions.

RESOLVED (read the code 2026-07-16): the fit-time normalization is rest-calibration, not a z-score. build_calibration_profile (natVR/src/natvr/calibration.py) computes, per channel, rest_mean_rms (avg RMS during the rest gesture) and scale_rms = active_mean_rms − rest_mean_rms (the rest→full-contraction dynamic range), then normalize_feature_vector rescales the amplitude features so rest ≈ 0 and full contraction ≈ 1 (rms→(rms−rest)/scale, mav and waveform_length divided by scale; zero_crossings/slope_sign_changes pass through). It also filters to phase=="hold" (plus rest) windows before fitting. This cancels electrode placement / skin impedance / per-person gain.

Implication for the live path (good news): the profile is just a few numbers per channel, so the bundle carries rest_mean_rms + scale_rms and the live transform applies the identical math — no separate live rest-capture is needed as long as placement is unchanged between training and classifying (exactly the convention flow: train, then classify immediately on the same pills). If pills are re-attached, retrain (ties into the Phase 4 recalibrate path).

Wrinkle — RESOLVED (user, 2026-07-16): build_calibration_profile needs an active_gesture to compute scale_rms and defaults to "fist". Decision: keep fist — the convention default protocol includes a fist gesture, so active_gesture="fist" works with no special-casing. Fist doubles as a good calibration anchor (a strong full-forearm contraction → broad dynamic range across all channels) and is classified like any other gesture — no need for a calibration-only class or an alternate scale derivation.

Phase 3 — Convention Quick-Start flow productization

Goal

Turn the walk-up scenario into a single guided flow on the VP page — no hand-wiring for the operator.

Work

  • Quick-Start starter template (extend starterTemplates.ts): a preset graph with the live EMG source auto-bound, an experiment node with a convention-tuned protocol, per-stage viewers for exploration, and an emg_gesture_classify node pre-placed (empty model until trained).
  • Guided steps layered on the existing pieces: (1) confirm the 3-channel stream & electrode placement (live viewer), (2) optional short rest capture if Phase 2 needs calibration, (3) record the gesture session (existing experiment runner UI, big cue prompt), (4) one-click "Train on this session" (the just-recorded run is pre-selected as train/eval via the experiment library discovery), (5) auto model-path → classifier goes live.
  • Convention-tuned default protocol: a short protocol (fewer gestures → higher accuracy; e.g. 3–4 well-separated gestures + rest, 3 reps, 2 s hold) sized to land inside the 1–5 min budget. Editable, but the default is chosen for walk-up accuracy.

Acceptance

An operator loads one template and, following on-screen steps, goes from bare canvas to live classifying in a few minutes without manually adding or wiring a single node.

Phase 4 — Individual profiles new

Goal

Persist a person as a first-class object so they can walk up later and resume live classifying in one click.

Work

  • Profile object & store (backend). A Profile = {participant_id, display_name, model_path, graph_id (the classify graph), protocol_id, channel binding / device_id, session_ids, best validation accuracy, timestamps}. Persist in a JSON store mirroring the existing stream-graph store (NATKIT_STREAM_GRAPH_STORE pattern → a new NATKIT_PROFILE_STORE), with the same atomic-write + load-on-startup mechanics.
  • WS actions: list_profiles / save_profile / delete_profile on the StreamViewer WebSocket, mirroring the graph-store actions. Frontend types + websocket.ts dispatch.
  • Profile picker (VP page): a profile list; "New profile" launches the Phase 3 flow and saves the result; selecting an existing profile loads its classify graph with model_path pre-filled and binds the current live channels → classifying immediately (no retrain). Reuses the composite/editor-metadata round-trip so a profile's graph reloads from the backend alone.

Acceptance

Record + train for "Alice" → save profile. Reload the page, pick "Alice", and live classification starts on her saved model against the live stream with no re-recording or re-training.

Note: a saved model reflects that person's electrode placement. If pills are re-attached differently, accuracy drops — the profile flow should offer a fast "recalibrate/retrain" path (re-run Phase 3 keeping the profile). Placement guidance belongs in the Quick-Start step 1.

Phase 5 — Live exploration & session replay verify/polish

Goal

Confirm the two "watch the data" clauses work on the Quick-Start graph and are one click away.

Work

  • Live exploration: the Quick-Start template pre-places viewers on the raw stream and on key pipeline stages (windowed, feature vector, classification) so the operator can eyeball signal quality and the feature space during a session. Uses the existing descriptor-driven viewer registry — no new renderers.
  • Training-session replay: verify the just-recorded session appears in the experiment library and that "Reprocess"/DVR replays it through the live graph (backend re-run from the session's historical offset). The mechanics exist (timeline strip + start_stream_graph.start_offset + experiment library); this phase confirms the just-recorded run is immediately selectable and scrubs cleanly.

Acceptance

During and after a session, viewers show data at each stage; the operator can scrub/replay the training session on the timeline and watch it re-run through the pipeline.

Phase 6 — Accuracy instrumentation & tuning tune

Goal

Surface accuracy where the operator can act on it, and give the levers to reach 80–90%.

Work

  • Surface validation accuracy in VP. The train node currently shows only status + model path; surface selected_mean_accuracy / mean coverage / per-class confusion (already in the report, rendered in MlPipeline) on the VP train node so the operator sees the number before going live.
  • Live confidence readout. The classification viewer already shows confidence.<label>; add a simple rolling live-accuracy / stability indicator during a known-gesture check so the operator can validate placement empirically.
  • Accuracy levers & guidance: fewer/well-separated gestures, good electrode placement, longer holds, more reps, per-session calibration (Phase 2). Optionally let training try LDA+SVM+RF and report the best, even though only LDA deploys live — a low SVM/RF-vs-LDA gap is a signal that LDA is adequate for this person.

Acceptance

A typical convention participant reaches 80%+ validation accuracy that holds up live (within the Phase 2 parity delta), with the number visible in the UI.

Risks & open questions

  • Normalization semantics (Phase 2): the exact fit-time normalization (baseline.py) must be pinned down before the bundle is designed. If it needs a per-session rest capture, the live flow inherits a calibration step.
  • LDA-only live ceiling: if LDA can't reach 80–90% for some people while SVM/RF can, a C++ SVM/RF inference path (or an ONNX export) becomes necessary — a larger effort deferred out of v1 but flagged here.
  • Model artifact reachability — DECIDED (add the mount + plumbing): remote ML workers can't currently deliver a live-loadable model, and mounting /models alone is necessary but NOT sufficient (verified in code 2026-07-16). persist_selected_model_artifact is only called on the in-process path (_run_job_in_slot, ~L3059); the remote-worker completion handler _handle_report_worker_job_state (~L2937) calls sanitize_pipeline_report(report) with no model_path, so it returns model_path=None / artifact_storage="ephemeral_scratch" and persists nothing; the worker's selected_model_path points at its own ephemeral (and backend-unreachable) workspace. Fix = (1) mount natkit-v0-models rw on ml-worker-a in docker-compose.dev.yml, + (2) have the remote worker persist into that mounted /models/<job_id>/ before its workspace is cleaned and report the durable path, and have _handle_report_worker_job_state pass it through sanitize_pipeline_report(report, model_path). Zero-code fallback for v1: pin training to the in-process control-plane worker (already persists correctly) — fine for a serialized one-person-at-a-time booth; costs the remote worker's parallel slots.
  • Placement drift: a saved profile's accuracy is tied to electrode placement; re-attach = likely retrain. Set expectations in the UI; make retrain fast.
  • Serial throughput: 3ch × 1 kHz × int16 as JSON over USB serial — confirm the baud rate and frame batching keep up (the 50-samples/frame batching already helps). Binary framing is a fallback if JSON-over-serial is too heavy.
  • Non-goal (v1): mixing live + historical inputs in one run (already deferred upstream); cross-person model transfer; automatic electrode-placement detection.

Suggested sequencing

0 → 2 first (verify baseline, then the accuracy fix) because the whole story hinges on live classification actually working. 1 (serial) is independent and can run in parallel — it touches firmware + a host shim, not the graph. 3–5 (Quick-Start, profiles, exploration/replay) layer productization onto the working spine. 6 is continuous but formally closes the accuracy target. Phases 1, 3, 4 are the only ones with meaningful new surface; the rest is verification and focused correctness work on top of what's already shipped.
