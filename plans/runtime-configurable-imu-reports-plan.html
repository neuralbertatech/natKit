Runtime-configurable IMU reports

TEC-NATKIT-40 · drafted 2026-08-14 · depends on TEC-NATKIT-39

The ask

Expose the four BNO08x reports — accelerometer, gyroscope, magnetometer, rotation vector — as toggles in the frontend, carried to the device over the EXECUTION_COMMAND channel, so which sensors a node collects becomes a runtime decision rather than a rebuild.

The motivation is TEC-NATKIT-35's measured result: the hub will not deliver all four at 100 Hz, and getting gyro or rotation genuinely past 100 Hz requires giving one of them up. That trade is currently a Kconfig edit and a reflash. It should be a switch.

⚠ The encoding change is not required, and separating it makes this much smaller

The ask assumed the wire format needs to become configurable. It does not, and this was checked rather than assumed.

sampleFromReadings() already gates every sensor on readings.X.has_data, which is only set when a report actually arrives. A disabled report never arrives, so its has_data bit stays clear and its floats stay zero — which is exactly the "absent, not zero" distinction the schema already carries and every decoder already honours. Turning a report off today produces a correct frame with no format change at all.

What a variable-length encoding would buy is airtime: a frame carrying only accelerometer and gyroscope could be 34 bytes per sample instead of 62. That is worth having eventually — airtime is shared across nodes, so smaller frames mean more nodes per channel — but it is not what makes the feature work, and it is measurably not the current constraint: leaf B delivered 100 samples/s at 524 bytes and again at 644 bytes. Deferred to its own ticket.

⚠ Two real gaps, neither of them the encoding

1. has_data is sticky, so a runtime disable leaves a stale value forever

SensorReading::has_data is documented as "false until the first report arrives" and is never cleared. Disable a report at runtime and the last value it produced keeps being copied into every subsequent sample, marked present, indefinitely. This is the one change the data path genuinely needs — disabling must clear the reading, not just stop refreshing it. It is a small fix, but nothing in the current code does it, because nothing could disable a report while running.

2. The leaf has no network at all

The old firmware's command channel worked because every node was a full MQTT client. In the current architecture a leaf has zero IP connectivity — grep mqtt leaf.cpp returns nothing. Commands arrive at the primary over MQTT and must be relayed to the leaf over ESP-NOW.

The transport for that already exists: the primary already sends TimeBeacon, TimeFollowUp, SyncState and SyncMarker downstream, so this is a new frame type on an established path rather than a new path. But the plumbing — correlating a command id, routing to one node by MAC, carrying the answer back up — does not exist.

This downlink is a shared enabler. TEC-NATKIT-37 (hub-feedback transmit power) is blocked on exactly the same missing capability: the hub knows a leaf is failing and has no way to tell it. Building the command relay unblocks both.

What already exists, and is correct

  • Backend — handleSendDeviceCommand in StreamViewerWebSocket.cpp: topic naming, command id generation, args pass-through as raw JSON, a reply thread with a clamped timeout, and correlation against the device log topic. Untouched by the migration and still right.
  • Frontend — the Visual Programming command buttons, verified on hardware 2026-08-05.
  • Device protocol shape — CommandRequest in the old firmware carries command_id, command and args as raw JSON, with fixed-size buffers and a two-queue design that keeps MQTT I/O off the sensor task. Worth porting as a design, not as code: the constraint it solved (PubSubClient thread-safety) does not exist in ESP-IDF, but the shape still fits.

Slices

#SliceWhy it is separable
1Command relay: server → primary → leaf, and the answer back. New ESP-NOW frame types for command and log; the primary subscribes per known node and routes by MAC. TEC-NATKIT-39. Ends with an existing command (an echo or a status dump) working end to end from the frontend. No IMU involvement, and it unblocks TEC-NATKIT-37.
2Runtime report configuration on the leaf. An NVS-persisted enable mask that enableReports() reads instead of the Kconfig defaults, plus clearing the sticky SensorReading on disable. Testable entirely over the console with no command channel, by writing NVS directly. Also the slice that must survive a hub reset — enableReports() is already re-called there and must pick up runtime state, not compiled-in state.
3get_reports / set_reports commands. args carries the four booleans; the reply carries the resulting configuration, which is what the frontend renders. The enabled set is configuration, so it is read back over the command channel rather than repeated in every data frame at 10 Hz. That is why no header field is needed for it.
4Frontend toggles. Four switches, populated by get_reports, written by set_reports, with the disabled sensors visibly disabled rather than silently flat. ⚠ A disabled sensor and a sensor that has not reported yet look identical in the data. Only the command reply distinguishes them, so the UI must take its truth from there and not from has_data.
5Deferred: variable-length encoding. A presence mask in the frame header, sample size from its popcount. Buys airtime, not function. Costs a frame version and a decoder change everywhere. See the open decision below — it makes the recording problem strictly worse.

⚠ The open decision: what a toggle does to a recording

Parquet has one column set per file. If reports can be toggled while a recording is running, a file's schema changes halfway through, and this is true whatever the wire encoding does — it is a property of the feature, not of slice 5.

Three options, and this needs Zach rather than a default:

  • Refuse toggles while recording. Simplest and most honest; the command returns an error. Costs the ability to change mid-session.
  • Keep every column, mark the disabled spans. Nothing breaks and files stay comparable, but a column of zeroes needs something alongside it saying "not collected" — and the transform mapping that drives Parquet columns has no way to express that today.
  • A config change rolls a new file. Clean schemas, but a session becomes several files and everything downstream must join them.

Related and already true: a Parquet export from a frame-version-1 recording carries three magnetometer columns of zeroes with nothing flagging them (TEC-NATKIT-38). Whatever is chosen here should cover that case too.

Risks worth naming

  • Disabling everything. sampleFromReadings() emits nothing unless accelerometer, gyroscope or rotation has data, so a node with only the magnetometer enabled goes silent — correctly, but it will look like a fault. set_reports should refuse it.
  • Configuration drift across nodes. Once this is per-node and persistent, two leaves in one session can be collecting different things. The recording metadata needs to say what each node was configured for.
  • A command that arrives and is never answered. The backend already clamps a timeout, but over ESP-NOW a command can be lost silently — the same near-far problem that has leaf …0644 at 0 samples/s (TEC-NATKIT-37). The relay needs its own acknowledgement, not just the application-level reply.
