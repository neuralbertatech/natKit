natKit - multi-language bindings - plan - July 7 2026

C ABI Foundation for Multi-Language Bindings

Stop hand-porting Kafka plumbing into every language that touches natKit data. Move the logic that Python currently reimplements from scratch into shared C++ libraries behind a stable extern "C" ABI, extending a pattern that already exists and already works (libnatkit-core's StreamStitch.cpp shim, consumed today via ctypes from natVR). Python is the first client to migrate; Java and Rust follow later against the same ABI once it is proven and stable.

Scope: libnatkit/lib/libnatkit-core, libnatkit/libnatkit/core/kafka, natVR/src/natvr, Dockerfile_natkit_ml_control_plane.

Decision

  • Adopt a stable extern "C" ABI as the single boundary for every non-C++ language that needs natKit's stream/schema/Kafka logic, instead of writing bespoke per-language implementations or per-language bespoke bindings (e.g. pybind11/nanobind wrapping C++ classes directly).
  • Extend the ABI shim pattern that already exists in libnatkit-core/src/StreamStitch.cpp (POD structs, caller-allocated output buffers, int status-code returns) rather than inventing a new one.
  • Python binds via ctypes, mirroring the already-deployed natVR/src/natvr/libnatkit_stitch.py pattern. This deliberately avoids pybind11/nanobind, whose compiled extension modules are pinned to a specific CPython ABI version — the dev venv runs Python 3.14 while Dockerfile_natkit_ml_control_plane pins 3.12, and ctypes loads a plain shared library at runtime with no per-version rebuild.
  • Keep the Kafka transport ABI (librdkafka-backed) in its own shared library, separate from libnatkit-core's ABI — libnatkit-core has an ESP-IDF (embedded) build branch with zero Kafka dependency today, and folding Kafka in would break that target.
  • Write down ABI conventions (naming, versioning, error handling, memory ownership) once, before the first new symbols ship, since retrofitting a policy after Python/Java/Rust depend on the symbols is expensive.
  • Java and Rust bindings are explicitly future work against the same ABI — not started in this plan.

Why This Exists

The bug that surfaced this

  • natVR/src/natvr/topics.py::_stable_stream_id() is a byte-for-byte reimplementation of stableStreamId() in StreamViewerWebSocket.cpp (FNV-1a hash) — two independently-maintained copies of the same logic.
  • This class of duplication is exactly what let the recent composite-graph race bug (chained transform topics resolved via live Kafka metadata rather than deterministic creation) go unnoticed for as long as it did — different problem, same root cause: logic re-derived per call site instead of shared.

It runs deeper than topic naming

  • natVR/src/natvr/emg_consumer.py hand-decodes JSON for ExgPillEmgDataSchemaV1, MarkerEventV1, and SessionMetadataRecord — schemas that already have canonical C++ encoders/decoders sitting in libnatkit-core.
  • classifier.py + bridge/hand_state_bridge.py aren't just a duplicate Kafka client — they're an independent Python-side "transform worker" producing a hand_state topic, duplicating the role of the C++ backend's createTransformWorker, not just its plumbing.

Target state

  • One implementation of stream/topic/schema logic, in C++, exposed through a stable ABI.
  • Python, Java, and Rust each get a thin, idiomatic wrapper over that ABI instead of a parallel reimplementation.
  • New logic gets one place to fix bugs, not N places to remember to keep in sync.

C ABI Conventions

Written once, applies to every phase below. Land this alongside Phase 1 — before it, there is no policy to violate; after it, retrofitting is expensive.

Concern Convention
Symbol naming nat_<module>_v1_<verb> (e.g. nat_core_v1_stream_id) — the version segment lets a future breaking change ship as _v2_ alongside the old symbol instead of breaking every existing caller in place.
Header layout Split a pure-C header, libnatkit-core-abi.h, containing only extern "C" typedefs/declarations. libnatkit-core.hpp today mixes C++ class declarations with the extern "C" block in one file — bindgen, jextract, and Panama FFM cannot parse C++ syntax even to skip past it. Do this at Phase 1 so every later phase adds symbols to the right place from the start.
Status codes int return, 0 = success, nonzero = error — matches StreamStitch.cpp today. No exceptions cross the ABI boundary.
Struct layout Fixed-width types only (int64_t, uint32_t, ...), no packed-struct pragmas, fields are append-only after first release — never insert or reorder. Both are already true of the existing structs; keep it true going forward.
Fixed-size outputs Caller allocates the output buffer at a size it already knows (matches every existing function). No change needed for this class of call.
Variable-length outputs (new — no precedent exists yet) Two-call pattern: first call with a null/zero-size output buffer returns the required size; caller allocates and calls again to fill. Preferred over callee-allocates-plus-nat_free() because it avoids allocator-mismatch crashes across language runtimes and maps more directly onto JNI/Panama/bindgen than an owned-pointer-plus-free-function convention.
Stateful / opaque handles (Phase 4) Opaque pointer typedef (e.g. nat_kafka_broker_t*) returned by an explicit _create call, released by a matching _destroy call. No handle is valid across a process boundary — each process owns the handles it creates.
Threading ctypes.CDLL calls release the Python GIL for the call's duration, so concurrent calls from multiple Python threads genuinely execute inside the library concurrently. Any static/singleton state (e.g. Registry::createDefaultInitializeRegistry()) must be audited for thread-safety, or the function must be documented as single-threaded-caller-only. Cross-process (C++ backend vs. a Python process) is not a concern — each process loads its own copy of the .so with its own state.
Versioning / stability Exported symbols are append-only. Add an exported-symbol diff (e.g. abidiff) to CI, comparing against the previous tag, so an accidental breaking signature change is caught before it ships.

Phased Rollout

Phase 0 Independent

Fix the immediate race bug: createStream() in the Kafka module produces a reserved-key sentinel record synchronously so a topic deterministically exists before a downstream chained transform tries to resolve it, instead of relying on Kafka's lazy auto-creation. Consumers skip the sentinel key before schema decoding.

Not re-planned here — already agreed separately. Ships independently of the bindings work below; reference only.

Phase 1 Start here

Move stableStreamId() into libnatkit-core, next to BasicTopicInformation. Add libnatkit-core-abi.h. Add extern "C" functions for stream-id computation and topic-string build/parse, following the conventions above. Point topics.py at them via a new ctypes module mirroring libnatkit_stitch.py. Land the ABI conventions doc in the same change.

Files: libnatkit-core/src/BasicTopicInformation.cpp, new libnatkit-core-abi.h, StreamViewerWebSocket.cpp (call the moved function instead of a local copy), natVR/src/natvr/topics.py. Zero new dependencies — no librdkafka needed.

Phase 2 With Phase 1

Not a separate ship — a checklist that lands with Phase 1: thread-safety audit of Registry/static state, the versioning policy written down, abidiff wired into CI. Kept as its own section here so the conventions are scannable independent of the code change.

Phase 3a Design pilot

Design and implement the variable-length JSON encode/decode ABI convention against exactly one schema — MarkerEventV1, the simplest. Validate the two-call size/fill pattern end-to-end before committing to it elsewhere.

Phase 3b Rollout

Apply the validated Phase 3a pattern to the remaining schemas emg_consumer.py hand-decodes today: ExgPillEmgDataSchemaV1, SessionMetadataRecord, and any others found during the port.

Phase 4 Heavier lift

New extern "C" shim over BrokerManager/TopicMessenger produce/consume, in its own shared library — not merged into libnatkit-core. Requires packaging work: add librdkafka and build the kafka module into Dockerfile_natkit_ml_control_plane, add a LIBNATKIT_KAFKA_PATH env var mirroring LIBNATKIT_CORE_PATH. Migrate emg_consumer.py, session_publish.py, replay.py, reconstruct_session.py onto it.

Phase 5 Deferred

Open question, not decided here: classifier.py + bridge/hand_state_bridge.py act as an independent Python-side transform worker (producing/consuming hand_state). Keep it as a consumer/producer on top of the shared plumbing from Phases 1-4, or eventually promote live classification into a first-class node kind in the C++ stream-graph engine and retire the parallel pipeline? Needs its own follow-up design doc.

Phase 6 Future

Java bindings (JNI or Project Panama FFM) and Rust bindings (bindgen), both against the same stable ABI from Phases 1-4. Not started in this plan — the point of Phases 1-4 is to make this an addition, not a rewrite, when it happens.

Verification / Acceptance Tests

Phase Verification
Phase 1 A golden-vector fixture (namespace/identifier pairs → expected uint64) checked in once, read by both a C++ test binary and the new Python ctypes binding — not regenerated per test run. Cover the existing stream_id == 0 → 1 fallback and multibyte identifiers.
Phase 3a/3b Per-schema round trip against real captured Kafka payloads (not synthetic ones): C++ encode → Python ctypes decode, and the reverse, byte-for-byte comparison.
Phase 4 Integration test producing via the new Python shim and consuming via the existing C++ BrokerManager (and the reverse direction), against a real or test Kafka broker, asserting topic string and payload bytes match.
Cross-cutting abidiff (or equivalent exported-symbol diff) in CI against the previous release tag, tied to the append-only versioning policy.

Non-Goals For This Plan

  • No Java or Rust binding implementation work — Phase 6 is a placeholder for later, not scoped here.
  • No decision on the classifier.py architecture question — Phase 5 is explicitly deferred to its own design doc.
  • No re-specification of the Phase 0 race-fix implementation details — cross-referenced only, already agreed separately.
  • No changes to the ML pipeline's model-persistence gap (ephemeral training-job scratch storage) — unrelated to this migration.

Open Questions

  • Phase 5's resolution: does live hand-state classification stay a Python-side consumer/producer, or become a first-class C++ stream-graph node type?
  • Should Java and Rust bind directly against libnatkit-core-abi.h as-is, or does each language need its own thin shim header layered on top for idiomatic type mapping?
  • Where should the Phase 4 Kafka-transport ABI's shared library physically live in the build tree — alongside libnatkit-core-kafka-cxx or as a fully separate CMake target?

Risks

  • ABI versioning debt: if the naming/append-only policy from Phase 1 isn't actually followed on later changes, every downstream language binding breaks silently at load time or, worse, at a mismatched-struct-layout runtime crash.
  • The GIL-release thread-safety gap is easy to miss because it won't reproduce in casual single-threaded testing — needs an explicit audit pass, not just "it worked when I tried it."
  • librdkafka packaging in Phase 4 meaningfully increases the ml-control-plane Docker image's build complexity and time; underestimate this and it becomes the phase that stalls the whole effort.
  • Scope creep risk: Phase 5 is deliberately left open, but it's tempting to fold classifier.py's redesign into this plan since it's adjacent — resist that; it deserves its own design doc with its own tradeoffs.
