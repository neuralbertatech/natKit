Toggleable Serial Backup Transport

Make USB-serial a runtime-toggleable backup for EXG-Pill / ESP32 EMG nodes, with WiFi/MQTT staying the primary path. Today serial is a separate compile-time build (NATVR_TRANSPORT_SERIAL=1) with no wireless at all — you must reflash to switch. For the convention-center demo, where the RF environment is hostile, we want a device that boots wireless-first and can fall back to (or be flipped to) serial without a reflash, so a flaky 2.4 GHz floor never takes the booth down.

Design captured — ready to sequence

Why: a convention floor is the worst case for 2.4 GHz, and reflashing mid-demo is not an option

The EMG classify pipeline runs end-to-end today, but every frame reaches natKit over WiFi → MQTT → Kafka. A convention hall is saturated with competing APs, phones, and badge scanners; MQTT can stall or the join can fail outright. A wired USB path to the booth laptop is immune to all of that. We already proved a serial path works — but it is an either/or firmware image, which means the fallback decision has to be made at flash time, before we know whether the RF will hold. This plan turns that into an operational toggle the booth operator controls in seconds.

Requirement (explicit): WiFi/MQTT is the primary transport and its behavior must not regress. Serial is an optional backup, off by default, that can be toggled on — and ideally engages automatically when wireless drops.

Already landed (the spine this builds on)

Groundwork from the Convention EMG Quick-Start plan, Phase 1 (branch vp-rework-phases-0-2):

  • have Firmware serial emit: a compile-time NATVR_TRANSPORT_SERIAL flag (main.cpp) writes the same newline-delimited exg.pill.emg.data.v1 JSON frames to the USB console via emit_serial_line (one locked puts+fflush), and quiets logs to ERROR so the stream stays clean.
  • have Host shim serial_bridge.py (natvr-serial-bridge; serial extra = pyserial + paho-mqtt): reads the lines, skips non-JSON, and republishes the original bytes onto natKit/sending/emg/raw/emg.raw.<device_id>. The KafkaMosquittoBridge routes MQTT → Kafka on the payload's schema_version, not the topic, so the Kafka stream is byte-identical to WiFi — the whole downstream pipeline (stream discovery, reconstruction, training, live classify) sees no difference. Tests: test_serial_bridge.py (routing/validation, no hardware).
  • gap It is a mutually-exclusive build: the serial image skips WiFi/NTP/MQTT bring-up entirely (app_main) and the WiFi image never touches the console. There is no runtime toggle, no wireless-primary + serial-backup coexistence, and serial timestamps come from the unsynced local monotonic clock (no NTP).

The transport-mode model

Replace the compile-time #if split with a transport mode the firmware holds in a runtime variable, initialized from a menuconfig choice (Phase 2). The variable is still needed at runtime because AUTO flips between MQTT and serial per frame; menuconfig just sets which mode the image ships with. Three modes; AUTO is the recommended demo default because it satisfies “wireless primary, serial backup” by construction, never double-publishes, and needs no live toggle at the booth — you flash the AUTO image and it self-manages.

ModeWireless (MQTT)Serial (USB)Use
WIRELESS Primary — publishes every frame (today's default). Off. Normal operation / good RF.
AUTO (recommended demo default) Primary — publishes while MQTT is connected. Engages only while MQTT is down (past a debounce), stops when it recovers. Booth: wireless-first, serial catches any RF dropout with no operator action.
SERIAL Off (or best-effort, see open questions). Always emits. Known-bad RF: force the wired path, ignore WiFi entirely.

No duplicates by design: the two emitters are mutually exclusive per frame — a frame goes to MQTT or the console, never both — so the same (device_id, seq_no) can't reach Kafka twice through one device. The host bridge still de-dupes across a switchover window as a belt-and-suspenders (Phase 4).

Phase 1 — Runtime transport mode in firmware new

Goal

One firmware image that can be any of the three modes at runtime; WiFi path byte-for-byte unchanged in WIRELESS.

Work

  • Introduce g_transport_mode (enum) initialized from the Kconfig choice (Phase 2) and convert the compile-time #if NATVR_TRANSPORT_SERIAL branches in publish_task, heartbeat_task, and app_main into runtime switches. The old NATVR_TRANSPORT_SERIAL define collapses into the CONFIG_NATVR_TRANSPORT_* Kconfig options (back-compat: map the old define to the SERIAL choice).
  • Always bring up WiFi/NTP/MQTT unless mode is SERIAL — the primary path is unconditional in WIRELESS/AUTO. Bring-up failures stay non-fatal (they already background-reconnect); don't ESP_ERROR_CHECK-abort so a demo device still runs and can fall back.
  • Per-frame emit decision in publish_task: WIRELESS → MQTT; SERIAL → emit_serial_line; AUTO → MQTT when networking_mqtt_is_connected(), else emit_serial_line (Phase 3 adds the debounce). Same for the heartbeat/status frame.
  • Console hygiene: only quiet logs to ERROR while serial is actually emitting, so WIRELESS keeps its normal INFO diagnostics.

Acceptance

A single image runs wireless with no behavior change; forcing SERIAL at boot streams clean JSON to USB; the bridge ingests it byte-identically.

Phase 2 — The toggle: a menuconfig dropdown new

Goal

Select the transport mode from idf.py menuconfig — a first-class ESP-IDF build option — instead of a bare -D define.

Work

  • A Kconfig choice in main/Kconfig.projbuild: natVR Transport → Wireless (WiFi/MQTT) [default] / Auto (wireless, serial fallback) / Serial (USB backup), producing CONFIG_NATVR_TRANSPORT_WIRELESS|AUTO|SERIAL. This is the dropdown in menuconfig and is also settable headless via sdkconfig.defaults (e.g. a checked-in sdkconfig.defaults.demo that pins AUTO).
  • Seed g_transport_mode from the choice at boot (Phase 1 reads CONFIG_NATVR_TRANSPORT_*).
  • Status visibility: the heartbeat/status frame already flows to natKit — add the active transport_mode so the UI/logs show which path a device is on (in SERIAL/AUTO-fallback the status rides the same serial line).

Build-time, by design. A menuconfig choice is baked into the image, so switching modes is a rebuild + reflash, not a live booth flip. That is fine — and intended — because the demo ships the AUTO image, which needs no live toggle (Phase 3 does the wireless→serial handoff automatically). If a no-reflash live flip is ever wanted, layer an NVS/console-command override on top of the Kconfig-seeded default; it is explicitly out of scope here.

Acceptance

idf.py menuconfig shows a natVR Transport dropdown; building each option yields a device that boots in that mode; sdkconfig.defaults.demo pins AUTO for a one-command demo build; natKit shows the active mode per device.

Phase 3 — Auto-fallback (wireless-primary, serial-safety-net) new

Goal

In AUTO, ride WiFi and transparently cover any dropout with serial — the behavior that actually protects the demo.

Work

  • Debounced switchover: emit serial only after MQTT has been down for N ms (hysteresis) to avoid flapping on a brief reconnect; return to MQTT after it has been stable for M ms. Frames stay queued (bounded g_frame_queue) across the gap; stale frames past kMaxFrameAgeUs are dropped exactly as today, so a long outage sheds old data rather than back-flooding.
  • One source at a time: the connected-state gate guarantees a frame is published to exactly one transport, so Kafka never sees duplicate seq_nos from a single device during the handoff.
  • Log the transitions (rate-limited) so the booth operator can see “fell back to serial” / “wireless recovered.”

Acceptance

Pull the AP / block MQTT mid-stream: frames continue over serial within the debounce window with no duplicates and no operator action; restoring WiFi returns to the wireless path.

Phase 4 — Host bridge hardening + a one-command backup runner tune

Goal

Make serial_bridge.py robust to real switchovers and trivial to run at the booth.

Work

  • De-dupe by (device_id, seq_no) over a short sliding window, so if wireless and serial ever briefly overlap (e.g. an operator forces SERIAL while MQTT is still flushing), the bridge drops the second copy before MQTT.
  • Optional host-timestamp rewrite for unsynced serial frames (see Phase 5): a --stamp-host-time flag that fills device_ts_us from the host wall clock when the firmware had no NTP, keeping the Kafka stream monotonic.
  • Auto-detect the port (scan /dev/ttyACM* / by USB VID:PID) and auto-reconnect on unplug, so a bumped cable doesn't kill the booth.
  • Run-alongside story: a documented one-liner (or a compose sidecar / systemd-style supervisor) that starts the bridge against the running stack; keep it off by default so it's genuinely opt-in. The bridge running is the host-side “serial enabled” toggle; pair it with the firmware being in AUTO/SERIAL.

Acceptance

Start the bridge, force a switchover, and Kafka receives a clean, de-duped, monotonically stamped stream; unplug/replug the cable and it recovers on its own.

Phase 5 — Timestamp & train/serve parity across the seam tune

Goal

Don't let the transport switch corrupt time alignment that reconstruction, the timeline, and the windowed classifier depend on.

Work

  • Prefer NTP even in fallback: in AUTO, WiFi is still associated during a broker-only outage, so keep NTP running and stamp serial frames with NTP time when available — only a full WiFi loss forces the monotonic clock.
  • Document the monotonic case: a serial-only device (no NTP) produces session-local timestamps. That is fine for the windowed EMG classifier (alignment is intra-session and the model is windowed), but cross-device combine and absolute-time replay degrade — call it out, and let the host-timestamp rewrite (Phase 4) restore a wall-clock reference for the record path.
  • No pipeline changes expected: because frames stay byte-identical, the classify bundle / featurize path is untouched; this phase is verification + docs, not code.

Acceptance

A session recorded across a WiFi→serial switch reconstructs and trains without a time discontinuity that breaks windowing.

Phase 6 — Booth dress rehearsal new

Goal

Prove the whole thing on the actual demo hardware before the floor.

Work

  • Throughput headroom: confirm the full frame rate (4 channels × sample rate) fits the USB-CDC console without back-pressure stalling publish_task — measure frames_dropped_stale under serial load. Expected to fit as-is (verbose JSON at 4 channels). If it doesn't, the byte lever is a compact serial frame (small binary or CSV; the bridge rebuilds canonical JSON so Kafka stays byte-identical) — not base64, which is an encoding that inflates ~33%, and not per-frame deflate (poor ratio + CPU/latency on tiny frames). Treat any encoding change as a contingency this spike decides, not up-front work.
  • Failure drills: kill the AP, saturate the band, unplug/replug USB, power-cycle a device — verify wireless-primary, clean fallback, persistence, and recovery each time.
  • Operator runbook: a half-page card — how to set AUTO, start the bridge, read the active mode, and what “good” looks like.

Acceptance

On the demo laptop + device, the classify pipeline stays live through an induced RF outage, end to end, with a written runbook.

Risks & open questions

  • USB-CDC throughput: serial must sustain the raw frame rate. If it can't, options are down-sampling in serial mode, larger frames, or accepting drop under outage. Confirm on hardware before committing to AUTO as default.
  • SERIAL + WiFi coexistence: in forced SERIAL, do we leave WiFi off (simplest, guaranteed no dup) or keep it associated for NTP only? Lean: off, with host-timestamp rewrite covering the clock.
  • Where the toggle lives: decided — menuconfig. A Kconfig choice (build-time), shipped as the AUTO image so the booth needs no live flip. Consequence: changing mode = rebuild + reflash. A no-reflash runtime override (NVS/console) is deferred unless a live flip proves necessary.
  • One USB port per device: serial backup is inherently per-cable — N devices need N ports + N bridge instances (or one multi-port bridge). Fine for a single-participant booth; flag for multi-device.
  • Duplicate risk on manual force: forcing SERIAL while MQTT is mid-flush could momentarily double-emit at the seam; the host de-dupe (Phase 4) is the safety net.
  • Non-goals (v1): a natKit-UI button that flips device mode remotely (the toggle is device-side + host-bridge-side); serial for non-EXG sensors; bidirectional control beyond the mode command.

Suggested sequencing

6 (bench throughput check) arguably comes first as a spike — if USB can't carry the rate, the mode design changes. Then 1 (runtime mode) is the foundation everything hangs off, 3 (auto-fallback) is the behavior that actually protects the demo, and 2 (toggle) makes it operable. 4 (bridge hardening) and 5 (timestamps/parity) are correctness + resilience that can land alongside. 1–3 are firmware (ESP-IDF, needs the device + idf.py); 4–5 are host Python; 6 is on the real booth kit. Keep WiFi the untouched default at every step so a half-finished toggle never regresses the primary path.
