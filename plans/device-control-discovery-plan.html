Plan · TEC-NATKIT-10 (#321) · TEC-NATKIT-102

Device control discovery, driven by a registry

Drafted 2026-08-26 · depends on TEC-NATKIT-101 (#469) for its end state

PROPOSED — not started

The problem, stated exactly

The Controls section on a Visual Programming node is hardcoded. SOURCE_BUTTON_CONTROLS and SOURCE_TOGGLE_GROUPS are static constants shown for any node of kind stream_source, regardless of what device is behind it.

Concretely: a Muse headband or an EMG pill source node renders four BNO08x report toggles it does not have, and "Read from device" sits there until it times out. The same shape as an un-flashed leaf offering an Identify button that answers nothing.

Only the values are device-driven today (the on/off states come from get_reports). The menu is an assumption compiled into the frontend.

What the device advertises

A device publishes what it can do on the HARDWARE_CONFIGURATION channel, which already exists in StreamType and maps to the topic prefix Configuration:

Configuration-<device_id>-Json-NatKitDeviceControlsV1

Why that channel and not the two obvious candidates

  • META is per-stream naming — BasicMetaInfoSchema carries only a streamName. Controls belong to a device, so the granularity is wrong.
  • EXECUTION_COMMAND is the imperative direction, server→device. A descriptive advertisement travelling the other way on the same channel mixes two meanings on one topic.
  • HARDWARE_CONFIGURATION is already named and reserved for exactly this, and TEC-NATKIT-10 already asked for it: "we should have a way to enable those from the UI, or at least show that they are possible."

Three control kinds, and nothing else

  • button — a one-shot action. identify.
  • toggle — a boolean, in a group READ together and WRITTEN one at a time. The four BNO08x reports.
  • input — a typed value, using the existing FieldValueType vocabulary (Bool, Int16, Uint32, Uint64, Float32, Float64, String, Enum) rather than a parallel one. set_tx_power.

The read/write asymmetry is load-bearing. A group is read whole and written one field at a time, because the device starts from its current state and applies only the field it was sent. That is what makes two in-flight toggles safe and stops a write resetting its neighbours. It is already how set_reports behaves — confirmed on hardware 2026-08-26.

The registry is the extension point

The device advertises control ids and their wiring. The human-facing descriptor — label, description, unit, range — is resolved through a registry, exactly as DataSchemaDescriptorRegistry already resolves schema field descriptors:

class DeviceControlDescriptorRegistry {
public:
  void registerDescriptor(const std::shared_ptr<const DeviceControlDescriptor> &);
  Optional<std::shared_ptr<const DeviceControlDescriptor>> findByControlId(
      const std::string &controlId) const;
  static DeviceControlDescriptorRegistry &getDefault();
};

A third party ships a library and calls:

MyDeviceControlsDescriptor::registerWithRegistry(
    DeviceControlDescriptorRegistry::getDefault());

No natKit source is modified to add a device. That is the requirement this plan exists to satisfy, and the pattern is already proven in-tree by DataSchemaDescriptorRegistry, Registry::registerDecoder and MetaRecord::registerMetaRecordType.

An unknown control id must still render

If a board advertises foo.bar and no library has registered a descriptor for it, the UI shows a button labelled foo.bar — not nothing.

The alternative is a control that vanishes silently, which is indistinguishable from a device that does not have it, and which turns "you forgot to load the library" into a hardware-looking bug. Same instinct as nodes_present_valid: make the unknown case representable rather than identical to a known one.

The server enforces the allowlist

The backend caches the latest advertisement per device and refuses a send_device_command whose command is not in that device's advertised set. The advertisement drives both what the UI offers and what the server will send — one source of truth, not two.

Migration, and it is not optional. Three leaves, the primary and the gateway will not advertise until they are reflashed. Strict enforcement from day one silently removes the calibration node's buttons and every other existing control. Proposal: the UI fails closed (shows only what is advertised), while the backend validates only where an advertisement exists and counts-but-allows otherwise. Flip to strict once the fleet is flashed, and make the counter the evidence that it is safe to flip.

Wire budget

ESP-NOW v2 on these chips refuses anything over 1470 bytes; the largest payload in use today is a 1016-byte IMU frame, and the existing command reply field is only 224 bytes — so an advertisement needs its own packet type rather than riding the command channel.

Ids, kinds, types and command wiring for identify + four toggles + tx_power land around 300–400 bytes. Carrying the prose labels as well would put it at 600–900 and growing with every added control. Keeping labels in the registry is what buys the headroom — and it is also what lets a third party translate or re-word a control without reflashing anything.

Relationship to TEC-NATKIT-101

Today the firmware does not link libnatkit-core, so a control id list on the device and a descriptor table on the server are two artefacts kept in step by hand — a third such boundary, alongside the frame layout and the status structs.

Once #469 lands and the library is on the ESP32, the id list and the descriptors become one shared declaration, and this design converges on "the device is the single source of truth" with nothing to undo. Whether the label strings ship to the board is then a LIBNATKIT_ESP_BUILD decision, not an architectural one.

So this plan is not a compromise awaiting reversal. It is the same design with the shared declaration temporarily living in two places.

Slices

  • 1 — the descriptor and its registry. DeviceControlDescriptor, DeviceControlDescriptorRegistry, natKit's own descriptors registered by default. Pure libnatkit-core, unit-tested, ships nothing user-visible.
  • 2 — the schema. NatKitDeviceControlsV1 encode/decode plus its golden fixture, registered with the Registry so a log viewer resolves it by topic.
  • 3 — firmware advertises. A Configuration publish on boot, on change, and at a low periodic rate. ⚠️ Retained on MQTT, or a late subscriber sees nothing until something changes.
  • 4 — backend caches and enforces. Per-device advertisement, the count-but-allow migration path, and the cache exposed over the StreamViewer WebSocket.
  • 5 — the UI discovers. Delete SOURCE_BUTTON_CONTROLS and SOURCE_TOGGLE_GROUPS; render from the advertisement. This slice is where the hardcoding actually dies, and it should not land before slice 4 or the UI has nothing to read.

Decided (2026-08-26)

Each leaf publishes its own advertisement

Not the gateway on their behalf. A Configuration topic per device, through the uplink. The airtime is small next to a 100 Hz data stream, and it means the advertisement comes from the thing it describes.

Configuration carries typed records with a registered type id

Mirroring MetaRecord::registerMetaRecordType(recordTypeId, decoder). NatKitDeviceControlsV1 becomes one record type on the channel rather than the channel's only meaning, so a third party can define its own configuration record — not merely its own control descriptors. This is the difference between an extensible channel and an extensible label table, and it belongs in slice 2.

An advertisement always originates from flashable hardware

There is no software-only advertiser. Either the device itself can be flashed (ESP32, Arduino), or a bridge microcontroller acts on behalf of a non-flashable end device. Nothing on the server invents an advertisement for hardware that cannot speak for itself.

That keeps the registry honest: the server resolves ids to labels and never authors the id list, so "what exists" and "what it is called" cannot drift into the same place.

⚠️ "Acting on behalf of" is the exact shape of TEC-NATKIT-81

The bridge-microcontroller case reintroduces the failure this rig spent a morning on. On 2026-08-26 the ESP-NOW hub was found republishing status frames for four leaves it had not heard for 16.8 hours — every counter frozen, every frame arriving fresh, nodes_known still reporting a complete rig. A proxy that keeps speaking for something it has lost is indistinguishable, from the outside, from a healthy system.

A bridge advertising for an end device it can no longer reach would do the same thing: publish a capability set forever for hardware that is unplugged, and the UI would offer controls for a device that is gone. Worse than the status case, because the operator can press these.

So an advertisement made on behalf of another device must carry liveness. Two acceptable shapes:

  • the bridge stops advertising when it loses the end device (clean, and the topic simply goes stale — but MQTT retain will keep serving the last one, so the retained message must be cleared); or
  • the advertisement carries when the advertiser last heard the device, the way last_seen_us does for a leaf, so staleness is visible rather than inferred.

⚠️ The second is preferred for the same reason TEC-NATKIT-81 landed on nodes_present beside nodes_known rather than aging the roster: silence cannot be told from "never existed", and a device that was here is worth saying so about. A device advertising for itself has no such problem — its advertisement stops when it does.

Supersedes the hardcoded catalogue added in TEC-NATKIT-40/-99 (natKit 9b6858b), which this plan exists to delete.
