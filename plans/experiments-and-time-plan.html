Experiments & the Concept of Time

Add an experiment node (parameters → markers output) to the stream-graph editor, and give the platform a first-class model of time so one graph can record an experiment, process it live, classify live, or reprocess recorded history — all through a shared timeline/transport surface.

Decisions resolved — ready to sequence Phase 1 (experiment node)

The mental model: a “DVR / DAW for sensor data”

Every natKit stream is Kafka-backed, so it already has a full recorded history and can be read from any point. The unifying idea: a graph never runs at “now” specifically — it runs at a time context, which is either the live head or a point/range in recorded history. The same processing graph then serves every scenario the platform needs:

  • Record an experiment — drop an experiment node in a live graph; the data (already durable in Kafka) plus the emitted markers become a labeled experiment on the timeline.
  • Process live — the graph tails the head (today's behavior).
  • Classify live — same graph, with a classify node loading a trained model.
  • Reprocess history — point the same graph at a past experiment/range and run the chain over it; tweak the chain, re-run, compare processing methods.

Borrowed metaphors that users already understand: a DVR (“you're watching live, but you can rewind”), a DAW / video timeline (tracks = streams, clips = experiments, playhead + transport), and Grafana (a time-range picker with a live toggle). The plan adopts the pieces of each that fit.

What already exists (build on it)

  • Cue engine + protocol: SessionProtocol (classes / rest_class / reps / hold / rest / lead-in / tail / seed) and the seeded scheduler buildCueScheduleForProtocol in StreamViewer/experiment.ts are already generic and sensor-agnostic.
  • Markers & metadata: MarkerEventV1 (session_id / marker_type / event / label / emitted_at_us / attributes) + SessionMetadataRecord, written through publish_session_bundle → handlePublishSessionBundle to deterministic Marker/<session_id>/MarkerEventV1 and Meta/<session_id> topics.
  • The session node already resolves N upstream stream ids and runs a client-side cue timeline that emits the marker bundle (it records nothing itself — the raw data is already in Kafka).
  • Run discovery: reconstruct_session.discover_runs turns markers into selectable runs (DiscoveredRun with start_us/end_us), surfaced by the ML control plane's list_recorded_runs and consumed by MlPipeline. This is the seed of an “experiment library.”
  • Historical read capability exists at the transport layer: BrokerManager::createMessenger(topicInfo, startOffset) supports OFFSET_BEGINNING / concrete offsets; reconstruct_session.drain_emg_frames_for_window is a working “read history, window by device_ts_us” primitive; replay.py paces a recording back onto Kafka.

The gaps this plan must close

  • The session node has no output ports (backend validation forbids them) — markers + passthrough outputs are net-new.
  • Markers are write-only: nothing in the frontend renders them. No marker viewer/overlay exists.
  • startOffset is never plumbed through the graph runtime, the WebSocket subscribe action, the C ABI, or the frontend — every consumer is hard-wired to live tail.
  • No time introspection: nothing calls offsets_for_times / watermark queries, so there is no way to know a stream's earliest available time or map timestamp → offset for scrubbing.
  • No timeline / playhead / transport UI. ChannelFrameViewer only windows already-received live samples; it cannot seek Kafka history.
  • Transform/combine workers have no time alignment (combine is FIFO). Correct multi-stream replay from an offset needs real timestamp alignment.

Part A — The experiment node (markers output)

Generalize the existing session node into an experiment node with a single markers output. (Decided: no passthrough port — a symbolic “looks-like-it-comes-from-the-experiment but reads the input” output isn't worth the complexity; if a user wants the data downstream they just draw the link from the source themselves.)

  • Inputs: one (or more) data streams to annotate/record (variadic, as today).
  • Output markers: the MarkerEventV1 stream for this experiment's session_id (the existing marker topic). Downstream marker-aware nodes subscribe to it — a marker viewer, or a train node that uses markers as the label source.
  • Config: the existing SessionProtocol (classes/timing) + experiment metadata (name, participant, notes) + a Record control. Reuse the cue engine and the publish_session_bundle pipeline verbatim.
  • Backend: relax the node validation (which currently forbids any output on a session node) to permit the single declared markers port; resolve it → stableStreamId of Marker/<session_id>; add the catalog entry. Recording stays client-driven initially (reuse today's recorder), with a follow-up to move emission server-side and tie markers to real frame timestamps (see Part E).
  • Frontend: rename/extend the session inspector to the experiment inspector; wire the markers output port and the record affordance.

Part B — Markers as a first-class stream

Markers are currently invisible; make them observable and consumable.

  • Marker renderer: subscribe to a MarkerEventV1 stream and render cue/session events as (a) ticks/regions on the timeline (Part D) and (b) vertical annotation lines overlaid on data viewers at the marker timestamps — so a cue is visible in context while scrubbing.
  • Descriptor-driven: extend the viewer registry so a stream whose schema is MarkerEventV1 picks the marker renderer, consistent with the existing sensor-agnostic viewer selection.
  • Markers as input to processing: a marker stream can feed a train node (explicit labeling in the graph instead of the implicit reconstruct_session discovery) and, later, a “gate/segment” node that slices data by cue windows.

Part C — The time model (backend foundation)

Give a graph run a time context and make the runtime able to honor it.

TimeContext = {
  mode: "live" | "replay",
  start:  timestamp | offset | experiment_id,   // where the playhead begins (replay)
  end?:   timestamp,                            // optional bound (an experiment window)
  speed?: number | "max",                       // paced (1x, 2x, 0.5x) or as-fast-as-possible
}
  • Plumb startOffset (already at createMessenger) through the subscribe action, the stream-graph start path, and the frontend. This is the enabling primitive: “start this consumer at offset X / timestamp T” instead of always live-tail.
  • Time introspection: add a backend query for a stream's earliest/latest offset and offsets_for_times (rdkafka supports it) — so the UI knows the available history extent and can map a scrubbed timestamp → offset.
  • Paced replay: a replay run delivers frames at a controlled rate (real-time or N×), or as-fast-as-possible for batch reprocessing (with a progress indicator). Model on replay.py's wall-clock pacing, but as an in-runtime consumer mode rather than a re-injection CLI.
  • Canonical clock: pick one time axis for scrubbing/alignment — device_ts_us for data frames, emitted_at_us for markers — with a defined mapping between them.

A Timestamped base for every message (decided)

Rather than special-case each schema's timestamp field, introduce a small virtual interface in libnatkit-core — e.g. Timestamped with a getTimestampUs() — that every message type implements (data frames return device_ts_us, markers return emitted_at_us, meta records their created/updated time, etc.). Every message on the platform should carry a timestamp, so the time model, scrubbing, alignment, and combine can all operate on one uniform accessor instead of per-schema knowledge. This is the clean foundation for Parts D–E and is worth doing early (it also tightens the descriptor *_ts_us_path conventions that already exist in the node catalog).

Part D — Timeline & transport UX

The user-facing surface for time. Proposed as an always-available strip along the bottom of the canvas (collapsible), plus transport controls in the toolbar.

  • Timeline strip: a horizontal time axis spanning the source stream's available history (earliest → the live edge). Recorded experiments appear as labeled regions; their cues appear as marker ticks. A playhead marks the current position.
  • Live edge: a glowing right edge with a “● LIVE” button. When the playhead is scrubbed back, the button snaps it to the head (the DVR affordance).
  • Transport: play / pause / step, jump-to-live, scrub, speed (0.5×–4× + “max” for batch), and an optional loop-region for iterating on a segment.
  • Time-range picker (Grafana-style): quick presets — “Live (last 30 s)”, “Experiment X”, “Absolute range”.
  • Recording affordance: while an experiment node records live, a “REC” indicator and the region growing at the live edge.

Alternatives considered (open for discussion): (i) a Grafana-style range picker only, no scrub playhead — simplest, but weak for stepping through cues; (ii) a full multi-track DAW timeline (one lane per stream) — richest, but heavy to build and possibly overkill until multi-stream is common; (iii) the hybrid above — one timeline for the graph's primary time axis, with per-stream detail on demand. The plan recommends (iii).

Part E — Correct multi-stream replay (the hard dependency)

Live processing tolerates loose synchronization; historical replay does not. Two correctness requirements gate trustworthy reprocessing:

  • Aligned start: when replaying from time T, every input consumer must start at the offset corresponding to T (via offsets_for_times), not offset 0 — otherwise streams start at different wall-clock points.
  • Time-aligned combine: the combine worker is FIFO today (“mismatched cadences will silently misalign”). Replay needs combine (and any multi-input node) to align by device_ts_us/seq_no, not arrival order.
  • Server-side marker emission (Part A follow-up) should stamp markers against real frame timestamps so cues line up with data on replay, independent of the browser wall clock.

Single-stream replay works without this; multi-stream replay is only correct once alignment lands. Sequence the phases so single-stream replay ships first and multi-stream follows.

Part F — Experiment library & the end-to-end workflows

  • Experiment library: generalize list_recorded_runs into a browsable list of recorded experiments (session_id + metadata + marker timeline + participating streams). Selecting one sets the graph's time context to that experiment's window and paints its region/markers on the timeline.
  • Record → explore loop: record an experiment live; it appears in the library and on the timeline; switch the graph to replay, scrub to it, and run alternative processing chains over the same data to compare methods.
  • Train / classify tie-in: experiment markers become the label source for a train node; a trained model's model_path wires into an lda_classify node to classify live (or over replayed history to evaluate).

Suggested phasing

  • Phase 1 — Experiment node. Session node → experiment node with data (passthrough) + markers outputs; reuse cue engine + publish pipeline. Ships value immediately, no time model needed.
  • Phase 2 — Marker rendering. Marker viewer + data-chart overlay; markers become visible. Independent of the time model.
  • Phase 3 — Time foundation. Introduce the Timestamped base (uniform getTimestampUs()); plumb startOffset through subscribe + runtime + frontend; add time introspection (earliest/latest, offsets-for-times). Enable “start a graph at a historical offset/timestamp” (single stream).
  • Phase 4 — Timeline & transport UI. The strip, playhead, LIVE edge, experiment regions, transport, range picker — wired to the per-graph time context (hybrid: one primary axis + per-stream detail on demand).
  • Phase 5 — Backend re-run replay + multi-stream alignment. Backend re-runs the chain from an offset with paced delivery (speed); aligned consumer starts and timestamp-aligned combine (Part E). Makes single- then multi-stream reprocessing correct.
  • Phase 6 — Experiment library + workflows. Browser (reusing run discovery), select-to-time-context, compare-processing loop, train/classify integration.
  • Phase 7 (later) — Safe result caching. Where processing is deterministic/pure, cache processed outputs and replay from cache to avoid re-running the whole chain; the Phase-5 re-run stays the source of truth and the fallback.

Decisions (resolved)

  • 1. Passthrough — dropped. Experiment node exposes only the markers output; users draw a data link from the source themselves if they want it downstream. Not worth the symbolic-rewire complexity.
  • 2. Time-context scope — per-graph. Each graph carries its own time context; the timeline widget reflects the selected graph.
  • 3. Live + historical mixing — deferred. Out of scope for v1; expected to need real experimentation to find a sane model. A run is entirely live or entirely replay for now.
  • 4. Canonical clock — via a Timestamped base. Every message implements getTimestampUs() (data → device_ts_us, markers → emitted_at_us). One uniform accessor for the whole time model. Built early (Part C).
  • 5. Replay engine — backend re-run first, cache later. Start by having the backend re-run the processing chain from a historical offset (correct and reuses the runtime, even if not the cheapest). Then incrementally add ways to safely cache processed results and replay from cache where the processing is deterministic/pure. Cache is an optimization layered on the re-run baseline, never the source of truth.
  • 6. natVR reuse. Reuse reconstruct_session.discover_runs for the experiment library (run discovery); build seek/replay into the C++ runtime so the live and historical paths share one engine.

Risks & non-goals

  • Risk: presenting time is where products like this usually get confusing. Mitigate by shipping the experiment node + markers (Phases 1–2) before any time UI, and by leaning on the familiar DVR/range-picker idioms rather than a bespoke metaphor.
  • Risk: incorrect multi-stream replay silently produces misaligned results that look plausible. Gate multi-stream replay on Part E; label single-stream vs aligned-multi-stream clearly in the UI.
  • Risk: Kafka retention bounds “all of history.” The timeline's left edge is the earliest retained offset, not the beginning of time; surface retention honestly.
  • Non-goal: a second storage/replay system. Reuse Kafka history + the existing marker/metadata topics; do not build a parallel recording store.
