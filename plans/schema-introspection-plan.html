EXG Pill EMG Core Schema and Descriptor Plan

Promote the EXG Pill EMG payload into libnatkit-core as ExgPillEmgDataSchemaV1, register it in the normal decode path, and build the first DataSchemaDescriptor proof on top of that core-owned schema so frontend stream wiring and future visual pipelines can depend on one canonical contract.

Scope: libnatkit-core, bridge and backend decode flow, then descriptor exposure, frontend adoption, and visual-pipeline follow-on.

Decision

  • Create a new canonical core schema class named ExgPillEmgDataSchemaV1.
  • Treat the old natVR-local EMG contract name as legacy and migrate everything onto ExgPillEmgDataSchemaV1.
  • Register the new schema in the default core Registry so normal topic decode works.
  • Move backend EMG handling from raw JSON parsing to typed schema decode.
  • Add a new abstract DataSchemaDescriptor base class in libnatkit-core that inherits from MetaRecord.
  • Use ExgPillEmgDataSchemaV1Descriptor as the first concrete descriptor proof target.
  • Keep descriptor instances stateless with respect to per-message values; runtime access methods must read from a passed decoded Schema record.
  • Use stable machine field ids for lookup paths and separate human labels for display text.
  • Expose typed path access with failure-aware APIs such as Optional<T>, not unchecked casts.
  • Because the platform is still under active development, prefer a clean breaking cutover over preserving backward compatibility; any temporary legacy aliasing should be optional and short-lived.

Why This Exists

What exists now

  • Concrete schemas such as NatImuDataSchema already own serialization and decode logic in core.
  • The backend currently hand-translates some schemas into frontend JSON views.
  • MetaRecord already exists as a typed metadata transport on META streams.
  • The EXG Pill EMG path now uses the canonical Kafka topic schema name ExgPillEmgDataSchemaV1.

What is missing

  • A core-owned EXG Pill EMG schema in libnatkit-core.
  • A schema-owned semantic field model for records such as IMU, Muse, and derived streams.
  • A generic path lookup mechanism like accelerometer.y across arbitrary schemas.
  • A typed contract that the frontend can use for generic inspectors and graph wiring.

Constraint

  • The semantics must live in core, not only in backend presentation code or TypeScript.
  • The wire formats should remain existing schema serializations, not be replaced by ad hoc introspection JSON.
  • Renaming the EMG schema changes Kafka topic suffixes, and that is acceptable at the current stage of platform development.
  • The visual-programming direction needs a real stream contract, not only pretty display JSON.

Migration Direction

The first proof target is the EXG Pill EMG payload. The first step is to promote that payload into libnatkit-core under the canonical name ExgPillEmgDataSchemaV1. 

firmware / replay / producers
  -> JSON payload
  -> bridge maps to Data-<stream-id>-Json-ExgPillEmgDataSchemaV1
  -> broker manager uses core Registry
  -> backend receives typed ExgPillEmgDataSchemaV1
  -> descriptor layer reads typed fields by path
  -> frontend / pipeline tools consume one canonical contract

The platform is still being shaped, so this migration does not need a heavy backward- compatibility posture. The preferred path is a direct cutover to the canonical schema, with short-lived aliases only where they materially reduce implementation effort.

Descriptor Ownership

The key design choice is that the descriptor itself should own the semantic field model and the runtime access methods, but it should not own per-record mutable values.

In other words, the descriptor is a typed metadata object that knows how to describe a data schema and how to read values out of a decoded record instance of that schema.

Layer Purpose Initial choice
DataSchemaDescriptor Abstract root for schema description and runtime access Derives from MetaRecord and defines the stable descriptor contract
FooDataSchemaDescriptor Concrete schema-specific implementation Knows field layout and how to read fields from FooDataSchema
Schema record instance Holds one decoded message payload Passed into descriptor accessors so values stay out of descriptor state

Proposed Core Model

Type Role Notes
FieldValueType Leaf/object/array kind enum Start with bool, integer widths, float widths, enum, object, array
SchemaFieldDescriptor One named field Includes machine id, label, description, unit, optional flag, enum definition, and child fields
DataSchemaDescriptor Abstract descriptor root Defines target schema identity, descriptor version, root fields, and typed runtime accessors
SchemaPath Parsed field path Canonical lookup tokenization for paths such as accelerometer.y
FieldValueRef Typed reference to one runtime field value Used by getters to avoid copying and to preserve type checks
DataSchemaDescriptorRegistry Lookup from schema name or id to descriptor Can reuse existing MetaRecord registration ideas while staying focused on descriptors 
class DataSchemaDescriptor : public MetaRecord {
public:
  virtual std::string getTargetSchemaName() const = 0;
  virtual uint16_t getDescriptorVersion() const = 0;
  virtual const SchemaFieldDescriptor& getRootField() const = 0;

  virtual Optional<FieldValueRef> tryGetFieldValue(
      const Schema& record,
      const std::string& path) const = 0;
};

Naming and Path Rules

  • Use machine ids for lookup, not display labels. Example: data_present instead of data-present.
  • Prefer simple path-safe ids such as accelerometer.x, accelerometer.accuracy, and rotation.real.
  • Allow frontend labels to be richer, for example “X Axis” or “Acceleration on X axis”.
  • Treat field ids as stable API once published; changing them is a compatibility break for pipelines.

Runtime usage

ExgPillEmgDataSchemaV1 record = ...;
ExgPillEmgDataSchemaV1Descriptor descriptor{};

auto sampleRate = descriptor.getUint32(record, "sample_rate_hz");
auto firstLabel = descriptor.getString(record, "channels.0.label");
auto firstSample = descriptor.getInt16(record, "channels.0.samples.0");

Accessor Direction

The runtime accessor API should live on the descriptor and operate on a passed record. A getter should fail cleanly when the path is unknown, the record is the wrong schema type, or the requested type does not match. 

class ExgPillEmgDataSchemaV1Descriptor : public DataSchemaDescriptor {
public:
  Optional<std::string> getString(const Schema& record, const std::string& path) const;
  Optional<int16_t> getInt16(const Schema& record, const std::string& path) const;
  Optional<uint64_t> getUint64(const Schema& record, const std::string& path) const;
  Optional<uint32_t> getUint32(const Schema& record, const std::string& path) const;
};

auto value = descriptor.getInt16(dataRecord, "channels.0.samples.0");
  • Use Optional<T> so missing fields and mismatched types are explicit.
  • Reject wrong-schema records rather than silently interpreting them.
  • Keep path parsing in one shared helper so frontend, backend, and runtime use the same canonical keys.
  • Add array index support in path parsing because EMG channel/sample access needs it immediately.
  • Add a lower-level tryGetFieldValue for generic tooling that needs dynamic typing.

Open Questions

  • Should descriptor objects be static singletons per schema class or rebuilt on request. Static descriptor storage is preferred unless mutation is required.
  • Should DataSchemaDescriptor instances be carried over the wire as ordinary MetaRecord payloads in the first slice, or should first adoption use only local registration and backend exposure. Local registration first is preferred.
  • How should fixed-size numeric groups be modeled: semantic objects like accelerometer.x or raw arrays with semantic aliases. The semantic-object model is preferred for pipeline usability.
  • How should EMG channel identity be modeled when labels vary by device. The initial proof should support indexed access such as channels.0.samples.0 and may later add sanitized label aliases where safe.
  • Do we want descriptor-layer versioning to remain independent of payload schema_version if additional EMG wire-format revisions appear later.
  • Do we need explicit schema-version negotiation on the descriptor layer beyond the existing schema class name. A version field should be added early even if initial implementations use 1.
  • Should field availability gates such as data_present live as sibling fields or as descriptor metadata. Start as explicit sibling fields because they are actual runtime data.
  • How far should the first frontend slice go. The recommendation is generic inspection and field selection first, not full graph editing yet.

What Not To Do

  • Do not make this a frontend-only JSON convention.
  • Do not add descriptor work on top of the current natVR-local ExgPillEmgDataSchemaV1 contract and call that finished.
  • Do not make DataSchemaDescriptor hold mutable per-record values internally.
  • Do not keep the backend raw-JSON EMG path once the core schema exists; that would preserve two parallel decode systems.
  • Do not force all schemas to serialize themselves as descriptor-plus-value objects on the DATA wire format.
  • Do not treat descriptor publication on META streams as a requirement for local descriptor use.
  • Do not let optional compatibility shims become the new long-term architecture.
  • Do not freeze path keys around punctuation-heavy names such as x-axis if we already know they will become long-term API surface.
  • Do not jump straight to a free-form visual programming canvas before the core field-contract model is stable.
This plan intentionally combines the EMG core-schema migration with the descriptor work because the first descriptor proof target should be built on a real core-owned natKit schema, not on the current natVR-local JSON contract.
