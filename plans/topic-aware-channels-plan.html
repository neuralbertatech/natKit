Topic-Aware Channels

Reframe a graph "channel" from a single stream into a bundle of topics (data + markers, and later meta). Make combine a topic-aware merger, show what a link carries with a per-edge topic badge, and let a viewer sprout a dynamic markers input when the incoming channel has markers — so markers and data flow, merge, and render together as first-class citizens.

Design captured from discussion — ready to sequence

The mental model: a channel is a set of topics

The transport already models this: every stream is a set of topics keyed by StreamType — DATA, META, MARKER (see BasicTopicInformation.type / RawStream::getTopicsByType). But the graph runtime and editor collapse a node's output to a single output_stream_id (one topic), so markers and data can never travel down the same link. This plan lifts that: a channel (a link between nodes) carries a list of topics, at most one per type. A link can therefore be:

  • "data" — a single DATA topic (today's default).
  • "markers" — a single MARKER topic (an experiment's output).
  • "stream" — both a DATA and a MARKER topic bundled together.

An input port detects what it's fed and relabels itself accordingly (data / markers / stream). Combine, links, and viewers all become topic-aware off this one model.

What exists (build on it)

  • Per-type topics: StreamType::{DATA,MARKER,META}; BasicTopicInformation{type,id,schemaName}; RawStream::getTopicsByType; createTopicInfo(type, key, id, schema). Topic id = stableStreamId of the full topic string (type is part of the string, so Data/<k> and Marker/<k> have different ids even for the same key k).
  • Marker plumbing (done): experiment nodes emit MarkerEventV1 to Marker/<experiment_id>; the backend forwards markers as marker WS messages (formatMarkerEventAsJson); subscribe binds MARKER/META topics via findMarkerOrMetaTopicForStreamId and reads them from OFFSET_BEGINNING; the frontend has a marker renderer + MarkerViewer.
  • Timestamped base (done): Schema::getTimestampUs() (data → device_ts_us, markers → emitted_at_us) — the shared axis for time-aligned merges + overlays.
  • Combine worker: CombineWorker concatenates NormalizedNumericChannelFrames into one NatSignalFrameDataSchemaV1 feature vector, now timestamp-aligned by device_ts_us (Phase 5). Validation requires ≥2 numeric-descriptor inputs.
  • Editor: nodes carry one output_stream_id in runtime status; edges are drawn from a source port to a target port; the viewer picks a renderer via chooseViewerRenderer.

The core gap this plan closes

  • A node output resolves to one output_stream_id. There is no way to represent "this link carries a data topic and a marker topic."
  • combine is numeric-only and rejects markers (a category error today).
  • A link shows nothing about what it carries.
  • A viewer has one input and can't show data with a marker overlay.

Part A — Channel model: a link carries a topic set

Generalize a node's output from one id to a channel: an ordered set of topics, at most one per StreamType. This is the enabling change everything else rides on. 

Channel = {
  topics: [
    { type: "DATA",   stream_id, schema_name },
    { type: "MARKER", stream_id, schema_name },
    // (META later)
  ]
}
// "kind" is derived: data-only | markers-only | stream (both)
  • Runtime status: add output_topics: [{id,type,schema}] to a node's status (keep output_stream_id = the DATA topic id, or the sole topic, for backward compatibility). Sources report their real topic set; transform reports its DATA output; experiment reports its MARKER output; combine reports the merged set.
  • Edge resolution: an edge inherits the source port's channel (its topic set). Downstream input resolution keys off the set, not a single id.
  • Subscribe: subscribing to a channel binds a messenger per topic in the set (the DATA-topic path stays live-tail; MARKER/META read from the beginning — already implemented per topic). The frontend routes each topic's records to the right consumer (data → chart buffers, markers → marker buffers).

Backward compatible: a plain data stream is a channel of one DATA topic; existing single-id graphs keep working (the set has one element).

Part B — Combine as a topic-aware merger

Each combine input detects its incoming channel kind and relabels itself (data / markers / stream). Combine's output is the per-type union of its inputs: same-type topics are merged together; the output channel carries one topic per type present across all inputs.

InputsOutput channelHow
data + dataone DATA topicnumeric feature-vector concat (today's behavior), timestamp-aligned
markers + markersone MARKER topicmerge/interleave marker events by emitted_at_us
data + markersDATA + MARKER (a "stream")pass data through to Data/<out>, markers to Marker/<out> — no cross-transform
stream + dataDATA + MARKERmerge the stream's data with the data; carry the stream's markers
stream + markersDATA + MARKERcarry the stream's data; merge the stream's markers with the markers
stream + streamDATA + MARKERmerge data topics together, merge marker topics together

Implementation: split CombineWorker into per-type mergers. The DATA merger is today's numeric concat. Add a MARKER merger (interleave MarkerEventV1 by emitted_at_us, republished to Marker/<output_identifier>). The combine node's output output_identifier becomes the shared key so Data/<out> and Marker/<out> bundle into one channel. Relax validation: combine accepts data and/or marker inputs; the old "numeric-only" gate becomes "at least one topic per input, merged by type."

  • Input relabeling: the frontend labels each connected combine input port data/markers/stream from the resolved upstream channel kind (live, from the edge's topic set).
  • Open: can a channel hold >1 topic of the same type (e.g. two distinct DATA topics carried side-by-side, not concatenated)? This plan says no — one-per-type, same-type inputs are merged. Revisit if a use case needs parallel same-type topics.

Part C — Link topic badge

Make it visible what a link carries. Render a small badge on each edge showing the topic count (e.g. a "2" chip mid-link). Clicking it opens a small dropdown listing the contained topics — type + schema + stream id (e.g. "DATA · NatSignalFrameDataSchemaV1", "MARKER · MarkerEventV1").

  • Positioned at the edge midpoint (the editor already computes edge endpoints from port anchors; the midpoint is cheap).
  • Reads the edge's resolved channel (Part A). For an unresolved/pre-run edge, show the statically-known count (e.g. an experiment output = 1 marker; a source = 1 data).
  • Non-blocking, click-to-toggle; closes on outside click / Escape.

Part D — Viewer dynamic markers input

A viewer stays single-input by default, but when the user connects a channel that contains markers, a dynamic (initially "fake") markers input appears. Clicking it enables the overlay; the incoming link then splits and connects to both the data input and the markers input, and the ChannelFrameViewer draws the markers as labeled vertical lines over the waveform (aligned by timestamp).

  • Detection: on connect, if the source channel's topic set includes a MARKER topic, reveal the phantom markers input on the viewer node.
  • Enable + split: clicking the phantom input promotes it to a real input and rewires the single incoming edge into two logical bindings (data → in, markers → markers) from the same source channel. Under the hood both read the same channel's respective topics — no second user-drawn edge required.
  • Overlay: ChannelFrameViewer gains a markers prop; marker emitted_at_us maps onto the rolling trace's time axis (for live, align by arrival/wall-clock; for replay, by device_ts_us). Cue = a colored vertical line with the class label; session start/end = a region boundary.
  • Fallback: a data-only channel never shows the phantom input; a markers-only channel renders the MarkerViewer as today.

Part E — General marker support (rides along)

  • The timeline strip already shows experiment markers; extend it to any channel that carries a MARKER topic.
  • A stream's own MARKER topic becomes browsable/inspectable (the transport already keys it per stream).
  • Markers as an explicit train-node label source (a "stream" or markers channel into a train node supplies labels).
  • Later: a dedicated gate/segment node that slices a data channel by cue windows (distinct from combine's merge; it filters/labels by marker windows).

Suggested phasing

  • Phase 1 — Channel model (Part A). Node status gains output_topics; edge/subscribe resolve a topic set; frontend routes per-topic. Backward compatible (one-topic channels behave as today). No visible feature yet — the foundation.
  • Phase 2 — Combine merger (Part B). Per-type mergers (data concat + marker interleave); relaxed validation; input relabeling data/markers/stream. Now data+markers combine into one "stream" channel.
  • Phase 3 — Link topic badge (Part C). Edge midpoint chip + dropdown of contained topics.
  • Phase 4 — Viewer markers overlay (Part D). Dynamic markers input + link split + ChannelFrameViewer vertical-line overlay.
  • Phase 5 — General marker support (Part E). Timeline per-channel, train label source, (later) gate/segment node.

Decisions (from discussion)

  • Channel = topic set. A link carries a list of topics, at most one per type (DATA/MARKER/META). Input ports relabel themselves data/markers/stream from what they're fed.
  • Combine = per-type union. Same-type topics merge (data concat, markers interleave); the output carries one topic per type present. data+markers → a bundled "stream" with no cross-transform.
  • Link badge. A clickable topic-count chip on each edge with a dropdown of contents.
  • Viewer phantom markers input. Appears only when the connected channel has markers; enabling it splits the one link into data + markers bindings and overlays markers on the waveform.

Risks & open questions

  • Same-type multiplicity: the plan forbids >1 topic of a type per channel (same-type inputs merge). If a real need for parallel same-type topics appears, the channel model must grow to a multiset — revisit before it calcifies.
  • Output-id sharing: bundling DATA + MARKER under one channel requires both topics to share a key (Data/<out> + Marker/<out>). Confirm the combine output_identifier can key both without colliding with an experiment's Marker/<experiment_id>.
  • Overlay alignment: the ChannelFrameViewer plots a rolling window; mapping absolute marker emitted_at_us onto it is exact for replay but approximate for live (wall-clock). Decide the live alignment reference.
  • Risk: the single-output_stream_id assumption is threaded through the runtime, status JSON, subscribe, and the editor. Part A is a broad, careful change; keep the one-topic path byte-identical so nothing regresses.
  • Non-goal: cross-type transforms in combine (e.g. deriving data from markers). Combine only unions + merges same-type topics.
