A WiFi rig: primary + serial + gateway

The rig today needs a board with an Ethernet port. This plan produces the two-chip WiFi alternative: one ESP32 is the ESP-NOW hub and timing master, a wire carries its framed stream to a second ESP32, and only that second chip associates with WiFi and talks to the broker. That is the architecture EPIC TEC-NATKIT-20 was designed around and it is already ~80% built — what this plan is really about is the 20% that was never wired up and the drift that accumulated in the gateway while the Ethernet primary got all the new work.

Status: planned, not started · plan written 2026-08-25

The one-sentence answer to "which serial protocol"

UART, three wires, 921600 baud 8N1, no flow control — and it is already implemented on both sides. See What to wire for the exact pins and Why UART and not SPI or I2C for the reasoning and the bandwidth arithmetic.

Why two chips and not one

The obvious cheap answer — leave the primary as the hub and just give it WiFi — was already built and already measured, as CONFIG_NATKIT_PRIMARY_WIFI_UPLINK (TEC-NATKIT-30 / #373). It does not work: one chip doing ESP-NOW plus an associated WiFi station lost ~85% of its ESP-NOW frames. They were acknowledged at the MAC layer and then dropped above it by a WiFi task busy servicing the association. There is a second, structural problem behind the throughput one: ESP-NOW needs every peer on one channel, and an associated station does not choose its channel — the AP does — so the leaves have to go hunting for whichever channel the AP moved the hub onto.

Ethernet solved it by getting the uplink off the radio entirely. Two chips solve it the same way: the hub's radio does nothing but ESP-NOW on a channel we pin, and the association lives on a different piece of silicon with a wire between them. This is the same fix, without requiring an Ethernet daughterboard.

⚠️ So the WiFi rig is one board MORE than the Ethernet rig, not one fewer. Ethernet is primary + N leaves. WiFi is primary + gateway + N leaves. The saving is the W5500 daughterboard and an Ethernet drop, not a board — worth saying out loud before anyone counts on it as the cheap option.

The real problem: the gateway has drifted, and it will drift silently

gateway.cpp has not been touched since 0fb6d57, before the Ethernet primary existed. Everything the rig has gained since — the device-health pill, the Logs page, the recording clock record, the indicator LED, the command relay — was built on the primary-publishes-directly path and none of it was carried across. Concretely:

  • The health panel would be blank behind a gateway. gateway.cpp receives kNodeStatus and kPrimaryStatus frames and uses them internally — the node's clock fit, the primary→wall offset — and then drops them. It never republishes them on Log-<id>-Binary-NatKitNodeStatusV1 / -NatKitPrimaryStatusV1, which is where DeviceHealthTracker (TEC-NATKIT-33) and the recording clock record (TEC-NATKIT-77) read from. A WiFi rig would stream data perfectly and report nothing at all about its own health — and TEC-NATKIT-77's whole point is that a recording seals that judgement, so it would seal "no clock data" on every run.
  • Every device button in Visual Programming would stop working. commandRelayStart() is called unconditionally on the primary, but it works by subscribing over MQTT. With no network on the primary there is no subscription, so the LED (TEC-NATKIT-83), calibration and the runtime report toggles (TEC-NATKIT-40) never reach a node. Nothing errors — the backend publishes and the command is simply unsubscribed, which is exactly the failure the README already warns about for the Arduino rollback path.
  • The frame got 23% bigger and nobody re-measured. #349's evidence is a 524-byte v1 frame. The fork now emits v2 at 644 bytes (13 floats, magnetometer). The bandwidth budget below is redone at v2.
  • Two silent drops in the gateway. if (length > sizeof(sFrame)) return; appears twice with no counter — the same defect shape as TEC-NATKIT-86, in a file nobody has re-read in two weeks.

None of that will announce itself. A WiFi rig would look correct in the Stream Viewer on day one and be missing its entire diagnostic surface, which is the half of this system that every hard bug so far has been found with. Phases 1 and 2 exist to close that before anyone runs a participant on it.

What to wire

The bench pair is a classic ESP32 as the primary (ESP-NOW hub) and a C3 as the gateway (WiFi + MQTT) — see Which chip gets which role for why round that way. The two boards do not use the same pin numbers, because CONFIG_NATKIT_UPLINK_TX_GPIO / _RX_GPIO are per-target defaults and each board gets its own generated sdkconfig. So the crossover is asymmetric:

FromToCarries
ESP32 PRIMARY GPIO 26 (UART1 TX)C3 GATEWAY GPIO 6 (UART1 RX)the data path — every frame from every leaf, plus status
C3 GATEWAY GPIO 5 (UART1 TX)ESP32 PRIMARY GPIO 25 (UART1 RX)the command path (Phase 2 — wire it now, it costs one jumper)
GNDGNDmandatory — the two UARTs need a shared reference

The ESP32 primary is unchanged from the committed defaults (TX 26, RX 25) — the pins the Kconfig help already vouches for. Only the C3 side is new, and it needs the defaults added in Phase 0b: default 5 if IDF_TARGET_ESP32C3 and default 6 if IDF_TARGET_ESP32C3.

Why those two pins on the C3, and not the others

The C3 has GPIO 0–21 and most of them are spoken for:

PinsWhy they are out
11 – 17SPI flash (11 is VDD_SPI). Unusable.
18, 19Native USB Serial/JTAG (D− / D+).
20, 21UART0 — the console. sdkconfig.defaults.esp32c3 deliberately leaves the console on UART0 rather than the native USB.
2, 8, 9Strapping pins, sampled at reset. 9 is BOOT. A UART line idles high and a driven pin at reset is how a board stops booting.
4The status LED. board_config.hpp pins the NeoPixel to GPIO_NUM_4 and statusLedRestore() runs in app_main before the role dispatch, so it is live on every role and every target.
0, 1Usable, but they are XTAL_32K_P/N if a 32.768 kHz crystal is fitted. Fine on most devkits; second choice.
3, 5, 6, 7, 10Free. 5/6 chosen as an adjacent pair. 10 and 3 are the alternates.

⚠️ 4, 5, 6, 7 are also the JTAG pins (MTMS/MTDI/MTCK/MTDO). Using 5/6 forfeits hardware JTAG — which costs nothing here, because the C3 debugs over its built-in USB Serial/JTAG on 18/19 instead. If you ever want an external probe, move the uplink to 10 (TX) / 3 (RX).

⚠️ It is a CROSSOVER. TX goes to RX. Wiring TX→TX puts two push-pull outputs on one net; they will fight whenever they disagree. Nothing catches fire at 3.3 V but nothing works either, and the symptom (garbage the CRC silently discards) looks identical to a baud mismatch.

⚠️ Do NOT connect 3V3 between the boards if both are USB-powered. GND only. Two USB supplies tied together is a ground loop at best and back-feeding a regulator at worst. To run from one supply, power one board from the other's 3V3/5V and leave that board's USB unplugged.
✅ FIXED 2026-08-25 (TEC-NATKIT-87 / #454) — a latent collision on the ESP32-S3, found while picking the C3 pins. CONFIG_NATKIT_UPLINK_TX_GPIO defaulted to 4 on the S3, and kStatusLedGpio is GPIO_NUM_4 for every target.

⚠️ Note where the LED half lives: status_led.* and the kStatusLedGpio block in board_config.hpp are on the unmerged zach/84-set-tx-power branch, not on trunk. So this was a thing to fix before that merge rather than a bug to hunt afterwards. It also never fired at runtime, because uplinkStart() skips uart_set_pin entirely when the uplink publishes over the network (if (!kOnConsole && !kWifiUplink)) and the S3 defaults to the Ethernet uplink — so it was armed to appear the first time somebody turned Ethernet off to use the serial uplink, which is exactly what this plan asks for.

The S3 uplink is now TX 9 / RX 10. ⚠️ Not 5/6, which was the obvious adjacent pair and is wrong: kBnoSck is GPIO_NUM_5 for that target, so 5 would have relocated a latent collision rather than removed one. 9/10 is what remains after subtracting the LED, every BNO08x pin, the native USB Serial/JTAG, flash and PSRAM, the W5500, the H2 co-processor, JTAG, UART0 and the strapping pins.

⚠️ The S3 pair is reasoned, not measured — that board runs the Ethernet uplink and never calls uart_set_pin at all, so nothing on this bench exercises it. Check it against a schematic before wiring an S3 primary to a gateway. The C3 and classic-ESP32 pins in the table above are the ones this rig actually uses.

Optional, later: hardware flow control

Two more wires (RTS↔CTS, crossed) would let the gateway back-pressure the primary instead of the primary dropping its oldest frame. Do not wire this yet. Drop-oldest is a deliberate decision, not an oversight — for a sensor stream the freshest frame is the valuable one, and both sequence numbers make the gap detectable downstream, whereas back-pressure propagates all the way into an ESP-NOW receive callback and starts costing other nodes' packets. Revisit only if Phase 3 measures the link saturating.

Why UART, and not SPI or I2C

The bandwidth budget, at v2 frames

A data frame is 18 (uplink header) + 644 (v2: 24-byte envelope + 10 × 62-byte samples) + 4 (CRC) = 666 bytes, at 10 frames/s per leaf (100 samples/s ÷ 10 samples per frame). Node status adds 214 B/s per leaf and the primary's own status 190 B/s, both at 1 Hz.

LeavesOffered load115200 (11.5 KB/s)921600 (92.2 KB/s)2 Mbaud (200 KB/s)
17.1 KB/s61% — marginal8%4%
427.7 KB/s2.4× over30%14%
8 (kMaxTrackedNodes)55.2 KB/s4.8× over60%28%

921600 is the right default — it is what both sides already configure, and it carries the full 8-node registry with 40% headroom. 115200 is a trap: it fits one leaf and looks fine, then silently drops most of the stream the moment a second leaf joins. That is precisely how natVR stalled its pipeline (~19 KB/s of frames into a 115200 console), which is why the Kconfig help text does the arithmetic.

The alternatives, and why not

  • SPI — faster (tens of MHz), but throughput is not the constraint: we need 55 KB/s and UART already gives 92. In exchange it costs 4–6 wires, a master/slave decision, an ESP32 slave driver that is transaction-oriented (so the master has to poll or you add a handshake GPIO), and it still needs the same framing — magic, length, CRC — because either end can reset mid-transaction. It is more wires and more code for a bottleneck we do not have.
  • I2C — 400 kHz fast mode is ~40 KB/s before per-byte ACK overhead, so it is under the 8-node load and barely over the 4-node one. It is also half-duplex, master-driven (the gateway would have to poll the primary for data it does not know is there), and clock-stretching-sensitive on ESP32. No.
  • Sharing UART0 / the USB console — supported today (CONFIG_NATKIT_UPLINK_UART_NUM=0) and it is a bring-up mode, not the design. The primary's console blocks its own task for ~87 ms per second on status lines alone (#340), and the uplink cannot share that budget. Useful for testing the protocol with no jumpers on the bench; not for a rig.

So: UART1, three wires, 921600, full duplex (which is what makes the command path in Phase 2 free rather than a redesign), both ends independently resettable, and the resync-and-CRC framing that makes that safe is already written and already exercised.

Phases

Phase 0a — Make the C3 target compile at all HARD BLOCKER · TEC-NATKIT-34 / #379

./build-role.sh primary esp32c3 does not build today and has not since b42d763 in August. Every source is compiled into every image by design, and board_config.hpp pins the BNO08x to GPIO_NUM_32, _14, _15 — numbers the C3 does not have. Nothing can be flashed to a C3 until this is fixed.

Measured 2026-08-25, not assumed: that one header is the ENTIRE blocker. Patching the sensor pins behind #if CONFIG_IDF_TARGET_ESP32C3 with scratch values made all three roles build clean for the C3 — primary, gateway and leaf. The primary image came out at 0xb9830 bytes, 76% of the 3 MB partition free. The scratch patch was reverted; the ticket's worry that this is a deep port is unfounded, and #379's own suggested fix is the right one.
  • Make the sensor pins target-conditional. ⚠️ Do not invent C3 sensor pin numbers — #379 is right that a header which builds and lies is worse than one that fails. The C3 here is the gateway, which carries no BNO08x at all, so the honest form is a #error on the C3 sensor path until a real C3 leaf is wired.
  • ⚠️ board_config.hpp does not include sdkconfig.h. Add it, or every #if CONFIG_IDF_TARGET_* in that header silently evaluates false and you get the ESP32 pins on every target — a header that builds and lies by a different route.
  • Add the target sweep from #379 to the handoff checklist so a target cannot rot again.
⚠️ Cost me two false failures while measuring this, so it will cost you too: build/esp32c3-gateway and build/esp32c3-leaf existed from a prior session and failed on eth_w5500_config_t undeclared — which reads exactly like an IDF incompatibility and is not. Their generated sdkconfigs predated CONFIG_ETH_SPI_ETHERNET_W5500=y, and ESP-IDF reads sdkconfig.defaults only when the generated sdkconfig does not exist. rm -rf build/<target>-<role> and they both built first time. Same trap as TEC-NATKIT-49's inert partition setting.

Phase 0b — Uplink pin defaults for the C3, and the S3 LED collision small, blocks the wiring

  • default 5 if IDF_TARGET_ESP32C3 / default 6 if IDF_TARGET_ESP32C3 for the uplink TX/RX, so a C3 does not inherit GPIO 26 and abort in uart_set_pin before anything else runs.
  • Move the S3 uplink TX off GPIO 4, which is kStatusLedGpio for every target (see the warning in What to wire). Latent today only because the S3 defaults to the Ethernet uplink and uplinkStart() then skips uart_set_pin entirely.
  • Both are one-line Kconfig changes and both are invisible failures if skipped — a boot loop in one case, two drivers on one pin in the other.

Phase 0c — Wire it, and prove the physical link closes a known gap in #348 and #349

Both of those tickets shipped with the same admission: "What is untested is the physical UART1 link itself — two jumper wires would close both at once." This is those two jumper wires.

  • Build and flash: ./build-role.sh primary esp32 -p /dev/serial/by-id/… flash and ./build-role.sh gateway esp32 -p … flash.
  • Fill in main/DevConfig.hpp from the .example — gateway only; a leaf or primary image must not be able to reach credentials.
  • Watch the gateway console: frames_ok climbing, 0 CRC failures, bytes_skipped flat after the first resync, uplink_seq_gaps at 0.
  • Confirm at the far end, not on the device: count records into Kafka and compare against the primary's frames_sent.

Done when: one leaf's data reaches Kafka over a real wire, with the reconciliation arithmetic on the ticket. This is the first time the wire itself has ever carried a byte.

Phase 1 — The gateway republishes the status frames the drift, part 1

  • kNodeStatus → natKit/sending/Log-<node id>-Binary-NatKitNodeStatusV1, payload verbatim.
  • kPrimaryStatus → natKit/sending/Log-<primary id>-Binary-NatKitPrimaryStatusV1, verbatim.
  • Keep the existing internal use (clock fit, primary→wall offset) — publish as well as, not instead of.
  • Factor the topic-and-publish switch that uplink.cpp::publishFrame already has rather than writing a second copy; the two paths must not be able to disagree about a topic name.
⚠️ The status frame's device id is in the payload, not the uplink header. A primary-status frame is about the primary and must be published under the primary's id, not the gateway's and not the stream id of whatever was last routed. Read it from offset 0 of the payload, which the struct asserts.

Done when: the toolbar health pill shows the hub and every leaf on a WiFi rig, and a recording sealed on that rig carries a real clock record rather than not_watching.

Phase 2 — The downward command path the drift, part 2

The uplink is full duplex and the primary's RX pin was claimed at design time precisely so this would not need rewiring. Nothing reads it yet.

  • Add UplinkType::kCommand, travelling gateway → primary. Same header, same CRC, same reader — the format is already directionless.
  • The gateway learns who to subscribe for from the kNodeStatus frames it already receives. No second registry, and no wildcard subscription (which would pick up commands for other rigs on the same broker).
  • Split command_relay.cpp so its JSON parse + ESP-NOW relay is fed from either an MQTT message (Eth/WiFi primary) or a serial kCommand frame. The relay must not learn which architecture it is in.
  • Run uplinkReaderStart() on the primary and a frame writer on the gateway — both files are already compiled into every image, so this is wiring, not porting.
  • The answer path needs nothing: kCommandLog already flows up and the gateway already republishes it on the topic the backend correlates against.

Done when: the Visual Programming LED button changes a leaf's colour on a WiFi rig, and the answer comes back and is correlated — the same evidence TEC-NATKIT-83 produced on the Ethernet rig.

Phase 3 — More than one leaf, and a soak never done

#349 was tested with one stream, because there were only three boards and the second leaf had been repurposed as the gateway. One stream proves the contract; it says nothing about the mux.

  • Four leaves through one primary through one wire. Per-node rate at Kafka against the primary's per-node counters.
  • Watch frames_dropped, queue_high_water and write_timeouts on the primary against bytes_skipped and uplink_seq_gaps at the gateway — the two sequence numbers exist so uplink loss and radio loss are distinguishable, and this is the run that uses them.
  • Failure behaviour: power-cycle the gateway (primary must drop, count and recover, not stall); power-cycle the primary (gateway must resync mid-stream); pull a leaf.
⚠️ A leaf publishes again long before it is at full rate — measured at 18.7 s to first frame and still 6.7% loss forty minutes after a reset. A rate taken in between reads as a fault that is not there. Do not call a recovery test failed inside the first hour.

Done when: four leaves sustain their rate through the wire over a soak long enough to see a drop and a recovery, and every counter reconciles.

Phase 4 — The gateway gets counters and a voice missing

  • Count the two silent drops in gateway.cpp (length > sizeof(sFrame)), same defect shape as TEC-NATKIT-86.
  • Publish the gateway's own health — reader stats, WiFi RSSI, MQTT disconnects, refused publishes, heap — so a WiFi rig is diagnosable from the broker like the Ethernet one is. Reuse the NatKitPrimaryStatusV1 shape or add a small V1 of its own; decide on the ticket.
The gateway's console IS readable, unlike the S3 primary's, so this is less urgent than it was for the hub. It is still worth doing: "readable if you go and plug into it" is not the same as visible in the panel, and a fielded rig has nobody at the bench.

Phase 5 — Defaults, docs and the rollback story small

  • default 4 if IDF_TARGET_ESP32C3 / default 5 for the uplink pins, so a C3 gateway does not boot-loop on an out-of-range GPIO.
  • roles/gateway.defaults: set CONFIG_NATKIT_PRIMARY_ETH_UPLINK=n explicitly, since it defaults on for the S3 and a gateway built for an S3 would inherit it.
  • ⚠️ The mirror hazard: a primary built for the S3 defaults to the Ethernet uplink and will not use the wire unless it is turned off. Two boards wired together with the primary quietly publishing over Ethernet is a confusing afternoon.
  • README: the board table gains a gateway row, and the two-board WiFi rig gets its build commands beside the Ethernet one.
  • Wiki page for the architecture as a whole — the ADR-shaped "how a natKit rig is put together, and the three ways it can reach the broker".

Which chip gets which role — DECIDED

Decided 2026-08-25 (Zach): ESP32 = primary, C3 = gateway, three leaves.

The first draft of this plan put the C3 on the hub, because that is the board that was to hand. It is round the other way, and the reason is that the C3 is single-core RISC-V while the primary is the busiest and most timing-sensitive role in the architecture: the ESP-NOW receive callback runs on the WiFi task, alongside the uplink drain task, the 1 Hz status loop, the command relay, the timing beacons and the coherence probe. On a classic ESP32 that work is spread across two cores.

That matters because hub scheduling latency is the open suspect in work already in flight: the coherence probe shows occasional millisecond excursions and the leading hypothesis on record is the receive callback being late because something else blocked. Node-to-node agreement of 0.1–0.2 ms is the number the fork was adopted on (TEC-NATKIT-27), and putting the hub on one core is a plausible way to spend it.

The gateway is the half that can afford one core. It reads a UART and publishes, and its clock hop is already the deliberately crude one — a single subtraction carrying the serial link's latency, ~1–2 ms and unmeasured — so scheduling jitter there is lost in a term the design already accepts. Meanwhile the primary lands on GPIO 26/25, the pins that are already the committed default and already vouched for.

✅ The cost is NOT a leaf after all. This was written expecting the primary to be one of the four BNO08x leaves, dropping the bench to three nodes. A bench audit on 2026-08-25 found a spare dual-core ESP32-D0WD-V3 rev 3.1 (MAC 30:c9:22:33:0c:ec, CP2102 at /dev/ttyUSB0) that is not one of them, so the primary costs nothing and all four leaves stay leaves.

⚠️ Leaf 5185027828 (MAC 4c:75:25:a4:45:3c) was NOT enumerated during that audit. Plug it back in before claiming a four-leaf run.
This is reasoning, not measurement. Nobody has run the hub on a C3. The decision is cheap to revisit — it is the same three wires with the pin pairs swapped — so if three leaves turns out to be the binding constraint, Phase 3's soak is where to test the other arrangement: run it both ways and compare coherence_typical_us over the same window.

One thing the swap makes cleaner: the C3 is now definitively never a leaf, so Phase 0a's fix to board_config.hpp is unambiguous. The C3 carries no BNO08x, so the sensor pins on that target should be a #error rather than a guess, and #379's objection to invented pin numbers is satisfied rather than worked around.

Open questions for Zach

  • ✅ ANSWERED 2026-08-25 — the console will work. The C3 is an ESP32-C3 (QFN32) rev v0.4, MAC dc:da:0c:d1:49:38, behind a CP2102N bridge at /dev/ttyUSB1. A bridge board is exactly what sdkconfig.defaults.esp32c3 already assumes when it deliberately leaves the console on UART0, so the gateway's console — the instrument Phase 0c is watched with — works out of the box, and UART0's GPIO 20/21 stay clear of the uplink pins 5/6.
  • Is the Ethernet rig staying? The plan assumes yes and keeps all three as build-time roles. If Ethernet is being retired, Phases 1 and 2 get simpler, but the primary's direct-publish code comes out — and the health path, the command relay and the channel survey all hang off it, so it is a bigger change than it sounds.
  • Does a C3 leaf ever need to exist? Phase 0a only has to make the C3 compile. If a C3 will never carry a BNO08x, the honest fix is a #error on that path; if one might, the fix needs real wiring and #379's objection to guessed pins stands.
