Restore Flow, Clean Up, Arduino→ESP-IDF, then C++→C

A staged overhaul of the natKit-IMU/embeded firmware. The device recently streamed real BNO08x IMU data but now boot-loops on sensor init, so nothing reaches the frontend. The goal is to get real data flowing again first, then give the code the attention it needs: clean it up, migrate the build from the Arduino framework to ESP-IDF (matching natVR), and begin shifting C++ → C to reclaim flash headroom for future features. The binding constraint the whole way: every step keeps data flowing.

Design captured — awaiting go. DO NOT implement yet.

Why now

Two things just landed and one thing just broke:

  • Landed: the IMU bulk stream now carries a real frame — a 24-byte binary envelope (schemaVersion | sampleCount | sampleRateHz | seqNo | deviceTsUs) on NatImuBulkDataSchema, plus a ~1 Hz device.firmware.status.v1 heartbeat. Validated end-to-end in simulator mode: broker shows len=5024 data frames + len=262 heartbeats, the bridge decodes them, Kafka has the topics. The cpp-only libnatkit-core change is pushed.
  • Broke: in real-sensor mode the device panics (Guru Meditation / StoreProhibited, null write) inside bno08x.begin_SPI(), right after "Starting the BNO08X", and reboots forever. It never reaches WiFi/MQTT — hence no data. This is the IMU bring-up path; the framing/heartbeat work is not implicated.
  • Pressure: release flash sits ~86.7% (1.31 MB part). We are fine today, but future features will crowd the ceiling — so we tackle flash structurally (leaner ESP-IDF + C) rather than with a one-off diet.

It recently worked, so the crash is most likely a regression, not a bring-up mistake. Leading suspects: unpinned sensor libraries (Adafruit_BNO08x / Adafruit_SensorLab are bare git URLs — a rebuild can pull a newer/incompatible sh2 HAL) and the recent 71e3be8 "Cleaned up the repo a bit" commit, which touched the sensor files.

Guiding principle — never break the data path

This is an incremental migration, not a rewrite. Every step ends with the same smoke test, and a step that fails it does not land:

  • Pipeline test (sim): build with NAT_SIMULATE_BNO08X, confirm Data-<id>-Binary-NatImuBulkDataSchema (len 5024) + heartbeat on the broker and bridge decode.
  • Real-sensor check: confirm frames carry physically-varying values (not sim randoms) with populated accuracies; move the board, values change.
  • Frontend: stream renders in the StreamViewer/VP for stream id 13793649670644 (ESP32-<board>).

Steps stay small and individually committable/revertible. Sim mode is retained as a first-class build so this smoke test survives the whole migration.

Phase 0 — Restore data flow first & most important

Get the real BNO08x streaming again and establish the working baseline everything else must preserve.

  1. Exact fault location. Flash the debug_verbose env (exception decoder + far less inlining than release -O3) in real mode; capture the decoded backtrace to pinpoint the null-deref (expected inside the Adafruit/sh2 SPI HAL).
  2. Find what changed. Identify the last-known-good commit/build; diff the sensor path against it, focusing on 71e3be8. Check dependencies.lock for an Adafruit/sh2 version bump between "worked" and "now".
  3. Pin dependencies. Pin all lib_deps to known-good versions/commits (Adafruit_BNO08x, Adafruit_SensorLab, AsyncTCP, etc.) and commit the lock. Bare-git-HEAD deps must go regardless of root cause — they make builds non-reproducible and are the prime regression vector.
  4. Verify. Run the full smoke test with the real sensor. This is the baseline.
Retracted from the earlier draft: the "INT=32 is wrong" theory. If it recently worked, the pins were right for this board; the schematic almost certainly uses symbol-relative pin labels, not raw ESP32 GPIO numbers.

Phase 1 — Cleanup behavior-preserving

Make the code legible and safe without changing what it does. Verify data still flows after each change.

  • Delete the large dead commented-out blocks (Kafka-REST/HTTP, old JSON paths, sample scaffolds).
  • Fix real bugs surfaced during diagnosis: the printf("...%s", std::string) UB at ImuReader.hpp:809; the misleading USE_SERIAL comment ("disables" vs actually enables).
  • Centralize configuration into one header — pins (documented against schematic nets), broker host and port (kill the hardcoded 1883), sample rate, device id.
  • Unify the time base on microseconds end-to-end (removes the ms/µs split the frame work exposed — per-sample time is currently ms while the header is µs).
  • Keep NAT_SIMULATE_BNO08X as a documented, supported test build.

Phase 2 — Arduino → ESP-IDF incremental

The structural move, and where the leaner runtime buys flash. The trick to staying-working is Arduino-as-an-ESP-IDF-component first, then peeling Arduino away one subsystem at a time toward natVR's native stack.

2a — Switch the build system, keep the APIs

Move to framework = arduino, espidf (PlatformIO supports this — it's already a commented line in platformio.ini). Same Arduino APIs, ESP-IDF build underneath. Verify identical behavior.

Leave PlatformIO for raw idf.py to fully match natVR's toolchain, if desired.

Phase 3 — Begin C++ → C long-term, flash-driven

Started here (not finished) — a direction, taken incrementally on the now C-first ESP-IDF base. Each conversion is measured for flash and verified for data flow.

  • Encoding. Replace the C++ libnatkit-core Schema classes with the C ABI (libnatkit-core-abi.h) or a small hand-rolled C frame encoder. The frame is trivial in C (24-byte header + fixed-size samples); natVR precedent is hand-built frames with cJSON and no C++ library.
  • Drop heavy C++. Remove std::string / unordered_map / std::function usage; remove exceptions and RTTI. These, plus the STL, are the bulk of the C++ flash cost.
  • Convert modules (sensor, buffer, framing, transport, config) to C one at a time, keeping the smoke test green throughout.
Note: the earlier standalone "quick flash relief" phase (-O3→-Os, LTO, --gc-sections) was dropped by request — we're fine on flash today, and Phases 2c and 3 address the ceiling structurally for future work. Those compiler-flag levers remain available as a cheap fallback if headroom gets tight mid-migration.

Decisions & risks to validate early

  • BNO08x on ESP-IDF/C has no in-repo precedent (natVR is ADC-EMG, not BNO08x). The CEVA sh2 driver is portable C, but this is the migration's riskiest piece — keep the sensor under the Arduino component the longest (Phase 2b, last).
  • libnatkit-core C ABI coverage for the IMU frame is unconfirmed — verify libnatkit-core-abi.h exposes an IMU-frame encoder, or plan to hand-roll one (cheap).
  • Flash math: biggest wins are dropping Arduino (2c) and the C shift (3); confirm each with a before/after size measurement so the effort is evidence-driven.
  • Nested-submodule / cpp-only divergence still applies to any libnatkit-core change — the firmware fetches remote cpp-only, distinct from the repo submodule.
