Worker Node Processing Rollout Plan

Deliver worker-node-backed processing incrementally, starting with the ML control plane and expanding toward a shared scheduler that can also own EMG transforms and other backend jobs.

First implementation focus: libnatkit/scripts/natkit_ml_control_plane.py, frontend/src/MlPipeline/, and project context updates in AGENTS.html.

Implementation Principle

  • Start from the existing ML control plane because it already has job orchestration, status streaming, and a frontend surface.
  • Introduce worker slots and queues before introducing distributed persistence.
  • Require slot selection in the UI once the backend can list and describe slots.
  • Keep the first slice compatible with current single-node local development.

Phase 1 - In-Memory Worker Slots In The Existing ML Control Plane

In progress - partially implemented
  • Implemented: worker-node model with logical thread slots and default slot count from host thread count.
  • Implemented: worker summary reporting with slot-capacity rollups and heartbeat timestamps on the current embedded worker.
  • Implemented: per-slot queueing, per-job priority, queued-job cancellation, checkpointed running-job cancellation, and slot snapshots.
  • Implemented: placeholder-principal ownership checks for queued-job reprioritization and stop requests.
  • Implemented: control-plane actions for slot listing, job listing, job updates, and job stop.
  • Implemented: ML frontend slot targeting plus slot utilization and assigned-job visibility.
  • Implemented: placeholder slot assignment in the frontend before real auth exists.
  • Implemented: placeholder principal id on slots and jobs before real auth exists.
  • Implemented: local persistence for slot ownership and job history via the control plane, with JSON snapshots and a stronger SQLite-backed state store.
  • Remaining: move from single-process local persistence to shared multi-process scheduler state once workers are split out.

Phase 2 - Persist Scheduler State

  • In progress: job, slot, and assignment state now has a SQLite-backed persistence path instead of only JSON snapshots.
  • Implemented in the current bridge slice: the SQLite path now runs with WAL-capable settings, tracks a monotonic scheduler-state revision, lets a running control plane refresh externally written worker, slot, and job state from the shared database without a restart, now probes only the revision metadata before deciding whether a full state reload is necessary, now throttles those revision probes behind a short poll window so repeated WebSocket actions do not hit SQLite every time, now persists scheduler workers, slots, metadata, and jobs through incremental row-level upserts with key-only stale-row probes instead of rereading full table bodies before every save, and now writes back normalized recovered in-flight job state immediately after a control-plane restart so shared readers do not keep seeing stale pre-recovery payloads.
  • Remaining: move scheduler state fully out of single-process local storage.
  • Choose whether the long-term mutable state store is PostgreSQL-backed, Kafka-backed plus relational projection, or hybrid.
  • Publish job-event streams and utilization summaries onto natKit metadata or logging streams where useful.
  • Ensure reconnects and control-plane restarts do not orphan visible job state.

Phase 3 - Separate Worker Runtime From Control Plane

  • Split the current single process into a control-plane process and one or more worker processes.
  • In progress: the control plane now has explicit external worker registration, heartbeat, and unregister actions, and persisted worker summaries can now include non-embedded workers even before their slot inventories are mirrored into the scheduler.
  • Implemented for the first remote slice: external workers can now mirror logical slot inventories into scheduler state, claim/report queued jobs for those slots through the control plane, and run them through the new libnatkit/scripts/natkit_ml_worker.py standalone worker runtime.
  • Implemented in that runtime slice: the standalone worker now retries control-plane connectivity with backoff, replays deferred terminal job-state reports after reconnect, reasserts surviving in-flight running jobs back to the control plane after a reconnect so recovered remote work does not remain stuck in an "awaiting external worker state" placeholder, and now treats a true worker-process restart under the same worker id as an explicit requeue-and-rerun event for that worker's in-flight jobs. Job state now persists and exposes a restart_count, worker/slot summaries now expose cumulative restart-attempt counts so those reruns are visible in scheduler and frontend views, automatic reruns are now bounded so exhausted restart attempts end in an explicit failed job state rather than unbounded retry churn, and active worker sessions are now enforced across heartbeat, slot-sync, claim, report, and unregister actions so stale worker processes cannot keep mutating scheduler state after a newer session has taken ownership.
  • Implemented in the local deployment slice: the dedicated dev-stack control-plane container now accepts runtime worker-thread overrides through compose, including an external-worker-only mode with NATKIT_ML_CONTROL_PLANE_WORKER_THREADS=0 so separate worker processes can provide the only scheduler-visible execution slots.
  • Implemented in the deployment-hardening slice: the control plane now exposes explicit worker drain/resume control, draining external workers now stop claiming queued slot work until resumed, embedded-worker slots now also hold queued jobs instead of starting new local work while the worker remains in a draining state, worker summaries now expose whether a draining worker still has active work attached or is ready to stop cleanly, deployment tooling can now block on that transition through an explicit wait_worker_drain_ready action instead of polling worker summaries manually, and the new libnatkit/scripts/natkit_ml_worker_operator.py CLI now wraps worker inspection plus that drain/resume flow for operator scripts, including repeated-worker coordinated maintenance commands with aggregate exit behavior, a fail-fast mode for stopping on the first hard request error, file-based worker-id inputs for generated deployment inventories, structured JSON worker manifest inputs with optional group filtering, and optional structured result JSON artifacts so rollout tooling can persist the requested worker set, the actually processed subset, and per-worker maintenance outcomes directly.
  • Remaining: harden deployment behavior, improve recovery for in-flight work across control-plane restarts, then move scheduler durability fully beyond control-plane-local state so external workers can become the default execution mode.
  • Replace the current embedded-worker summary with external worker registration and heartbeats from separate worker processes.
  • Route job claims to the worker that owns the target slot.
  • Retain the same slot-based frontend contract so the transport split is internal.

Phase 4 - Migrate Other Backend Processing To Workers

  • In progress: the Stream Viewer EMG transform path now exposes local worker-slot capacity, active-transform listing, and stop control instead of unbounded detached worker creation.
  • Implemented in that local slice: per-transform slot identity, frames-processed counts, last-frame timestamps, live frontend polling, active-transform state updates for connected clients, and explicit worker summary fields such as available slots and worker heartbeat.
  • Remaining: move EMG transforms fully out of the Drogon WebSocket process and onto separate worker processes.
  • Move other long-lived processing paths, such as calibration or replay workloads, onto the same scheduler surface.
  • Keep the browser backend focused on control-plane and stream access responsibilities.

Phase 5 - Real User Ownership And Quotas

  • Replace placeholder principal ids with authenticated user or workspace identities.
  • In progress: explicit slot assignment and release now exist in the ML control plane, and slot reassignment is blocked while active work owned by another principal is still attached.
  • Extend that placeholder policy surface into authenticated slot assignment, revocation, and quota rules.
  • Implemented in the placeholder-principal slice: a user may now submit only to slots already assigned to them; unassigned slots must be claimed first.
  • Implemented in the frontend ownership slice: the ML Pipeline now exposes principal-scoped slot counts plus filters for all, mine, claimable, submittable, and active slots so placeholder ownership can be worked without scanning the full scheduler state manually.
  • Add per-user views, filters, and capacity summaries in the frontend.

Metrics To Surface Early

Metric Why it matters
queue_depth Shows oversubscription pressure immediately
assigned_job_count Shows how much work is attached to a slot, not just what is running now
running_job_id Makes current ownership and activity obvious
busy_ratio_60s Gives a stable utilization signal instead of a single instant boolean
last_heartbeat Necessary once workers become separate processes

Risks To Watch

  • Trying to generalize every backend workload before one path is production-worthy.
  • Letting UI concepts depend on raw thread implementation details.
  • Building queue semantics that become invalid when jobs are made durable later.
  • Deferring cancellation semantics until too many job types assume they can only fail or complete.
This plan is intentionally staged. The immediate goal is a usable slot-based scheduler surface, not a complete cluster rewrite in one pass.
