Frontend-Driven ML Pipeline Plan

Add a frontend workflow for discovering Kafka-backed data streams, building processing and ML graphs, training and validating models, and publishing results back onto natKit stream infrastructure. Move runtime inference and graph execution into natKit/libnatkit over time, with ONNX Runtime as the target inference engine and the current Python tooling retained only as a reference path during migration.

Scope: frontend/ as the user interface, libnatkit as the execution substrate, natVR Python as the current reference implementation to phase out deliberately.

Recommendation

  • Yes: the frontend should become the primary UI for model training, validation, and deployment workflows.
  • Yes: ONNX Runtime support in libnatkit is the correct long-term runtime direction if natKit is meant to own ML execution.
  • No: do not immediately scrap the existing Python scripts. Keep them as the reference implementation until the C++ graph/runtime path can reproduce reconstruction, featurization, training, and replay validation with equivalent outputs.
  • Build this as a staged migration: frontend orchestration first, shared pipeline model second, native execution third, Python removal last.

Why This Direction Makes Sense

Operator workflow

  • Users need stream browsing, run selection, labeling, training, and deployment in one place.
  • The current Python CLIs are composable, but they are not a usable end-user surface.
  • The existing Svelte frontend already has stream-viewer and experiment UI pieces that can anchor this work.

System ownership

  • If natKit owns real-time stream processing, natKit should eventually own inference runtime too.
  • Keeping inference in Python forever creates two systems: the stream platform and the ML runtime.
  • A core runtime in libnatkit gives one transport, one deployment story, and one execution model.

Constraint

  • Training and validation logic already exist in natVR.
  • The frontend should not directly implement signal processing or training math in TypeScript.
  • The frontend should configure and inspect pipelines; the backend/runtime should execute them.

What Should Not Happen

  • Do not rebuild the existing Python DSP and model selection logic ad hoc in the frontend.
  • Do not make the browser responsible for long-running training, Kafka consumption, or model artifact storage.
  • Do not jump straight to a free-form visual programming UI before the execution model is stable.
  • Do not remove Python before there is a compatibility harness proving the native path matches expected outputs.

Target System

Frontend (Svelte)
  ├─ browse Kafka-backed stream clusters and recorded runs
  ├─ assemble training / validation datasets
  ├─ design pipelines as graphs
  ├─ trigger training / validation jobs
  ├─ inspect metrics, artifacts, confusion matrices, and lineage
  └─ publish or deploy selected models

natKit control plane
  ├─ stores graph definitions
  ├─ resolves stream schemas and artifact locations
  ├─ schedules jobs
  └─ exposes job progress and logs to the frontend

libnatkit execution runtime
  ├─ Kafka source / sink nodes
  ├─ stream windowing and transform nodes
  ├─ feature extraction nodes
  ├─ ONNX inference nodes
  ├─ post-processing / smoothing nodes
  └─ artifact emitters and output publishers

Reference / migration layer
  └─ existing natVR Python pipeline remains callable until native parity is reached

Execution Model

Graph definition

  • Represent each workflow as a typed directed graph.
  • Nodes define input contracts, output contracts, config schema, and runtime capability requirements.
  • Graphs must be serializable as JSON so they can be stored, diffed, and executed outside the UI.

Job types

  • reconstruct: Kafka run to parquet/markers/artifacts
  • feature-build: artifact to features/calibration
  • train: dataset to model artifact
  • validate: model + validation runs to report
  • stream-runtime: live source to live output stream

Runtime separation

  • The browser defines graphs and watches jobs.
  • The control plane validates graphs and dispatches work.
  • The runtime executes nodes and publishes logs, metrics, and artifacts.

Visual Programming Scope

The visual interface should start narrow. The first graph editor should be about assembling a stream-processing pipeline from a fixed catalog of nodes, not arbitrary user-authored code.

Kafka Integration Model

  • Recorded-run discovery should reuse the session/run logic already built for natvr-emg-reconstruct.
  • The frontend should let users choose training and validation sets directly from discovered Kafka-backed runs.
  • The runtime should treat Kafka as both source and sink, with artifact emission separated from live stream publication.
  • Each job should record exact input stream topics, selected run windows, transformation graph revision, and output artifact IDs.
  • Lineage needs to be first-class; otherwise model reproducibility will collapse as soon as multiple users are training variants.

Native ONNX Runtime Direction

  • Add ONNX Runtime support to libnatkit for inference first, not for all training immediately.
  • Inference is the right first native milestone because it has the clearest runtime value for live stream processing.
  • Traditional training families already in Python (LDA, SVM, RF) do not naturally map to ONNX as the training authority. They can still export inference artifacts or remain training-time reference tools during migration.
  • If the long-term goal is user-authored ML pipelines, native execution should focus on: tensor transforms, feature builders, model inference, post-processing, and streaming sinks.
  • Training can remain hybrid longer than inference without harming the product direction.

Migration Strategy

Recommended: dual-track migration
Phase Goal Primary implementation
1 Frontend job orchestration for existing workflows UI + backend wrapper around current Python scripts
2 Shared graph/job schema Control-plane contracts used by both UI and Python wrappers
3 Native libnatkit inference graph runtime C++ nodes + ONNX Runtime + Kafka source/sink nodes
4 Parity harness against Python outputs Golden-run comparison suite for reconstruction, features, and inference
5 Frontend graph editor and deployment UX Svelte pipeline designer backed by native runtime
6 Retire Python runtime paths that are fully replaced Only after measured parity and operational confidence

Implementation Phases

  • Phase A · Control-plane first: expose existing reconstruct/train/validate operations through a backend service the frontend can call.
  • Phase B · Dataset UI: build run browser, train/eval selectors, job submission, and report viewing in the frontend.
  • Phase C · Graph schema: define a versioned JSON graph format and node catalog that can describe the current pipeline without visual editing yet.
  • Phase D · Native runtime: implement libnatkit stream nodes and ONNX inference support for live runtime graphs.
  • Phase E · Visual editor: add a constrained graph canvas that edits the same JSON graph model used by jobs.
  • Phase F · Python reduction: remove or freeze Python paths only after parity tests, artifact compatibility, and operator workflows are stable.

Open Questions

  • Where should the control plane live: a new natKit backend service, existing bridge process, or a dedicated job service?
  • Should graph definitions live in Kafka metadata streams, filesystem artifacts, or a persistent database?
  • What is the minimal node catalog that makes the first graph editor useful without turning it into a generic IDE?
  • What artifact format should native inference expect for non-ONNX classical models during migration?
  • Which parts of training truly need to move into C++, and which can remain service-side wrappers longer without hurting the architecture?

Immediate Next Steps

  • Define a backend service boundary for the existing Python reconstruct/train/validate workflow.
  • Add a frontend page for Kafka run selection and training job submission.
  • Write a versioned graph JSON spec before building a canvas UI.
  • Prototype libnatkit ONNX inference integration on one narrow live-stream path.
  • Create a parity test harness comparing Python and native outputs on a fixed set of recorded runs.
This plan assumes the product direction is correct: frontend for workflow, natKit/libnatkit for execution. The migration risk is not in the UI; it is in replacing implicit Python pipeline behavior without a shared graph model and parity harness.
