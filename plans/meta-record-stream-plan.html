MetaRecord Metadata Stream Plan

Replace the single-purpose metadata schema path with a generic MetaRecord transport rooted in libnatkit-core C++ record classes, so one Meta stream can carry multiple metadata record types while keeping serialization abstracted behind the existing schema/registry model.

Scope: libnatkit-core first, then bindings, then natVR/frontend adoption.

Decision

  • Keep StreamType::META as the stream category.
  • Use one generic wire schema name: MetaRecord.
  • Dispatch concrete metadata types by a stable numeric record_type_id.
  • Define concrete metadata as C++ classes such as SessionMetadataRecord.
  • Make JSON and binary two serializations of the same record contract, not two separate designs.

Current State

What exists

  • StreamType::META already exists in core.
  • Schema, Decoder, and Registry already provide codec registration.
  • BasicMetaInfoSchema is the current placeholder metadata type.

What is missing

  • Generic typed metadata dispatch within one meta stream.
  • Concrete session metadata record class in core.
  • Bindings for Python/frontend publication and decoding.

Constraint

  • All semantics should live in C++ first.
  • Bindings should expose the existing core record model.
  • Do not make metadata typing a Python-only convention.

Record Model

Layer Purpose Initial choice
Meta stream type Topic/category for low-volume stream-cluster metadata Keep existing core stream type
MetaRecord Generic wire schema used by the topic registry New core decoder path
record_type_id Selects the concrete metadata record class Stable numeric registry in core
SessionMetadataRecord Session-level metadata such as purpose, participant, protocol, devices, tags First concrete record type

Implementation Phases

Phase 1 complete · Phase 2 started
  • Phase 1: Add MetaRecord base decode path in libnatkit-core, keep BasicMetaInfoSchema for compatibility.
  • Phase 2: Add SessionMetadataRecord with JSON and binary codecs and register it through the new typed metadata path.
  • Phase 3: Add tests or compile-time validation examples for round-trip encode/decode and registry dispatch.
  • Phase 4: Add bindings and natVR helpers that publish/consume MetaRecord topics.
  • Phase 5: Update the EMG experiment frontend to create a session, publish session metadata, and publish session lifecycle markers.

Open Design Follow-Ups

  • Whether ExgPillEmgDataSchemaV1 eventually needs session_id on the raw data path for overlapping sessions on one device.
  • Whether to migrate or deprecate BasicMetaInfoSchema after bindings are updated.
  • How to expose the metadata type registry to Python without duplicating ids outside core.
  • Which next concrete record type should follow session metadata: hardware metadata, experiment metadata, or marker definitions.
This plan is intentionally core-first. Higher-level language bindings should wrap the C++ records, not redefine the metadata protocol.
