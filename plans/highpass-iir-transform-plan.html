High-Pass IIR Transform Plan

Add a new generic numeric-channel transform named highpass_iir that runs on the descriptor-driven transform path, emits NatSignalFrameDataSchemaV1, and lets the caller choose either a Butterworth design or a direct biquad high-pass section without bundling rectification into the same operation.

Scope: Stream Viewer transform capability model, backend transform worker DSP path, frontend transform controls, validation, and transform provenance.

Decision

  • Add highpass_iir as a new transform kind rather than overloading highpass_rectify.
  • Keep rectification as a separate transform concern, not a flag hidden inside the new high-pass transform.
  • Use NatSignalFrameDataSchemaV1 as the derived output contract so the new transform remains chainable.
  • Treat butterworth as a response-family choice implemented internally as cascaded sections.
  • Treat biquad as a single configurable 2nd-order section with explicit q.
  • Keep the current highpass_rectify path temporarily for compatibility while the pure high-pass transform is introduced.

Implementation Progress

  • 2026-07-03: created this plan and fixed the transform boundary: the new work is a pure high-pass stage, while rectification remains separate.
  • 2026-07-03: started the first implementation slice in the Stream Viewer transform protocol, backend worker, and frontend transform controls.

Why This Exists

Current state

  • The generic transform path already supports descriptor-based numeric channel inputs.
  • The backend currently exposes bandpass_envelope and highpass_rectify.
  • The runtime high-pass stage is only a one-pole filter inside the WebSocket worker.

Target state

  • A user can request a pure high-pass transform without implicitly rectifying the signal.
  • The transform config can choose between Butterworth and biquad IIR methods.
  • The new transform can run over any compatible descriptor-driven numeric channel frame.

Constraint

  • This should stay on the generic transform path, not reintroduce EMG-specific branching.
  • The first slice should improve capability and signal-processing fidelity without forcing a full transform-DSP library extraction in the same patch.
  • Compatibility for existing highpass_rectify clients should remain explicit during the transition.

Transform Contract

The new transform keeps the same input requirements as the existing numeric-channel transform surface. Only the DSP config changes.

Field Type Notes
transform_kind string highpass_iir
config.cutoff_hz number Required positive cutoff frequency
config.iir_method enum butterworth or biquad
config.butterworth_order integer Used only when iir_method=butterworth
config.biquad_q number Used only when iir_method=biquad

Execution Model

source topic
  -> descriptor compatibility check
  -> normalize numeric channel frame
  -> select highpass_iir config
  -> build per-channel IIR state
  -> apply Butterworth cascade or biquad section
  -> emit NatSignalFrameDataSchemaV1
  -> publish provenance with exact method/config

Butterworth and biquad share the same source and output frame model. The difference is only the internal section design and state allocation.

Implementation Phases

New plan · active on 2026-07-03
  • Phase 1 · Protocol shape: add highpass_iir to capability discovery, request parsing, provenance serialization, and transform summaries.
  • Phase 2 · Worker DSP: replace the one-pole-only high-pass branch for the new transform kind with configurable Butterworth and biquad IIR processing.
  • Phase 3 · Frontend controls: add method selection plus conditional controls for Butterworth order and biquad Q.
  • Phase 4 · Validation: reject invalid method values, non-positive cutoff, invalid orders, and invalid Q values before worker startup.
  • Phase 5 · Follow-on cleanup: decide whether highpass_rectify becomes a compatibility preset over separate high-pass and rectify transforms or remains temporarily as a legacy combined action.

Open Questions

  • Whether a standalone rectify transform should be added immediately after this slice or in a follow-on patch.
  • How aggressively to move DSP helpers out of StreamViewerWebSocket.cpp into reusable core utilities once the first backend slice is stable.
  • Whether Butterworth order should be capped at a small fixed maximum in the public API or only in the current implementation.

What Not To Do

  • Do not hide rectification inside the new high-pass transform.
  • Do not create a new output schema just because the filter method changed.
  • Do not add schema-name allowlists when the descriptor path model already expresses compatibility.
  • Do not silently reinterpret biquad and butterworth as equivalent user-visible methods.
The immediate goal is a clean pure high-pass transform that fits the generic transform surface. Rectification can then become an explicit downstream stage instead of an accidental side effect.
