Additional Transformations Plan

Extend the generic descriptor-driven transform surface with a composable DSP set: pure band-pass filtering, notch filtering with optional harmonics, a standalone rectifier, RMS windowing, low-pass envelope detection, and sliding-window framing. The goal is to keep each operation explicit, chainable, and reusable across compatible numeric channel streams.

Scope: transform capability definitions, backend worker DSP implementations, frontend transform controls, provenance, and validation for the next generic transform stages.

Progress Update

  • 2026-07-03: Phase 5 cleanup is implemented as a direct breaking removal of the old combined bandpass_envelope and highpass_rectify transform kinds.
  • 2026-07-03: Phase 1 is implemented on the generic transform path with standalone rectify and pure lowpass_envelope.
  • 2026-07-03: Phase 2 is implemented with descriptor-driven bandpass_iir and notch_iir, including capability discovery, worker DSP, provenance config, and Stream Viewer controls.
  • 2026-07-03: Phase 3 is implemented with rms_window on the same generic transform surface using explicit sample-count configuration and prefix-window startup behavior.
  • 2026-07-03: Phase 4 is implemented with sliding_window using window_samples and step_samples, worker-local output sequence numbering, and end-of-window timestamps while still emitting NatSignalFrameDataSchemaV1.
  • Latest validation: backend rebuilds and frontend typechecks passed after the direct removal of the legacy combined transforms.

Decision

  • Keep these as separate transform kinds rather than bundling them into larger EMG-specific presets.
  • Preserve NatSignalFrameDataSchemaV1 as the shared output contract for all transforms that keep the same channel-frame shape.
  • Prefer simple transform chaining such as highpass_iir -> rectify -> rms_window over creating one large opaque preprocessing transform.
  • Add sliding-window support as an explicit transform, since it changes time semantics and often acts as the bridge into feature extraction.
  • Leave room for later transform-specific schemas only when the output field model genuinely changes.

Current State

  • Implemented: highpass_iir, rectify, lowpass_envelope, bandpass_iir, notch_iir, rms_window, and sliding_window.
  • Removed: the combined legacy transforms bandpass_envelope and highpass_rectify.
  • Remaining gap: any later schema split for windowed outputs remains an open design choice, but the planned transform set itself is now implemented.

Target Transform Set

Transform kind Purpose Notes
bandpass_iir Pure band-pass filtering No rectification or smoothing; likely shares design choices with highpass_iir
notch_iir Suppress mains or narrowband interference Should support base frequency plus optional harmonic count
rectify Absolute-value transform Used as the explicit magnitude stage in place of the removed combined rectification path
rms_window Windowed RMS magnitude estimate Should expose window size and possibly overlap behavior
lowpass_envelope Linear envelope detector Should be a pure low-pass stage; caller can chain rectification first when desired
sliding_window Explicit framing into overlapping windows Most likely the first transform here that may need output-shape review beyond the current frame semantics

Design Direction Per Transform

Band-pass filter

  • Pure filtering only.
  • Config should include low cutoff, high cutoff, and method.
  • Reuse the same IIR design machinery as high-pass where practical.

Notch filter

  • Base frequency, Q, and harmonic count should be explicit config.
  • Harmonics should stop at Nyquist automatically.
  • Chain of notch sections is a clean first implementation.

Rectifier

  • No filter state required.
  • Pure absolute-value mapping over samples.
  • Acts as the explicit magnitude stage instead of the removed combined rectification transform.

RMS window

  • Config should include window length in samples or milliseconds.
  • Need clear edge behavior for startup frames.
  • May operate sample-by-sample inside each channel stream while preserving frame shape.

Low-pass envelope

  • Pure low-pass stage.
  • Do not silently rectify inside it.
  • Typical usage becomes rectify -> lowpass_envelope.

Sliding window

  • Config should include window size and step size.
  • Needs explicit policy for cross-frame buffering and timestamps.
  • This is the transform most likely to force a second shared derived schema later.

Recommended Order

1. rectify
2. lowpass_envelope
3. notch_iir
4. bandpass_iir
5. rms_window
6. sliding_window

That order keeps the first slice simple. rectify and lowpass_envelope finish the cleanup of the current combined transform model. notch_iir and bandpass_iir can reuse most of the recent IIR work. rms_window is still frame-local if implemented carefully. sliding_window is last because it has the largest semantic impact on buffering, timestamps, and output shape.

Implementation Phases

In progress · updated on 2026-07-03
  • Phase 1 · Rectification split: completed in the generic transform path with rectify and lowpass_envelope.
  • Phase 2 · Additional IIR filters: completed with notch_iir and bandpass_iir using the same generic numeric-frame path and shared IIR section design utilities.
  • Phase 3 · Window energy transform: completed with rms_window using explicit sample-count config and prefix-window startup behavior.
  • Phase 4 · Sliding-window framing: completed with explicit overlapping windows, end-of-window timestamps, worker-local output sequence numbering, and NatSignalFrameDataSchemaV1 output preservation.
  • Phase 5 · Cleanup: completed as a direct removal of the legacy combined transforms once the explicit composable set fully covered their behavior.

Validation Requirements

  • Reject invalid cutoff orderings for band-pass filters.
  • Reject invalid notch frequencies, Q values, and harmonic counts.
  • Reject zero or negative RMS and sliding-window sizes.
  • Verify that harmonic notch chains stop before Nyquist.
  • Verify transform chaining over NatSignalFrameDataSchemaV1 without schema-specific code paths.
  • Add provenance coverage so downstream consumers can see exact transform settings.

Open Questions

  • Whether the current choice to keep sliding_window on NatSignalFrameDataSchemaV1 should remain permanent or later move to a dedicated shared windowed-frame schema.
  • Whether RMS and low-pass envelope should accept durations in milliseconds, samples, or both.
  • Whether the frontend should start grouping transforms into filter, magnitude, and framing categories for discoverability.

What Not To Do

  • Do not reintroduce hidden rectification inside new filter transforms.
  • Do not collapse all preprocessing into one broad transform kind with a large config blob.
  • Do not let sliding-window semantics drift without an explicit timestamp and sequence policy.
  • Do not create frontend-only transform definitions that bypass backend capability discovery and provenance.
The direction here is a clean transform vocabulary: filters, magnitude stages, and framing stages that can be composed explicitly and inspected independently.
