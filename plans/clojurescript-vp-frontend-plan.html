A ClojureScript Frontend for Visual Programming

Build a standalone frontend in ClojureScript whose entire scope is the Visual Programming page: author, validate, run and observe stream graphs; record experiments; train and classify. It speaks the existing /ws/stream_viewer protocol and /api/auth/* — zero backend change — and adopts the stack and the design language of rvbbit: reagent + re-frame, garden-driven theming, and a dark neon direct-manipulation canvas. Not a visual port of the Svelte page — a better-looking rebuild with behavioral equivalence where it counts.

Phase 0 done — Phase 1 in progress — code in frontend-cljs/

1. Why this is tractable

The Visual Programming page is already a client of a data protocol, not a view over an ORM. Everything it knows arrives as JSON over one WebSocket; everything it changes leaves the same way. That protocol is the seam, and it is stable enough that the whole frontend below it is replaceable without touching C++.

Second, the page is already data-driven by design. Per the visual-programming rework (Phases 0–8, all landed), the palette and inspector render from the runtime list_node_catalog, and viewer choice comes from a descriptor registry, never a sensor name. There are no node-type unions to re-encode.

Third, the thing most in need of a rewrite is exactly the thing ClojureScript is good at. StreamGraphEditor.svelte is 6,326 lines, and a prior session tried and abandoned splitting it further because canvas/palette/inspector/context-menu share mutable interaction state (drag, pan, pending-connection, context-menu) that can't leave the component. In a re-frame app that state is data in app-db, and the file decomposes into ~20 namespaces on the first pass. That is the concrete, non-aesthetic payoff.

The bet: the graph editor becomes a set of subscriptions over one inspectable app-db plus pure functions over graph data (geometry, flattening, validation, cue schedules). Interaction becomes events ([:node/drag-start id]). Everything hard to test today becomes trivially testable, and undo/redo comes almost free.

2. Scope

In scope

  • The Visual Programming page in full: graph library sidebar, toolbar, canvas (nodes, edges, pan/zoom, connect, context menu, command palette), inspector for every node kind, run control, live inline viewers, timeline/transport, experiment recording, train submit, classify wiring, composites, param nodes, profiles.
  • The parts of the shared StreamViewer/ layer VP depends on: the WS client, the descriptor helpers, the viewer registry, the cue/experiment engine, and the eight viewer surfaces VP renders on-canvas.
  • A minimal auth gate (session check + login form) so the app is usable standalone.
  • An rvbbit-flavored design system in garden (§6) — the visual identity, not a copy of the Svelte CSS.
  • Dev + prod packaging (compose service, Dockerfile, nginx) alongside the Svelte app.

Explicitly not in scope

  • Porting StreamViewer, MlPipeline, AdlExperiment, ImuExperiment, Admin, home/about. They stay in Svelte.
  • Any change to the C++ backend, the ML control plane, or the WS protocol. If the port wants a protocol change, that's a separate plan — this one must be able to succeed without one.
  • Visual parity with the Svelte page. Explicitly abandoned (see §6). Behavioral and protocol equivalence still gate every phase; pixels do not.
  • Deleting the Svelte app. Retiring its VP page is the last phase, gated on function.

Three invariants the port must not break

1. editor_metadata is an opaque round-trip. The backend stores and returns it verbatim (it holds the unflattened composite editor tree, which is how a composite graph reloads from the backend alone with no localStorage). Any key renaming — snake_case → kebab-case in and back — silently corrupts it. Decision: keep wire keys verbatim as snake_case keywords end-to-end (:graph_id, :output_stream_id). No global key transformation. This is un-Clojure-y and it is correct; one round-trip test on a captured payload pins it.

1b. Only plain FIELD NAMES may become keywords (found in Phase 1, against captured payloads). (js->clj x :keywordize-keys true) turns a key containing a slash into a namespaced keyword, and writing it back with clj->js emits only the name — so "source/13793649670644-1785250699870" silently becomes "13793649670644-1785250699870". natKit node ids routinely contain a slash (source/…, viewer/…, composite/…, param/1) and node_statuses, node_diagnostics and edge_diagnostics are all keyed BY NODE ID — three of five node_statuses keys in a real captured payload hit this. The rule: keywordize a key only when it matches ^[A-Za-z_][A-Za-z0-9_]*$, leave every other key a string. That also lands on the right semantics — field names keywordize, identifier keys stay strings, and every id-keyed lookup table is accessed with the raw id.

2. The node catalog stays the source of truth. No TransformKind-style union in the new app either. Adding a C++ transform must remain a zero-frontend-change event.

3. Viewer choice is descriptor-driven. chooseViewerRenderer keys off descriptor/channel-label shape, never a schema or sensor name. Its 10 unit cases port verbatim even as the visuals change.

5. Toolchain — decided

Verified on this machine: Clojure CLI 1.12.5.1664, Java 25, Node, and babashka are installed (~/.m2 is empty and will populate on first run).

5.1 Build — shadow-cljs, deps from deps.edn

shadow-cljs for the build (npm interop is the whole point: Chart.js and any React widget come straight from node_modules), with dependencies declared in deps.edn via :deps true in shadow-cljs.edn. Now that the Clojure CLI exists, that gives one dependency file that also serves clj -M:test, clj-kondo, cljfmt and nREPL tooling. rvbbit runs plain :dependencies inside shadow-cljs.edn; either works, and deps.edn is the better default here.

Rejected: figwheel-main (weaker npm interop, and shadow is what the reference project uses); squint/cherry (no JVM needed, but not real ClojureScript — no full macro system, no core.async, different stdlib — wrong trade for a 13k-line port leaning on malli and re-frame).

5.2 Renderer + state — reagent + re-frame decided

This supersedes the earlier Replicant recommendation. The deciding factor is the rvbbit target: rvbbit is a re-frame app, and its supporting library set is not incidental — it maps almost one-to-one onto things the VP page already does by hand. Adopting the stack means inheriting the infrastructure along with the look.

Correction from the build (Phase 0): websocket-fx was tried and rejected. It imposes its own envelope on every frame — {:id <uuid> :proto :request|:subscription|:push :data <payload>} — and routes inbound frames by matching :id against an outstanding request or an open subscription. natKit's protocol is flat and mostly push-driven: outbound is {"action": …}, inbound is {"type": …}, and most inbound frames are unsolicited broadcasts (stream_graph_status, live frames, ml_control_plane relays) that correlate to no request id. Under websocket-fx those frames route nowhere, so adopting it would have meant changing the backend protocol — explicitly out of scope. protocol/socket.cljs is the ~100 lines that actually apply (connect, exponential backoff, send, inbound dispatch). Every other row of the table stands.

Decision: mirror that stack. The Phase-0 renderer spike is cancelled — there is no longer a question to answer. Replicant would have meant re-implementing every row of that table by hand for an aesthetic gain that the rvbbit target makes moot.

Adopt rvbbit's stack and aesthetic, not its file layout. rvbbit's bricks.cljs is 1.35 MB, views.cljs 565 KB, flows.cljs 364 KB. Escaping a 6,326-line file is a primary motivation for this port — keep the ~20-namespace decomposition in §7 and treat any namespace crossing ~800 lines as a smell.

5.3 Data validation — malli

Schemas for the inbound message union, the outbound action union, and StreamGraphDefinition. Used in tests (against golden payloads captured from the live backend) and as a dev-only assertion at the socket boundary, compiled out of release via goog.DEBUG. ~1,400 lines of TS interfaces become ~200 lines of data that also validates at runtime.

5.4 Charts — Chart.js on the hot path, free choice elsewhere

rvbbit reaches for recharts / nivo / vega-lite. Those are React+SVG and are the right call for static or low-rate visuals — but not for a 20-second rolling waveform being fed frames continuously, which is what ChannelFrameViewer and ImuViewer do. Those two keep Chart.js behind a single lifecycle wrapper (create on mount, .update with {:duration 0}, destroy on unmount). The low-rate surfaces — classification bars, feature vectors, markers, descriptor inspector — are redesigned as plain hiccup/SVG, where the rvbbit look is easiest to hit anyway.

5.5 Icons and the command palette

Inline the ~30 lucide SVG paths the editor uses into an icons map (kills a JS dep). cmdk-sv is Svelte-only; the palette becomes a ~120-line filtered list over re-pressed keybindings — the catalog it filters is already plain data. rvbbit's right-click context palette is the interaction model to copy here.

5.6 Tests — cljs.test on :node-test

Port all seven vitest suites first. Add golden-payload round-trips using real captured node_catalog / stream_graph_list JSON — the same technique already used for the C-ABI golden vectors and the marker-ABI real-payload tests.

6. Design language — rvbbit-flavored

Parity with the Svelte page is explicitly abandoned. The target is rvbbit's feel: “Part Blade Runner, part living whiteboard, part movie Hacker terminal” — a direct-manipulation canvas that reads as a game engine rather than a form. What follows is derived from rvbbit's own flow editor and board screenshots (docs/ffl.jpg, docs/sigsol.jpg, docs/rvbbit-dev-mosiac.jpg), which is fortunate: rvbbit's flow editor is a node-graph editor with ports, curved edges, an inspector panel and a transport bar — the same object as natKit's VP canvas.

6.1 Surfaces

  • Translucent dark panels over a backdrop. Near-black surfaces (rgba(10,12,20,.82)) with backdrop-filter: blur(), floated over an optional wallpaper/backdrop layer that shows through. Rounded ~10 px outer panels; small radii on inner boxes.
  • 1 px accent borders, no heavy shadows. Structure comes from thin bright lines and translucency, not elevation.
  • Nested boxes render nested data. rvbbit draws a nested structure as nested bordered cards (see the :or/:and signal editor). natKit's transform config, session protocol and train spec are all nested maps — use the same idiom instead of flat form rows.
  • Dense, low-chrome lists with a search filter at the top, value right-aligned per row, selected row boxed.
  • Tab strip across the top of a panel for the sidebar's modes (graphs / experiments / composites / profiles), active tab lighter + underlined.
  • Toast stack, bottom-right for connection events, validation results and job status — replaces today's single floating error banner.

6.2 Type

Mixed, not mono-everywhere: a geometric sans for labels, titles and prose; monospace for identifiers, values, stream ids, code and numeric readouts. Small sizes, generous line-height in lists, low-contrast secondary text. Big soft display type for the current graph's name in the canvas's top-right corner (rvbbit puts the flow name there) and for headline numbers (accuracy, frame counts).

6.3 Color — one accent per graph

rvbbit's boards each read as a single-accent scene (hot magenta, cyan, amber, purple) against near-black. Do the same: derive a per-graph accent (hashed from graph_id, overridable in graph metadata) and drive borders, port dots, selected states and the primary chart series from it. Semantic colors stay fixed so status never depends on the accent:

Adopting the rvbbit treatment makes lineage legible at a glance.

6.4 The canvas

  • Node cards: compact, translucent, 1 px accent border, monospace title, an inline value/status readout, and round port dots on the card edge. Selected = violet outline + a corner ✕. Runtime state colors the border, not a separate badge.
  • Edges: thick beziers — solid for data, dashed for provenance — with a visible glow on the running path. Chunky and high-contrast; rvbbit's edges are unmissable and natKit's currently are not.
  • Transport bar pinned to the bottom of the canvas: play / stop / clock / save / layout, matching rvbbit's flow controls. This is where natKit's start/stop and the timeline scrubber belong.
  • Right-click context palette as the primary way to add nodes, with the ⌘K palette and sidebar as secondary surfaces (all three already exist and are catalog-driven).
  • Optional backdrop layer behind the grid. Cheap to implement, and it is a large part of why rvbbit looks the way it does. Ship one tasteful default plus off.

6.5 Theme as data

rvbbit's theming is “fully data-driven — you can style or re-skin your boards on the fly, or even control the theme via the output of a query.” Implement the theme as a Clojure map in app-db, compiled to CSS by garden. That yields dark/light/high-contrast switching for free and leaves the door open to the genuinely interesting version later: a classifier's live output driving the theme, which for a biosignal tool is a real demo, not a gimmick.

Scope guard: the design system is one namespace plus a theme map, built in Phase 2 and refined thereafter. It is not a phase of its own, and it is not a component library — re-com covers layout.

8. Phases

Each phase is independently verifiable and leaves the Svelte app untouched and working. Note the verification shift: with parity abandoned, gates are behavioral and protocol-level — the strongest one (the flattened-graph JSON diff) survives intact, because it tests the thing that actually has to match.

Phase 0 — Toolchain ~½ day

  • deps.edn + shadow-cljs skeleton with re-frame/reagent/re-com/garden; dev server; nREPL; release build proves out.
  • websocket-fx connected to the live backend; get_streams → stream list in app-db, visible in the re-frame inspector.
  • Verify the auth cookie reaches the socket from a different port. Cookies are host-scoped, not port-scoped, so natkit_session set on localhost should be sent to ws://localhost:7409 from a dev server on :8280. Confirm empirically. Fallbacks: an nginx dev service, or NATKIT_AUTH_DISABLED=1 on the dev backend (an existing dev-only flag).

Exit: live stream list in app-db against the running podman stack. (The renderer spike is cancelled — §5.2 settled it.)

Phase 1 — Protocol + pure logic + the ported test suite ~1 week IN PROGRESS

  • protocol/wire, protocol/schema (malli), protocol/socket routing, protocol/ml_proxy.
  • Every pure namespace: graph/model, graph/composite, graph/starters, graph/library, graph/validate, experiment/protocol, experiment/time, stream/descriptor, stream/viewer_registry.
  • All seven vitest suites translated to cljs.test; golden payloads captured from the live backend into test/resources/.
  • No UI.

Exit: npx shadow-cljs compile test && node out/test.js green with at least the current 28 assertions' coverage; malli validates real captured node_catalog and stream_graph_list payloads; the flatten round-trip preserves editor_metadata byte-for-byte.

Phase 2 — Canvas + design system, read-only ~1.5 weeks

  • theme.cljs + garden stylesheet: the §6 surfaces, type scale, semantic colors, per-graph accent, optional backdrop.
  • Shell: sidebar tab strip with the graph list, toolbar, bottom transport bar, toast stack.
  • Canvas rendering a graph loaded from the backend: node cards with ports, thick bezier edges (solid data / dashed provenance), runtime state on the border, diagnostics.
  • Pan/zoom via react-zoom-pan-pinch; re-pollsive driving the 1 s status refresh.
  • No editing.

Exit: an existing saved graph renders with correct topology, correct per-node runtime state, and the intended aesthetic; status updates arrive live while a graph runs (started from the Svelte page or the smoke script).

Phase 3 — Editing, palette, save round-trip ~1.5 weeks

  • Selection (single + multi), node drag, delete, right-click context palette, ⌘K palette (re-pressed), catalog-driven node creation.
  • Connect with descriptor compatibility + typed rejection feedback; edge selection; edge topic badges.
  • Save / validate round-trip including editor_metadata; starter templates; undo/redo via day8 undo.

Exit: build the “Filter + envelope” starter from scratch, save, clear localStorage, reload from the backend alone, and diff the flattened graph JSON against what the Svelte editor produces for the same board — they must match. Undo restores the previous topology.

Phase 4 — Inspector + run control ~1.5 weeks

  • Inspector for every kind — source, transform (catalog config fields via the nested-card idiom, input mapping, inline node doc), combine (variadic ports), experiment (protocol authoring + schedule summary), train, classify, param, viewer, graph metadata.
  • Start / stop from the transport bar; diagnostics as toasts + inline; “recommended next” from the output descriptor.
  • Debounced config edit → restart_stream_graph_node.
  • Profiles: save / load / delete.

Exit: start a graph, edit a band-pass cutoff while running, confirm restart_stream_graph_node fires and the node returns live with the same output id and the source untouched — the existing Phase-7 acceptance, re-proven here.

Phase 5 — Live data + viewers ~1.5 weeks

  • stream/buffers: refcounted subscribe/unsubscribe, per-stream buffers, capped 200 ms flush, EMG trim-by-duration + bounded trims.
  • Descriptor-driven registry over seven renderers; the Chart.js wrapper for channel-frame + IMU; the low-rate viewers redesigned per §6; inline-on-node charts; marker overlay and the viewer's phantom markers input.
Carry the $state.raw lesson forward. The Svelte page hit a progressive stutter because deep-reactive proxies wrapped every sample read on the chart hot path; the fix was raw state plus a decoupled flush. The re-frame equivalent: sample buffers do not live in app-db — keep them in a separate atom (or plain JS arrays behind the chart wrapper) and put only a small per-stream summary/reference in app-db. A 100-frame × N-channel buffer inside a subscribed path will reintroduce the exact bug, and undo/redo would snapshot it too.

Exit: an inline viewer node plots the live EMG stream, and three inline charts open simultaneously stay responsive.

Phase 6 — Experiments, timeline, ML ~1.5 weeks

  • experiment/recorder: session id generation, start bundle, 100 ms cue tick, cue + lifecycle markers on completion/stop, via publish_session_bundle.
  • ExperimentRunner inline + modal; timeline in the transport bar with ticks/regions, playhead, speed, scrub → query_stream_time → replay start_offset.
  • Train submit through ml_proxy with thread-slot auto-pick; job status, accuracy and bundle path landing on the node; classify model dropdown from train→classify provenance edges; recorded-runs experiment library.

Exit: record a 2-class session end-to-end (one session_id, markers published), submit a train job, and see status → accuracy → bundle path appear on the train node and auto-fill the classify node.

Phase 7 — Composites + param nodes ~1 week

  • Extract from selection, instantiate, ungroup, import/export, composite internals view.
  • Param nodes with inline sliders driving a target transform's config + the reactive restart.

Exit: ported composites suite green (param nodes and provenance edges dropped by flattening), and a slider restarting a running subgraph live.

Phase 8 — Packaging + cutover ~3 days

  • Dev compose service; two-stage prod Dockerfile (node+JVM builder → nginx) reusing frontend/nginx.conf's /api + /ws proxy blocks.
  • Route the CLJS app at /vp/; point the Svelte nav's VP entry at it.
  • Retire (or flag off) the Svelte VP page; write the decision-log entry and update .claude/state.md.

Total ≈ 9–10 weeks of focused work (Phase 2 grew by ~½ week for the design system; Phase 0 shrank by ~½ day now that the renderer question is closed). Phases 0–4 (≈5.5 weeks) are the go/no-go: they deliver an authoring editor with run control, which is the load-bearing half.

9. Serving and deployment

Dev

  natkit-v0-frontend-cljs:

    command: npx shadow-cljs watch app
    ports: ["8280:8280", "8777:8777"]   # :dev-http + :nrepl
    volumes: ["./frontend-cljs:/app:Z", "natkit-v0-cljs-m2:/root/.m2", ...]

The WS base URL is configuration, not a hardcode: read from js/window.NATKIT_WS_URL (injected by a <script> in index.html) defaulting to the current same-origin derivation. In-container that is ws://natkit-v0-backend:7409; from the host during a bare shadow-cljs watch it is ws://localhost:7409, which relies on the Phase-0 cookie finding. Cache the Maven repo in a named volume so restarts don't re-resolve deps.

Prod

Two-stage: a builder image with Node + a JDK running npx shadow-cljs release app, then nginx:1.27-alpine serving resources/public with the same /api/ and /ws/ proxy blocks the Svelte app already uses. The JVM is a build-time dependency only; the shipped artifact is plain JS.

11. Open decisions

Two of the original five are now closed. Defaults in bold.

  1. CLOSED — Renderer: reagent + re-frame, mirroring rvbbit's stack (§5.2). The two-way spike is cancelled.
  2. CLOSED — Parity: abandoned in favor of an rvbbit-flavored design language (§6); behavioral and protocol gates remain.
  3. Coexistence: serve at /vp/ alongside the Svelte app vs replace / outright. The default de-risks everything else here.
  4. Theming depth: per-graph accent + one optional backdrop vs full rvbbit-style user-editable themes (vs. eventually: theme driven by a live classifier's output). Start at the default; the theme-as-data structure keeps the rest reachable.
  5. Long-term intent: is this the first step toward replacing the whole Svelte app, or permanently a VP-only app? Doesn't change Phases 0–7, but it decides whether Phase 8 invests in a shared shell, routing and nav.

12. Acceptance

The whole-plan gate, phrased as one operator run:

A user logs in, opens the ClojureScript app, sees their saved graphs, builds a source → band-pass → viewer board from the right-click palette, starts it from the transport bar, watches live data plot inline on the node, edits the cutoff and sees only that subgraph restart, records a two-class experiment against the same source, submits a training job and sees accuracy land on the train node, wires the resulting model into a classify node, runs it and sees predictions — without ever opening the Svelte VP page, and with no backend change anywhere in the diff.

Supporting gates: the ported test suite green in CI; the flattened graph JSON byte-identical to Svelte's for the same board; three inline charts responsive; a composite graph reloading from the backend alone with editor_metadata intact; undo restoring topology.

13. Smallest honest first slice

  1. Phase 0 — toolchain + cookie verification (½ day).
  2. Phase 1 — protocol + pure logic + the seven ported suites (1 week). Worth having on its own: an independently tested model of the graph, the cue engine and the descriptor rules, currently only reachable through a Svelte component.
  3. Phase 2 — the canvas and the design system, rendering a real saved graph with live runtime status (1.5 weeks). This is also the phase that answers “does it actually feel like rvbbit?” — the cheapest possible test of the aesthetic premise.

Three weeks in you have a good-looking live canvas and a tested core, plus a grounded estimate for the remaining six phases. If it looks wrong at that point, the Svelte app has not been touched.
