Explicit Train/Classify Provenance Edges

Replace the implicit, by-time-and-guesswork wiring between the EMG source, the experiment, the train node, and the classifier with explicit provenance edges on the canvas. An operator draws: source → experiment (what stream a session records), experiment → train (what sessions are available), and train → classify (pick a model from a dropdown). No more typed model paths, no more “discover the active device by scanning the live topic.” The graph itself carries the data lineage.

Design captured — ready to sequence

Why: the walk-up flow works, but the wiring is invisible and fragile

The Convention EMG Quick-Start now runs end to end — record → train → live-classify with train/serve parity proven (live accuracy matched the reported validation accuracy). But getting there exposed that the connections between the nodes are not modeled on the canvas at all; they are inferred at runtime, and that inference is brittle:

  • The train node has no idea what to train on. Runs are entered as free-text session:run selectors. The operator has to read a run id out of the Experiments library and type it.
  • The classifier's model is a pasted file path. A durable bundle path like /models/<job_id>/emg-gesture-bundle.json is auto-filled today, but there is no first-class notion of “the models this train node produced.”
  • Reconstruction guesses which EMG stream a session used. Because the experiment records empty device_ids, training scans the broker for “the one device active in the session window.” That guess is what hung the pipeline (an idle-only scan over a continuously-live topic never terminated), and it breaks outright with more than one EMG device.

Every one of those is the same missing concept: the graph does not record data lineage. This plan adds it as a distinct edge type so the source→experiment →train→classify relationships are drawn, validated, and resolved deterministically.

Already landed (the spine this builds on)

Groundwork completed while bringing the Quick-Start flow up live (branch vp-rework-phases-0-2):

  • have Self-contained emg_gesture_classify C++ transform + self-describing model bundle (windowing, DSP, feature order, rest-calibration, LDA) — train/serve parity proven live.
  • have Worker-side artifact persistence to a shared /models (:z-relabeled for SELinux); train report surfaces model_path + bundle_path + accuracy.
  • have Train submit auto-picks a compute slot; run selectors accepted as strings; recorded-run discovery skips non-session meta records and no longer scans the live topic forever.
  • tune Auto-fill of the trained bundle into the classify node + a manual per-node restart. These are the seams the provenance edges replace with a modeled connection.

The provenance-edge model

A second class of edge, visually distinct (e.g. a dashed blue line vs. solid data edges), that expresses a lineage / control relationship rather than a streaming data path. Provenance edges are persisted with the graph but are excluded from the executed data-flow — they resolve node configuration at author/submit time, not at runtime.

EdgeMeaningResolves
EMG source → experiment “This experiment records against this stream.” Stamps the source's device_id into the session bundle so reconstruction reads the right topic directly — no window-scan guessing.
experiment → train “Train on sessions from this experiment.” The train node's run picker lists exactly that experiment's recorded runs (its session_id); no typed selectors.
train → classify “Classify with a model this trainer produced.” The classify node shows a dropdown of the train node's completed models (label + accuracy + date); selecting one sets model_path to its bundle.

Optional refinement (later): the source end of the source→experiment/train edge can be a point downstream of the raw source (a band-pass output, say) to train on preprocessed data. v1 binds to the raw EMG topic, which is what the current reconstruct+featurize pipeline expects.

Phase 1 — Provenance edge primitive new

Goal

A drawable, persisted, validated edge kind that the executor ignores.

Work

  • Model: add edge_kind: "data" | "provenance" to StreamGraphEdge (default "data"; round-trips backend to_json/from_json + frontend type).
  • Execution: flattenGraph / the backend graph executor drop provenance edges from data routing (mirrors how param nodes are dropped). The executed graph stays purely data edges — zero runtime behavior change.
  • Rendering & connect rules: render provenance edges dashed/blue; provenance-typed ports only connect to provenance ports; a source's data output can originate a provenance edge (dual-purpose) or expose a dedicated provenance stub.

Acceptance

An operator can draw a provenance edge; it saves/reloads; a running data graph is unaffected.

Phase 2 — Deterministic session↔stream binding new

Goal

Kill the “guess the active device” reconstruction path by recording the real device_id on the session.

Work

  • source → experiment edge gives the experiment node the bound source(s). On Record, startSessionRecording stamps device_ids = resolved device id(s) of the bound source(s) into the session metadata + lifecycle markers (today it sends []).
  • Resolve the device_id string, not the numeric stream id: read it from the live EMG frames / stream descriptor for the bound source (the value reconstruction matches on, e.g. emg01).
  • Result: resolve_device_id takes the metadata's single device id directly — discover_device_ids_for_window (the scan that hung) is never reached, and multi-device setups become unambiguous.

Acceptance

A recorded session carries its device id; reconstruction pulls that topic without scanning to disambiguate; multiple EMG devices no longer error.

Phase 3 — experiment → train run sourcing new

Goal

The train node knows which sessions are available from its connected experiment(s).

Work

  • Train node ports: add a provenance input port that accepts experiment (and source) provenance edges. Backend catalog + validation updated (train gains input ports; still no data output).
  • Run picker filtered by lineage: the train inspector's run picker (already added) lists recorded runs whose session_id matches a connected experiment's experiment_id, instead of every run on the broker. Train/eval toggles unchanged.
  • Manual string selectors remain as an advanced fallback.

Acceptance

Wiring experiment→train scopes the run list to that experiment's sessions; picking train/eval runs needs no typing.

Phase 4 — train → classify model dropdown new

Goal

Replace the typed/auto-filled model_path with a first-class model picker.

Work

  • Per-train-node model registry: on each completed job, associate the result ({job_id, bundle_path, model_path, accuracy, family, created_at}) with the submitting train node. Store it in the train node's config / editor-metadata so it round-trips through the graph store (mirrors the composite metadata round-trip); a backend registry keyed by graph+node is the alternative if cross-session sharing is wanted.
  • Train node output port + train→classify provenance edge. Backend catalog: train gains a provenance output port.
  • Classify model dropdown: when a classify node has an inbound train→classify edge, its inspector shows a dropdown of that trainer's models (label + accuracy% + date). Selecting one writes the bundle path into config.model_path and (if running) restarts the node — exactly the auto-fill path, now explicit and re-selectable. Free-text path stays as fallback.

Acceptance

After training, the classify node offers its trainer's models in a dropdown; selecting one goes live with no pasted path; re-training adds to the list.

Phase 5 — Surface the lineage polish

Goal

Make the “what am I training on / classifying with” answer visible.

Work

  • Show on the train node: the bound source stream + experiment, and the resolved run window. On the classify node: the selected model's label + accuracy.
  • Validation diagnostics for missing/ambiguous lineage (e.g. train with no experiment edge, classify with no model selected).

Acceptance

An operator can read, from the canvas, which stream and sessions feed training and which model the classifier uses.

Risks & open questions

  • Edge duality: does a provenance edge start from a node's existing data-output port (overloaded) or a dedicated provenance stub? A dedicated stub is cleaner to validate but adds port clutter. Lean: dedicated provenance ports on train/classify; the source end taps the data-output port.
  • device_id resolution: the frontend must map a bound source to the EMG frame device_id string (not the stable numeric stream id). Confirm it is available client-side (stream descriptor / a sampled live frame) before Phase 2.
  • Model registry home: train-node config (simple, per-graph, round-trips) vs. a backend store (shareable across graphs, survives node deletion). v1 = node config; promote to a store only if needed.
  • Backward compatibility: keep the manual model_path and string run selectors working; provenance edges are additive, not required.
  • Non-goals (v1): training on preprocessed (non-raw) stream taps; cross-train-node model sharing; provenance edges for non-ML nodes.

Suggested sequencing

1 (edge primitive) first — everything else hangs off it. 2 (device binding) next: highest correctness value, it removes the reconstruction fragility that caused real hangs. 3 and 4 are the productization the operator sees (scoped run picker, model dropdown) and can land in either order once the edge + ports exist. 5 is polish that closes the “invisible wiring” complaint. Phases 1–2 touch the backend (edge kind, executor exclusion, catalog ports, session device stamping); 3–5 are mostly frontend on top.

Adjacent follow-ups (not this feature, but flagged)

  • Reconstruction performance: even bounded, reconstruction scans the live EMG topic from the beginning. A seek-by-timestamp (Kafka offsets_for_times) path would jump straight to the session window. Big win for the live flow; independent of provenance edges.
  • Make the dev-stack fixes permanent: rebuild control-plane + worker so the :z /models mount, worker artifact persistence, and run-selector fixes are baked into images (they are committed but were hot-patched into running containers). Sort out ml-worker-a's auth (401) or leave it off — the in-process worker suffices for a single-person booth.
