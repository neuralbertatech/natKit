Experiments, Instances & Immutable History

Stop treating an experiment as a node on the canvas. Make it a first-class object that owns a graph and a history. Every recording produces an instance: a permanent, immutable snapshot of the graph as it was, welded to the data and markers captured during that run. Instances are reviewable forever, and forkable into editable copies so you can re-analyse old data with a different pipeline — all nested under the experiment that produced them.

Status: PLAN — decisions locked, Phase 0 in progress

The shape of it

Experiment "finger-counting"          <- owns protocol, participant, notes
├── live graph  (editable, the one you record with)
├── instance 0001   2026-07-29 08:48   [IMMUTABLE]   from: recording
│     ├── graph snapshot (as recorded)
│     ├── data: imu.parquet  markers: markers.jsonl     <- materialized, read-only
│     └── instance 0001-a  "higher band-pass"  [editable]  from: fork of 0001
│            └── instance 0001-a-1 "…and RMS"  [editable]  from: fork of 0001-a
└── instance 0002   2026-07-29 09:31   [IMMUTABLE]   from: recording

Two object kinds, not three. A fork is not a different animal from an instance — it is an instance that happens to be editable. Same record shape, same place in the tree, same data. Only two things differ: immutable, and whether it was born from a recording or from a fork. So there is an experiment, and there are instances; recordings mint immutable ones, forking mints editable ones, and forks nest under whatever they were forked from.

Consequence worth stating: a fork references its ancestor recording's data rather than copying it. Same session_id, same window, same Parquet paths. The artifacts are already immutable and read-only, so sharing them is safe, and forking stays free no matter how large the recording was. A fork changes the pipeline, never the data.

The hard part: “permanent” means the data must leave Kafka

Everything else here is bookkeeping. This is the part that decides whether the feature is real.

Today a recording publishes markers and metadata (publish_session_bundle → Marker/<session_id> + Meta/<session_id>) and leaves the data wherever it already was — in Kafka, under retention. A “permanent historical snapshot” backed by Kafka topics is not permanent; it silently becomes an empty snapshot when retention rolls or the broker is recreated. We have already lost topics twice this week: once to a podman-compose up --build (Kafka's KAFKA_LOG_DIRS lives in the container filesystem), and the IMU topic currently holds ~930k records with no durability guarantee at all.

So creating an instance must materialize the data — and we just built exactly the right tool. ParquetExport.cpp already drains a session window, projects any sensor through the shared channel-frame projection, joins cue labels via assignIntervalsToTimeline, and writes Parquet. Instance materialization is that worker pointed at a durable directory instead of an HTTP response. foundation exists

Corollary, learned the hard way today: materialization must verify it captured something. A recording ran for 65s against a bridge that had silently stopped forwarding to Kafka 10 hours earlier, and produced a session with zero data frames. An instance that materializes to nothing must be marked failed and say why — never sealed as an immutable snapshot of nothing.

Data model

Experiment — a new stored entity

New store experiments.json behind NATKIT_EXPERIMENT_STORE, mirroring the existing stream_graphs.json / profiles.json pattern (NATKIT_STREAM_GRAPH_STORE, NATKIT_PROFILE_STORE) so persistence is a known quantity. 

{
  "experiment_id": "finger-counting-1785336502546",
  "label": "Finger counting",
  "protocol": { …SessionProtocol… },     // moved off the node's config
  "participant_id": "p01",
  "notes": "",
  "live_graph_id": "board-7",            // the editable graph you record with
  "created_at_us": …, "updated_at_us": …
}

Instances and forks are just graphs, with provenance

Deliberately not a second graph store. An instance's snapshot and a fork are both StreamGraphDefinitions, so they inherit save / load / validate / start / editor_metadata round-tripping for free. They gain fields:

FieldMeaning
experiment_idWhich experiment this graph belongs to. Present on the live graph, instances, and forks — this is what makes the tree.
instance_idSet on every instance, recorded or forked (…/run-0001, …/run-0001-a). Absent only on the live graph.
immutabletrue for recordings, false for forks. The only behavioural difference between them. Backend refuses to overwrite when true.
origin"recording" | "fork" — provenance, and what the tree icon shows.
forked_from{instance_id} of the parent, for fork-of-fork nesting. Null on recordings.
recordingThe captured session: session_id, window, recorded stream list, artifact refs, status. Inherited verbatim by forks — a fork points at the same materialized files.

Because instances live in the graph store, list_stream_graphs would start returning every snapshot. The board picker must filter to instance_id == null && forked_from == null; instances and forks are reached through the experiment tree, not the board list. 

"recording": {
  "session_id": "finger-counting-1785336502546",
  "window_start_us": 1785336527253000,
  "window_end_us":   1785336592254000,
  "streams": [ {"stream_id": "13793649670644", "schema_name": "NatImuBulkDataSchema", "role": "source"} ],
  "artifacts": {
    "markers": "markers.jsonl",
    "data": [ {"stream_id": "13793649670644", "path": "imu.parquet", "rows": 1575, "sha256": "…"} ]
  },

}

If the experiment isn't a node, where do markers come from?

This is the design question that decides how invasive the change is. Markers are wired data today: the experiment node's markers output feeds the marker viewer overlay, topic-aware combine's marker lane, and the export node's label join. Deleting the node without a replacement breaks all three.

Proposal: keep a lightweight markers source node, move the definition off the canvas. The node has no protocol config — it resolves its topic from the graph's bound experiment_id (Marker/<experiment_id>, exactly as the experiment node's output does today). Wiring stays identical; what leaves the canvas is protocol authoring, participant, notes and the Record button, which move to experiment-level UI.

Consequence to accept explicitly: the provenance edges from vp-provenance-edges-plan.html partially collapse. prov_source (source→experiment) becomes meaningless — the experiment now owns the whole graph, so every source in it is a recorded source. prov_experiment (experiment→train) is replaced by something better: a train node points at instances, which are concrete datasets with materialized files, instead of at run-selector strings. That's a net simplification, but it is a reversal of a recent deliberate design and should be a conscious decision, not a side effect.

Immutability: where it is enforced

  • Backend is the authority. handleSaveStreamGraph currently accepts any save (drafts may be invalid by design). Add: if the stored graph for this id has immutable: true, reject with a diagnostic immutable_graph whose message names the fork action. Enforcing in the UI alone is not enough — the WS protocol is a public surface.
  • Watch the reactive auto-save. Phase 7's incremental reactivity debounces a config edit into saveDraftGraph + restart_stream_graph_node. On an immutable graph that would fire a save on every keystroke and spray rejections. The editor must make an instance genuinely read-only (inputs disabled, drag/connect suppressed), not merely warn after the fact.
  • New action fork_stream_graph {source_graph_id, label?} → a new editable graph with forked_from and the same experiment_id, and immutable: false. Server-side so id generation and provenance rules live in one place.
  • Artifacts are immutable too. A snapshot whose Parquet can be overwritten isn't a snapshot. Write artifacts once, then chmod read-only and record a sha256 so tampering or truncation is detectable at review time.

Parquet is the stored form; replay streams out of it

DECIDED. An instance's data lives as Parquet, and replaying an instance means streaming records back out of those files. No Kafka time-travel: the snapshot is self-contained, so an instance recorded a year ago replays identically to one recorded a minute ago, and retention stops being part of the story.

Where the replayed records go

The one real constraint: the browser's subscribe path binds Kafka messengers (broker_manager_->createMessenger(topic, start_offset)). The in-process transport exists, and createInProcessMessenger is explicitly “a drop-in for BrokerManager::createMessenger” — but it is used for private colocated edges, i.e. exactly the edges nobody is watching. A viewer forces Kafka.

So replay publishes into a scratch Kafka topic per replay session (short retention, deleted when the replay ends). Everything downstream — transform workers, viewers, topic-aware combine, the marker overlay, even Parquet export of the replayed result — then works with zero changes, because from the graph's point of view it is just another live stream. Permanent data on disk, ephemeral data on the wire.

In-process replay stays available as a later optimization for headless recompute (train a model over a snapshot, no viewers attached), where skipping the broker is pure win. Not the default, because the common case is a human watching.

A pleasant side effect: replay is more compatible than live

The Parquet is the canonical channel-frame projection — that is what the exporter writes. So replay can emit NatSignalFrameDataSchemaV1 regardless of what the original sensor published, and a fork's transforms bind to it directly. The IMU needs the natimu_motion_v1 alternate input mapping to be filterable live; replayed from Parquet it needs nothing. Forks are strictly easier to wire than live boards.

Two replay modes

ModePacingFor
ReviewWall-clock paced from device_ts_us deltas, with a speed multiplier (0.25×–8×) and scrubWatching the recording play back through viewers, like a video.
RecomputeUnpaced — as fast as the pipeline drainsRunning a fork's changed pipeline to get a result, or training. Nobody is watching frames go by.

natVR/src/natvr/replay.py already has the pacing shape (replay_intervals(frames, speed)) as a reference, but the implementation belongs in C++ alongside the writer — the Arrow reader comes free with the libparquet we already link.

Non-negotiables

  • Preserve device_ts_us. Never restamp to now. The cue-label join is a timestamp interval join; restamping silently destroys every label, and it would also desynchronise two streams replayed together.
  • Replay markers too, interleaved by timestamp from the .markers.jsonl sidecar onto the scratch marker topic. Otherwise the marker overlay is blank, combine's marker lane is empty, and a re-export of the fork's output comes back unlabelled.
  • Reset stateful transforms at replay start. IIR filters, envelope followers and vote windows carry state; replaying the same instance twice through the same graph must give the same answer, or forks aren't comparable — which is the entire point of forking.
  • Multi-stream replay shares one clock. Two sources recorded together must replay together, ordered by timestamp across files, not file-by-file.

Small gap to close first

The exporter's Parquet metadata currently records natkit.stream_id, session_id, channel_labels, marker_count and the window — but not the original schema_name. Replay does not strictly need it (it emits the canonical frame), but provenance does: without it a snapshot can't say what sensor it came from. One line in ParquetExport.cpp.

Phases

Ordered so each phase leaves the system working, per the house style.

Phase 0 — Model + immutability, no UI change foundation

Add the graph fields (experiment_id, instance_id, immutable, forked_from, recording) as optional and round-tripped. Add experiments.json + list/save/delete_experiment. Add the immutable-save rejection and fork_stream_graph. Verifiable entirely over the WS protocol with the smoke script — no frontend work yet.

Phase 1 — Experiment replaces the node

Experiment-level UI: bind an experiment to a board, author the protocol there, Record from the board header. Introduce the config-less markers source node. Retire experiment from the node catalog. Migration: keep parsing kind:"experiment" (the session→experiment alias in normalizeGraphNode is the precedent) and offer a one-click convert that lifts the node's protocol into an experiment record and swaps the node for a markers source.

Phase 2 — Recording creates an instance

On Record: allocate instance_id, snapshot the graph (flattened + editor_metadata), publish markers as today, and write the instance with status: "recording". On stop, transition to materializing.

Phase 3 — Durable materialization

Reuse exportStreamToParquet per recorded stream, writing into NATKIT_INSTANCE_STORE (a named volume, plus a host bind mount in the dev compose so snapshots survive container recreation). Verify non-empty, checksum, mark read-only, then status: "complete" — or failed with the exporter's own diagnostic, which is already written for humans.

Phase 4 — History tree + instance review

Sidebar tree: Experiment → instances → forks. Opening an instance loads a read-only board with an IMMUTABLE badge, the recorded window, label histogram and artifact list, plus a Fork to edit button. Data review can start with what exists: the Parquet download endpoint, and the marker/label summary already computed during materialization.

Phase 5 — Replay: stream a snapshot back out of Parquet

C++ ReplaySource: read the instance's Parquet via Arrow, rebuild canonical channel frames, interleave the markers sidecar by timestamp, publish to a scratch Kafka topic, and bind the instance's source nodes to it. Review mode (paced + speed) and recompute mode (unpaced). Reset stateful transforms on start. Delete the scratch topic when the replay ends.

Phase 6 — Train from instances

Replace the train node's "session:run" selector strings with instance references. Instances are strictly better training inputs: fixed windows, materialized files, a recorded label histogram, and provenance back to the exact graph that produced them.

Decisions — and what is still open

  • Which streams get materialized? DECIDED: raw sources only — every stream_source in the graph, no transform outputs. Keeps snapshots small and lets a fork legitimately recompute differently, which is the whole point of forking; snapshotting derived streams would also let a fork silently read stale derived data. A per-source opt-out can come later if a board pulls in a high-rate stream nobody cares about.
  • Storage budget and retention for instances. These are permanent by design, so they only grow. The live IMU stream alone is ~2.3 MB per 30s of Parquet. Do instances need a size cap, a prune/archive command, or an explicit delete (which contradicts “permanent”)?
  • Does a fork's own run produce a new instance? DECIDED: no. Forking is what mints a new instance; running one just executes it. A fork already is an instance (editable), so a run needs no new object — the lineage lives in forked_from.
  • Is the live graph owned by one experiment, or shared? “Associate an experiment with that graph” reads as 1:1. But a board you want to use for two different protocols would then need duplicating. 1:1 is simpler and matches your phrasing; I'd start there.
  • Provenance edges. DECIDED: retire them. prov_source / prov_experiment existed to tie a source to an experiment; experiment-owns-the-graph expresses the same lineage implicitly and more cleanly. Both stubs come out of the catalog and port normalization.

Risks

  • Silently empty snapshots. Already happened once this week for unrelated reasons (a wedged bridge). Materialization must fail loudly, and the recording UI should surface “frames seen” live so a dead pipeline is obvious during the run, not discovered afterwards.
  • Kafka is not durable here. KAFKA_LOG_DIRS=/tmp/kraft-storage is inside the container: any up --build destroys every topic. Until materialization exists, a “permanent” instance is a lie. Worth fixing the volume regardless of this plan.
  • Graph-store growth. Instances and forks share stream_graphs.json. A flat JSON file re-serialized on every save will not love hundreds of snapshots; watch for a store split or an index if it bites.
  • Immutability has many back doors. Save, reactive auto-save, node restart, composite flatten-on-save, starter-template load. Each is a path that can mutate a graph; the read-only mode has to cover all of them, and the backend rejection is the backstop.
  • Migration blast radius. The experiment node is referenced by the editor inspector, ExperimentRunner.svelte, inline-card rendering, the client recorder, topic-aware combine's marker classification, the starter templates, the node catalog, and the smoke script. All must move together or the intermediate states break the board.
