Visual Programming Rework: a Sensor-Agnostic Reactive Canvas

Turn the current EMG-centric stream-graph editor into an RVBBIT-style reactive canvas where a non-programmer can drop any sensor stream onto a board, process it, visualize it, and train/run ML classifiers on it — all without touching code, and without the system being wired to the EXG Pill. The graph engine, composites, descriptor system, transform workers, and an ML control plane already exist; this plan collapses the hard-coded EMG paths onto those generic seams and closes the missing pieces (data-driven node catalog, descriptor-driven viewers, first-class sessions, ML-as-nodes, script nodes, reactive execution).

Supersedes/extends: stream-graph-programming-plan.html, worker-node-processing-plan.html, frontend-ml-pipeline-plan.html, descriptor-transform-plan.html. Touches frontend/, libnatkit/ (backend + core submodules), and natVR/.

Decision

  • Do not rebuild — generalize. The node graph, composites, the self-describing DataSchemaDescriptor, the canonical NatSignalFrameDataSchemaV1 channel frame, transform-capability negotiation, and the Python train/validate control plane all exist. The clunkiness is EMG hard-coding layered on top of generic machinery. We remove the hard-coded layer.
  • One canvas, everything is a node. Merge the three fragmented surfaces (StreamViewer, VisualProgramming, MlPipeline) into a single reactive board. Sources, transforms, viewers, sessions, trainers, and classifiers are all node kinds.
  • The descriptor is the only sensor contract. A sensor is data: a schema + descriptor + optional input mapping, registered at runtime. Kill the closed "imu"|"muse"|"emg" enum and the dynamic_cast dispatch chain.
  • The node catalog is data, not code. The backend advertises every node type (config schema + typed ports) and the frontend renders purely from that catalog. Adding a node type must not require editing a TypeScript union.
  • Script/worker nodes are the extensibility escape hatch. Hot-path DSP stays compiled C++; arbitrary user processing runs as Python worker nodes on the existing control-plane/worker infrastructure.
  • Structured training sessions become first-class. Generalize the EMG gesture experiment into a configurable protocol (cues, labels, runs) that produces labeled datasets for any classification task, and a train node + classify node that live on the canvas.

Why This Exists

Current state

  • Three separate pages, three WebSocket connections, three mental models: live viewing (/ws/stream_viewer), graph editing (same WS, different actions), and ML jobs (a direct WS to the control plane on :8786).
  • Everything assumes multi-channel EMG from the EXG Pill: viewer selection, feature families, experiment cues, field selection, config/action naming.
  • Adding a transform means editing a 6,600-line C++ file and a TypeScript union; adding a sensor means a new schema class, a dynamic_cast branch, a bespoke JSON formatter, and a new wire message type.

Target state

  • A non-programmer opens one board, drags a stream (any sensor) onto it, and builds a pipeline from a searchable node palette.
  • Viewers, transforms, and ML nodes are chosen and rendered from a runtime catalog + the stream's own descriptor — nothing is hard-coded to a sensor.
  • Recording a structured session, training a model, and running live classification are all nodes on the same board, sharing lineage and provenance.

Constraints (unchanged natKit rules)

  • Derived data becomes new immutable Kafka channels with descriptors + provenance (TransformProvenanceRecord).
  • The hot path stays in C++ / the transform worker; reactivity and catalog logic must not move DSP into JS.
  • Saved graphs (data/stream_graphs.json) must keep loading; migrations are additive.
  • Auth stays on the shared auth store (backend + control plane already share it).

Design Principles (RVBBIT, adapted)

RVBBIT ideanatKit adaptation
One infinite canvas; everything is a block One board holds sources, transforms, viewers, sessions, trainers, classifiers, and param/input nodes. No separate "viewer page" vs "graph page" vs "ML page".
Reactive dataflow — change an upstream value, downstream recomputes Editing a node's config live-restarts only the affected subgraph; run-state and live values are visible on the node, not on a separate screen.
Everything is a self-describing value Every port carries a DataSchemaDescriptor. Type compatibility, viewer choice, and field pickers all derive from the descriptor — never from a sensor name.
Multiple runners (SQL / Clojure / Python / shell) Runner kinds: compiled C++ DSP (hot path), Python worker/script node (custom code), and ML control-plane jobs. A node declares its runner; the canvas doesn't care.
Inspectable generated logic Any node exposes its resolved config, output stream id, descriptor, and provenance. Composites can be opened read-only (already built).
Screens / dashboards composed from blocks Viewer nodes are the dashboard: pin them, arrange them, and a board doubles as a live monitoring view.
Solvers / parameters as first-class reactive inputs Param/input nodes (sliders, dropdowns, thresholds) feed transform configs so a user can tune a pipeline live without opening inspectors.

Reference: https://github.com/ryrobes/rvbbit

Target Architecture

1 · Unified reactive canvas

Fold StreamViewer and MlPipeline into the VisualProgramming board. Live viewing becomes viewer nodes rendering on the canvas; ML becomes trainer/classifier nodes. A single StreamViewerWebSocket connection carries stream data, graph control, and (proxied or co-located) ML job control, so there is one connection model instead of three.

2 · Universal node model

Replace the closed NodeKind union with an open, catalog-driven node_type string. A node is { node_type, config, input_ports[], output_ports[] }; each port is typed by a descriptor. The frontend holds zero hard-coded node knowledge — it renders from the catalog.

3 · Node Catalog service

Generalize buildTransformCapabilitiesJson() into a full node catalog: for every node type, advertise label, category, runner, typed config fields (already supported), and input/output port descriptors. Sources, viewers, sinks, and ML nodes all appear here. The palette is built from it.

4 · Descriptor-driven viewers

A viewer registry maps descriptor capabilities → renderer: numeric channel frame → waveform (EmgViewer, renamed ChannelFrameViewer); feature vector (samples≤1 && channels>1) → bars/heatmap; scalar+label → classification readout; fallback → the generic SchemaDescriptorInspector. Delete inferStreamType() and the sensor-name ladder.

5 · Sensor onboarding = data

Replace the dynamic_cast dispatch chain with a descriptor-driven formatter: any record whose descriptor matches the channel-frame contract emits one generic frame message; anything else is emitted generically from its descriptor. A new sensor = register schema + descriptor (+ optional input mapping made data-driven, not a static C++ list). No per-sensor branches.

6 · First-class Sessions

A session/experiment node captures a structured protocol (ordered cues, per-cue labels, run count, participant/protocol metadata) and emits markers + a labeled-dataset handle. Generalizes EmgExperiment/experiment.ts so any classification task (not just gestures) can be recorded.

7 · ML nodes

train node wraps a control-plane train_validate job (families/features/label source all generic, fed by field selection over the descriptor). Its output is a model artifact — a first-class canvas object. classify node consumes a model artifact + a live frame and emits predictions, backed by the existing lda_classify path generalized beyond LDA.

8 · Script / worker nodes

A script node runs user Python on frames via the worker (per worker-node-processing-plan). Input and output are channel frames or descriptor-typed records, so a custom node is a first-class citizen. This is how users add "all sorts of processing" without a C++ recompile.

Phased Roadmap

Ordered so that each phase ships independently and de-risks the next. Phases 0–3 remove the EMG hard-coding and unify the surface (the bulk of the "clunky" complaint); 4–6 add the new capabilities; 7–8 are polish and UX.

0 De-EMG the seams low risk, high leverage

Goal: remove sensor-name coupling without changing behavior, so later phases have generic seams to build on.

  • Rename the EMG-specific identifiers to generic ones behind aliases already in place: create_emg_transform→create_transform (aliases exist), EmgTransformConfig→TransformConfig, EmgViewer→ChannelFrameViewer, NATKIT_EMG_TRANSFORM_THREADS→NATKIT_TRANSFORM_THREADS.
  • Replace inferStreamType()'s "imu"|"muse"|"emg" enum + schema-name matching with a capability probe over the descriptor (Phase 2 consumes this).
  • Make MlPipeline/fieldSelection.ts descriptor-generic (walk any channels[].samples, not EmgDataMessage).

Files: StreamViewer/types.ts, page.svelte, StreamViewerWebSocket.cpp (config struct/env), MlPipeline/fieldSelection.ts.

Acceptance: npm run check + ctest green; existing graphs still load and run; grep shows no "emg"-keyed control flow outside genuinely EMG-only viewers.

1 Node Catalog service + data-driven node rendering

Goal: the frontend renders any node type from a backend catalog; adding a node type never touches a TS union.

  • Extend buildTransformCapabilitiesJson() into a list_node_catalog action returning every node type: category, runner, typed config_fields (reuse existing typed-field machinery), and input/output port descriptor templates.
  • Change NodeKind from a closed union to an open node_type: string; keep the coarse structural kinds (source/transform/viewer/sink) only where the runtime genuinely needs them.
  • Build the palette and node inspector generically from the catalog (the config-field renderer in EmgTransforms.svelte already does this — lift it into a shared component).

Acceptance: add a new transform in C++ only (no TS edit) and it appears in the palette with a working config form; smoke script still passes.

2 Descriptor-driven viewers, on-canvas

Goal: viewers are nodes chosen by descriptor capability, rendering live data on the board.

  • Build a viewer registry: capability(descriptor) → renderer. Ship channel-frame waveform, feature-vector (bars + heatmap), classification readout, and the generic inspector fallback.
  • Make viewers node kinds that subscribe to their upstream node's output stream and render inline (a compact preview on the node, an expandable full view).
  • Retire the page.svelte viewer ladder and the per-sensor inline IMU markup; MuseViewer/FeatureVectorViewer stay as capability-matched renderers, not sensor-matched.

Acceptance: an IMU stream and an EMG stream each auto-pick a sensible viewer with no sensor-name branch; the old StreamViewer page is reproducible as a board of viewer nodes.

3 Sensor onboarding pipeline

Goal: a new sensor is registered as data, not code.

  • Replace the backend dynamic_cast dispatch (~cpp:5887) with a descriptor-driven formatter: channel-frame-shaped records → one generic frame message; everything else → generic descriptor-projected JSON. Collapse the per-sensor *_data wire messages to one generic frame/record message (keep old types as compatibility aliases for one release).
  • Make alternate input mappings (getAlternateTransformInputMappings()) data-driven/registrable rather than a static C++ list, so mapping a new sensor's fields onto the channel-frame contract is config.
  • Document a "sensor onboarding" checklist: publish schema + register descriptor (+ optional mapping) → it appears as a source, gets a viewer, and is transform-compatible automatically.

Acceptance: onboard a synthetic new sensor (e.g. a 3-axis force plate) end-to-end with no C++ dispatch/formatter edits; it plots and can be band-passed.

4 First-class Sessions / Experiments

Goal: record structured, labeled data for any classification task, not just EMG gestures — including multiple sensors synchronized under one protocol (decision #5, in scope).

  • Define a generic SessionProtocol (ordered cues, per-cue label, hold/rest durations, run count, participant/protocol metadata) — generalize experiment.ts + cues.py.
  • Multi-sensor sessions: a session node subscribes to N source nodes and records all of them under one marker timeline (e.g. EMG + IMU together). The labeled dataset references every recorded stream keyed by the shared session_id/run_index, with one label column from the cue timeline — so a train node can later select fields across sensors. Timestamp alignment rides the existing ntp/device-timestamp machinery; markers are the single synchronization spine.
  • Add a session node: runs a protocol, emits markers to Kafka, and produces a labeled-dataset handle (a named set of recorded runs across its subscribed streams, with a label column) that a train node can consume.
  • Make "training session" a first-class stored object (not just marker-delimited runs discovered post hoc), keyed by protocol + participant, discoverable in the palette.

Acceptance: author a 3-class protocol in the UI, record runs capturing two sensors at once (e.g. EMG + IMU), and see a single labeled dataset spanning both, ready to train.

5 ML nodes on the canvas

Goal: train and classify are nodes; models are canvas objects; MlPipeline page dissolves into the board.

  • train node: config = labeled dataset + families (MODEL_FAMILIES, generic) + feature set + windowing + field selection (descriptor-driven). Submits a control-plane train_validate job; shows live job state on the node; output = a model artifact object.
  • Generalize the feature layer: expose features.py as a selectable feature set (Hudgins today) and allow a script-node feature extractor later; make the label source generic (from the session dataset), not gesture-specific.
  • Support cross-sensor field selection so a model can train on features from a multi-sensor session dataset (Phase 4), not a single stream.
  • classify node: consumes a model artifact + a live/derived frame, emits predictions + confidence; backed by generalizing lda_classify to a model-family-aware inference transform.
  • Full unification (decision #3): proxy the control-plane protocol through the single backend /ws/stream_viewer connection so the frontend speaks to exactly one endpoint. The MlControlPlaneWebSocket on :8786 is dropped from the browser; the backend becomes the sole client of the control plane. This is the firm target, not the two-connection fallback.

Acceptance: record → train → drop the resulting model into a classify node → see live predictions, entirely on one board; works for a non-gesture task.

6 Script / worker nodes deferred (decision #2)

Goal: users add arbitrary processing without a C++ recompile. Deferred until later — the sandbox is out of scope for now, so this phase is sequenced after Phases 7–8 and gated on a separate security review. Everything before it stands on its own without it.

  • Implement the worker-node-processing-plan: a script node whose Python body transforms an input channel frame / descriptor record into an output frame, executed on a worker thread slot.
  • Declare input/output descriptors so script nodes compose with everything else and get viewers for free.
  • Sandboxing + resource limits + auth scoping are a hard requirement and the reason this is deferred — treat as a security-reviewed sub-project when picked up. Until then, extensibility for v1 is data-driven config over the compiled C++ transform catalog (decision #5).

Acceptance (when eventually built): a user writes a 10-line Python node computing a custom feature and wires it into a pipeline that then trains a classifier.

7 Reactive execution + composite round-trip

Goal: the board feels live, and composites survive a backend save.

  • Incremental reactivity (decision #1): a config change restarts only the affected downstream subgraph; per-node live state + a sampled live value render on the node. Debounce edits, and keep an explicit "run" gate for expensive ML nodes. (Not full spreadsheet-style recompute-on-every-keystroke.)
  • Composite round-trip (decision #4, chosen: minimal backend awareness): the backend stores the composite tree as opaque metadata alongside the flattened graph, so a saved graph round-trips from the backend alone without the frontend-only flattenGraph being the sole source of truth. The backend still executes the flattened primitives — it does not need to understand composite semantics, only to persist and return the tree.
  • Add param/input nodes (slider/dropdown/threshold) that feed transform configs reactively.

Acceptance: dragging a cutoff-frequency slider visibly changes a downstream plot without a manual stop/start; reloading a saved composite graph from the backend alone reproduces it.

8 Beginner UX & libraries

Goal: a non-programmer succeeds without a manual.

  • Ship a starter template library (composites already support this): "view a stream", "filter + envelope", "record a session", "train a 2-class model", "run live classification".
  • Guided flows / recommended next nodes derived from the current node's output descriptor (the stream-graph-programming-plan's "recommended next transforms" idea).
  • Inline docs from catalog metadata (config field descriptions, units) and clear invalid-connection feedback typed by descriptor compatibility.

Acceptance: a first-time user follows a template to a live classifier without reading code or docs.

Cross-Cutting Concerns

  • Backward compatibility. data/stream_graphs.json and saved composites must keep loading. The NodeKind→node_type change and message-type collapse need a migration + a compatibility window where old aliases still resolve.
  • Performance. Reactivity and catalog logic live in JS/orchestration; DSP stays in the C++ worker. Incremental restart must not thrash the hot path — debounce config edits.
  • Security (script nodes). Arbitrary Python execution is the highest-risk item; it needs sandboxing, resource limits, and auth scoping before it ships. Gate behind the shared auth store and admin-owned compute pools (ADR-004).
  • Three→one connection. Proxying control-plane traffic through the backend WS is a real refactor, and it is the committed target (decision #3) — no two-connection fallback. Landed in Phase 5; the backend gains a control-plane client and re-broadcasts job state over /ws/stream_viewer.
  • Testing. Keep the parity guarantees: vitest for frontend pure helpers (composites.test.ts pattern), ctest for core, natVR pytest for ML, and extend libnatkit/scripts/natkit_stream_graph_smoke.py to cover new node kinds end-to-end.

Resolved Decisions (confirmed July 8 2026)

  1. Reactivity: incremental. Config change restarts only the affected downstream subgraph, with an explicit run gate for expensive ML nodes. Not full recompute-on-every-edit. → drives Phase 7.
  2. Script-node sandbox: deferred. Script/worker nodes (Phase 6) move to the end, gated on a separate security review. v1 extensibility is data-driven config over the compiled C++ transform catalog.
  3. Unification: full. Collapse to one board and one WebSocket — proxy the control-plane protocol through the backend /ws/stream_viewer; drop the browser's direct :8786 connection. → firms Phase 5.
  4. Composites: minimal backend awareness. Store the composite tree as opaque metadata alongside the flattened graph so it round-trips from the backend alone; the backend still executes only the flattened primitives. → drives Phase 7.
  5. Catalog ceiling: config-driven for v1. C++ transform impls stay; adding a transform is data (catalog + config). A compiled-transform plugin ABI is deferred alongside script nodes.
  6. Sessions: multi-sensor in scope. A session records N synchronized sensors under one protocol and marker timeline, producing one cross-sensor labeled dataset. → expands Phase 4 and Phase 5 field selection.

Suggested Sequencing & First Slice

Phases 0–2 deliver most of the felt improvement (de-EMG'd, one canvas, viewers that work for any sensor) and are low-risk because they ride existing machinery. A concrete first slice to validate the whole direction:

  1. Phase 0 renames + kill inferStreamType (behavior-preserving).
  2. Phase 1 list_node_catalog + generic palette/inspector.
  3. Phase 2 viewer registry with two renderers (channel-frame + inspector fallback), rendered on-canvas.
  4. Demo: drop an IMU stream and an EMG stream on one board; both plot; both accept a band-pass transform; nothing in the path names a sensor.

That slice proves the descriptor spine carries the whole system, after which Sessions → ML nodes → script nodes are additive.
