In-Process Transport for Colocated Graph Edges

Add an in-process message-queue transport for graph edges whose endpoints are provably colocated, selected by the scheduler, behind the existing messenger interface. Realizes the boundary defined in ADR 005 and honors the worker-node direction in ADR 001.

Phases 0–4 implemented (static: builds + gtest) · Phase 5 tie-in staged behind the colocation proof

Implementation Principle

  • Keep transport choice orthogonal to correctness. Startup and topic resolution must never depend on which transport an edge uses.
  • Choose transport by provable colocation decided by the scheduler, never by composite membership (ADR 005).
  • Reuse the existing MessagingQueue / TopicMessenger interface. An in-process edge is a second MessagingQueue implementation, not a new abstraction bolted alongside Kafka.
  • Default to Kafka. An edge earns the in-process path only by proving it is safe; when in doubt, stay on Kafka.
  • Any edge that is exposed as a composite port, tapped by a viewer/sink, or recorded/replayed by a session/train node is published and must be on Kafka.

Phase 0 — Decouple intra-graph resolution from Kafka discovery

Done. This removes the chained-transform startup race independently of transport, so later phases are a pure optimization rather than a correctness fix.

  • Implemented: findGraphInternalOutputTopicForStream in StreamViewerWebSocket.cpp resolves an upstream transform/combine node's deterministic output topic from the in-process worker registries when Kafka broker metadata does not yet list it.
  • Implemented: createTransformWorker and createCombineWorker fall back to that resolver before failing; Kafka discovery remains the path for hardware stream_source inputs.
  • Implemented: getOutputTopicInfo() accessors on the transform and combine worker classes.
  • Implemented: the resolution decision is extracted into a pure, dependency-injected helper (nat::tools::resolveGraphSourceTopic in tools/.../GraphTopicResolution.hpp), which createTransformWorker/createCombineWorker route through and which createTopicInfo shares for deterministic topic identity.
  • Implemented: gtest regression coverage (libnatkit-tools-unittest-cxx, GraphTopicResolutionTest.cpp) — the first backend test target — asserting deterministic output-topic identity and that resolution falls back to the graph-internal topic when broker discovery has not yet materialized it.
  • Remaining: nothing for correctness. A full end-to-end test that starts a deep chained pipeline against a live broker would additionally cover worker wiring, but requires broker test infrastructure that does not yet exist.

Phase 1 — In-process MessagingQueue implementation

Implemented. nat::tools::InProcessMessagingQueue (implements core::MessagingQueue) + InProcessChannel/InProcessChannelRegistry and a createInProcessMessenger factory in tools/…/InProcessTransport.{hpp,cpp}. Channels are keyed by stableStreamId (== topic id) so a producer and its consumers rendezvous without a broker; frames cross as reference-counted message_t handles (no broker round-trip). Single-producer / multi-consumer fan-out with per-subscriber FIFO slots. gtest InProcessTransportTest.cpp covers produce/consume ordering, fan-out (shared handle), drop-oldest bounding, block+close, teardown, and a full round-trip of a real schema through the TopicMessenger+Registry path a worker uses.

Introduce a same-process transport behind the existing interface, with no scheduler wiring yet.

  • Add an InProcessMessagingQueue implementing core::MessagingQueue, backed by a shared bounded ring buffer keyed by a stable channel id (reuse the deterministic stableStreamId so a channel maps 1:1 to what would have been a Kafka topic).
  • Add a process-local registry of live in-process channels so a producer and its consumer(s) rendezvous by channel id.
  • Pass frames by reference-counted handle (no serialization) while keeping the same record types that cross the messenger boundary today, so a channel can be swapped for Kafka without touching node code.
  • Support single-producer / multi-consumer, since a node output can fan out to several downstream nodes.
  • Unit-test produce/consume, fan-out, and teardown in isolation.

Phase 2 — Edge classification and colocation proof

Implemented. Pure, unit-tested classifyPrivateOutputs in tools/…/GraphTransportPlan.hpp runs over the flattened graph (so composite grouping cannot change transport, per ADR 005) and returns the producer outputs that are private + colocated. An output is private iff every consuming edge targets a transform/combine (no viewer/sink/session/train tap) and the injectable areColocated proof holds for each — defaultColocationProof returns true today. executeStreamGraphStart and handleRestartStreamGraphNode recompute this every run and pass per-edge input_in_process/output_in_process flags into createTransformWorker/createCombineWorker, which mint an in-process or Kafka messenger accordingly. A global kill-switch (NATKIT_INPROCESS_TRANSPORT) forces all-Kafka.

Give the runtime the two facts it needs to pick a transport per edge.

  • Published vs private: classify each edge. An edge is published if its source output is exposed via a composite output port, or its consumer is a viewer/sink/session/train node, or a top-level graph edge subscribes to it. Otherwise it is a candidate private edge.
  • Colocation proof: an edge may use the in-process path only if the scheduler can prove both endpoints run in the same worker process. Until Phase 5 splits transforms onto separate worker processes, all graph nodes share the backend process, so the proof is trivially true — but it must be asked as a scheduler question, not assumed.
  • Transport decision = (private AND colocated) ? in-process : Kafka. Record the decision per edge in the graph runtime so status reporting and teardown can see it.
  • React to edits: if a graph edit exposes a previously private edge (e.g. a new viewer is attached, or the subgraph is ungrouped), the edge must be re-classified and its channel promoted to Kafka on the next run.

Phase 3 — Backpressure and buffering policy

Implemented. Each channel is bounded (default 256 frames, per frame not per sample; tunable via NATKIT_INPROCESS_CHANNEL_CAPACITY). Graph signal edges use drop-oldest (matches live-monitoring); block is available for lossless handoff. Per-channel published/dropped/depth/subscriber counts are surfaced per node in makeGraphStatusJson alongside a transport: "in_process"|"kafka" tag, on the same status surface Kafka transforms report. Teardown: a stopped producer closes + deregisters its channel (waking any blocked producer via close()); polling consumers drain then see empty, so nothing wedges.

In-process channels have no broker-side buffer, so the policy must be explicit.

  • Bound each channel to a fixed capacity. On overflow, apply a per-channel policy: drop-oldest for real-time signal edges (matches live-monitoring semantics) vs block where lossless handoff is required.
  • Handle rate-changing stages (e.g. sliding window emits one frame per N samples) — buffering is per frame, not per sample, so window/feature stages need no special case beyond capacity sizing.
  • Surface per-channel drop counts and depth into the same worker-summary/status surface that Kafka transforms already report, so an overloaded in-process edge is observable.
  • Decide teardown ordering so a stopped producer drains or discards cleanly without wedging a blocked consumer.

Phase 4 — Preserve tap-ability, recording, and replay

Implemented by construction. Because classification runs on every run, attaching a viewer/sink/session/train node to a formerly private edge re-classifies its producer output as published and promotes it to Kafka on the next run — the existing viewer/recording path then works with no frontend special case. Session and train nodes are published consumers, so a private in-process edge can never be a recording/replay source. The composite “expose internal node as output port” case is handled for free: after flattening it is just an edge to whatever taps it, so a viewer tap forces Kafka while a transform-only tap stays legitimately private regardless of grouping. (Accepted tradeoff, per ADR 005: an ad-hoc standalone tap on an intermediate private stream sees nothing until a viewer node is added and the graph re-run; the NATKIT_INPROCESS_TRANSPORT=off kill-switch restores universal tap-ability.)

Do not silently lose the observability Kafka gives.

  • When a user attaches a viewer to an edge that is currently in-process, promote that edge to Kafka (or dual-write) so the existing viewer path keeps working with no special case in the frontend.
  • Ensure session recording and replay only ever read published (Kafka) edges; a private in-process edge is never a recording source.
  • Confirm the composite “expose internal node as output port” feature (e.g. the linear-envelope second output) forces its edge onto the published path.

Phase 5 — Worker-node migration tie-in

Staged. The colocation proof is already an injected predicate (classifyPrivateOutputs's areColocated, defaulting to defaultColocationProof == always true). When ADR 001 Phase 4 lands slot placement, swap in a scheduler proof at the single call site in classifyGraphPrivateOutputs; a cross-slot consumer then answers false and its upstream falls back to Kafka automatically — no new transport, no other change. A unit test (NonColocatedConsumerForcesKafka) already exercises that fallback.

When ADR 001 Phase 4 moves EMG transforms off the Drogon process onto worker slots, the colocation proof stops being trivial.

  • The scheduler must decide slot placement for graph nodes and only then can two nodes be known co-located.
  • Cross-slot / cross-node edges fall back to Kafka automatically under the Phase 2 rule — no new transport needed, consistent with “Kafka is the cross-node data plane.”
  • Optionally let the scheduler bias placement to co-locate a private chain on one worker to maximize in-process fast-path usage, subject to slot capacity and ownership policy (ADR 004).

Risks and non-goals

  • Non-goal: a websocket or any second network transport. Cross-node transport is Kafka (ADR 005).
  • Risk: transport-dependent behavior differences (ordering, loss, latency) leaking into node logic. Mitigate by keeping node code transport-agnostic behind the messenger interface and testing each node against both transports.
  • Risk: stale edge classification after graph edits causing a tapped edge to be silently private. Mitigate with the Phase 4 promotion path and re-classification on every run.
