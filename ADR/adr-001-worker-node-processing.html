natKit ADR 001 · backend · workers · June 29 2026

Worker-Node Execution With User-Assignable Thread Slots

Move long-running processing out of the browser backend process and into worker nodes that expose a fixed set of logical thread slots. Each worker node defaults its slot count to the machine thread count, allows slots to be assigned to future users, and schedules jobs by slot with priority, queue visibility, and utilization reporting.

Status: accepted for incremental implementation. First surface: libnatkit/scripts/natkit_ml_control_plane.py and frontend/src/MlPipeline/.

Decision

  • Use worker nodes for backend processing instead of spawning ad hoc threads inside the browser backend.
  • Model user-visible execution lanes as stable logical thread_slot_id values, not raw OS thread identities.
  • Default the worker slot count to std::thread::hardware_concurrency() or the host equivalent, with an explicit override.
  • Allow multiple jobs to be assigned to a slot through queueing, while running at most one job at a time per slot in the initial design.
  • Require job creation flows to name a target slot once slot ownership exists in the UI.

Context

What exists now

  • The Drogon backend still performs some processing in-process.
  • EMG transform creation starts local worker threads in the WebSocket server.
  • The ML control plane already owns job orchestration, but job state is still process-local.

Why change

  • The project direction already assumes clustered workers and replayable Kafka-backed processing.
  • Per-process thread spawning does not give durable ownership, capacity accounting, or slot visibility.
  • User-facing scheduling requires a stable resource model that survives reconnects and supports future authentication.

Constraint

  • The existing ML pipeline is the most practical first implementation path.
  • We do not have users yet, so owner assignment must be designed before auth exists.
  • The first slice should avoid forcing a full cluster-state store redesign in one step.

Execution Model

frontend / service
  -> control plane
    -> worker node
      -> thread slot queue
        -> job runner

worker node
  -> slot-1
  -> slot-2
  -> ...
  -> slot-N  (N defaults to machine thread count)

A slot is a logical scheduling lane. It has stable identity, owner metadata, queue state, and utilization metrics. The runtime may back a slot with different pool workers across restarts, but the product surface stays stable.

Why Logical Slots Instead Of Raw Threads

Option Result Decision
Expose OS thread ids Unstable across restarts, awkward for ownership, poor UX Rejected
Expose logical slot ids Stable identifiers, easy ownership, clean queue semantics Accepted
Hide execution lanes entirely Removes the user's ability to intentionally place work Rejected

Initial Scheduling Semantics

  • A worker node creates N slots by default, where N equals the machine thread count.
  • Each slot runs one job at a time in the initial implementation.
  • Each slot may hold multiple assigned jobs through a priority queue.
  • Priority sorts first, then FIFO inside equal priority.
  • Queued jobs may be reprioritized or cancelled before they start.
  • Running jobs may be requested to stop, subject to the job runner's ability to cooperate.

Required State

Entity Purpose
worker_node Identifies one execution host and its capacity
thread_slot Stable user-visible execution lane on a worker
slot_assignment Maps a future user or principal to one or more slots
job Owns payload, status, priority, slot target, and result summary
job_event Timeline of state changes and progress messages
slot_utilization_sample Busy ratio and queue state for oversubscription visibility

Consequences

  • The browser backend should stop spawning persistent transform threads as the preferred execution model.
  • The ML control plane becomes the seed of a broader scheduler instead of a one-off service.
  • Authentication is not required to start, but slot ownership needs a stable principal field now.
  • Some current APIs that assume one active job per page will need to be widened to multi-slot, multi-job responses.

Implementation Status

Initial slice implemented
  • The existing ML control plane now exposes worker, worker-slot, and job-list actions.
  • The current protocol includes embedded worker summaries with slot capacity counts and heartbeat timestamps, which preserves the frontend contract for a later control-plane and worker-process split.
  • The current frontend ML workspace now targets slots and shows slot/job scheduler state.
  • The Stream Viewer EMG transform path now has explicit local slot capacity, active-transform listing, stop control, per-transform slot identity, and lightweight runtime activity metrics, which replaces the previous unbounded spawn-only behavior with a visible resource boundary.
  • Ownership is still placeholder-principal-based rather than real authenticated user identity.
  • Explicit slot release now exists, and slot reassignment is blocked while active work owned by another principal is still attached.
  • The current placeholder policy now also requires jobs to run only on slots already assigned to the submitting principal; unassigned slots must be claimed first.
  • The control plane now also has explicit external worker registration, heartbeat, and unregister actions, which lets multi-process worker identity show up in worker summaries before external slot inventories are fully synchronized.
  • External workers can now mirror logical slot inventories into scheduler state and claim/report queued jobs for those slots through the control plane, and libnatkit/scripts/natkit_ml_worker.py now provides the first standalone runtime for that execution path.
  • The standalone worker now retries control-plane connectivity with backoff and can replay deferred terminal job reports after reconnect, so the remaining implementation gap in this slice is no longer the basic remote-execution loop or transient reconnect handling.
  • The remaining implementation gap is deployment topology, richer recovery for in-flight work across control-plane restarts, and moving scheduler durability beyond control-plane-local state.
  • Queued-job reprioritization and stop requests are now owner-scoped under that placeholder-principal model.
  • Running-job cancellation now stops at pipeline checkpoints between substantial work units; hard interruption inside an individual reconstruction or model-training call is still not implemented.
  • The current single-node service now has both lightweight JSON snapshots and a stronger SQLite-backed persistence path for slot ownership and job history, but this is still a bridge toward shared multi-process scheduler state.

Deferred Decisions

  • Whether mutable scheduler state lives in Kafka topics, a relational store, or both.
  • Whether future slots should permit bounded concurrent execution greater than one.
  • How multi-process worker-node discovery and heartbeats should integrate with the rest of cluster metadata beyond the current embedded-worker heartbeat.
  • Whether long-lived streaming transforms should queue, reject, or preempt when all slots are occupied.
  • How job editing should be limited once execution has started.
This ADR accepts the logical slot model now so the control plane, frontend, and future user model can converge on one scheduler surface.
