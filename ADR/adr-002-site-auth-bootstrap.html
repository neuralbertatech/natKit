natKit ADR 002 · auth · users · June 30 2026

Local User Accounts With Bootstrap Admin Creation

Status: accepted for the current browser backend. First surface: libnatkit-natkit-backend and the frontend SPA shell.

Decision

  • Introduce local site users before broadening more operator-facing features.
  • Use a cookie-backed session on the Drogon backend for both HTTP and WebSocket access.
  • Require bootstrap of the first enabled admin account before the site can be used.
  • Support two bootstrap modes: a random backend-logged password or automatic first-admin creation.
  • Expose a small admin panel so enabled admins can create, update, disable, and delete users.

Context

The Stream Viewer and related browser tools have become operational control surfaces rather than passive demos. Existing APIs and the browser WebSocket currently assume an anonymous caller, which is enough for early prototyping but weakens any future scheduling, ownership, or audit model.

ADR 001 already called out future authentication as an architectural dependency for slot ownership and worker scheduling. This ADR adds the first concrete user concept so later authorization does not have to be retrofitted into a larger, more fragmented API surface.

Bootstrap model

Mode Behavior
password The backend generates or accepts a bootstrap password and logs it. The first admin creation request must present that password.
auto_admin If no users exist, the first bootstrap request directly creates the initial admin and signs that browser in.

The default is password because it prevents silent takeover when a shared dev backend becomes reachable before an operator is ready.

Authorization scope

  • All existing browser backend API routes require an authenticated session.
  • The Stream Viewer WebSocket handshake uses the same session cookie and rejects anonymous clients.
  • User management routes require an enabled admin account.
  • The system must never allow the last enabled admin to be disabled, demoted, or deleted.

Initial constraints

  • User state is stored locally in a backend-managed JSON file. This is acceptable for the current single-process deployment shape, but not the long-term clustered model.
  • Password hashing is intentionally lightweight compared with a dedicated identity service. It is adequate for the current local-admin slice, but not the final identity architecture.
  • No per-feature RBAC exists yet beyond authenticated user versus admin.
  • ML control-plane principal ownership still remains a separate concept and is not unified by this ADR yet.

Next implications

  • When worker-slot ownership moves fully into authenticated user identity, this site account can become the principal source instead of placeholder strings.
  • Once backend state becomes multi-node, user and session persistence will need a shared store instead of local JSON state.
  • Operator-visible audit events should eventually record the authenticated username for control actions such as transform creation, drain/resume, and job submission.
