natKit ADR 004 · scheduler · authz · July 2 2026

Admin-Owned Shared and Dedicated Compute Pools

Status: accepted for the current site-admin deployment model.

Decision

  • The site admin owns compute policy for worker thread slots.
  • Each slot is configured as either shared or dedicated.
  • Users receive shared-pool access through an explicit per-user entitlement flag.
  • A dedicated slot names exactly one enabled site user as its designated consumer.
  • Job ownership stays with the authenticated submitting user, but slot access is governed by admin policy rather than user-side claim and release.

Context

Earlier scheduler behavior treated slot access as a runtime ownership claim by the current user. That model was convenient for early experimentation, but it does not match the operational ownership model for real deployments where a site or lab operator controls access to finite compute.

The target use cases require both broad shared access and reserved capacity: a freemium deployment where free users share a common pool while premium users receive reserved slots, and a lab deployment where one workstation or experiment may require a dedicated slot while the rest remain open to the larger group.

Policy model

Slot mode Who can submit Admin configuration
shared Any enabled user with shared_compute_access, plus admins. No dedicated owner is set.
dedicated The configured dedicated username, plus admins. A valid enabled username must be assigned.

Shared-pool entitlement and slot policy are stored in the shared SQLite auth database so the browser backend and the ML control plane enforce the same authorization view.

Operational implications

  • Admins manage users and their shared-pool entitlement through the site admin panel.
  • Admins manage slot mode and dedicated owner through scheduler-facing admin controls.
  • Non-admin users no longer control access by claiming or releasing slots.
  • Schedulers may still report job ownership by authenticated submitting username for audit and job management.

Constraints

  • The current model supports two access classes only: shared and dedicated.
  • There is no explicit named pool object yet, only per-slot policy plus per-user entitlement.
  • Subscription tiering, quotas, or billing state remain outside this ADR and can layer onto the same primitives later.
  • Changing slot policy while jobs are active is intentionally restricted to avoid mid-run authorization ambiguity.

Follow-on direction

  • If the product grows beyond two access classes, introduce first-class pool records rather than overloading slot policy further.
  • Audit trails should eventually record admin policy changes alongside job submission and worker control actions.
  • Usage accounting can build on the current distinction between shared-pool entitlement and dedicated-slot ownership.
