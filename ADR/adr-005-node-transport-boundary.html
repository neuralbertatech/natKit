Node Transport Boundary: Colocation-Based In-Process vs Kafka

Status: accepted as direction; implementation deferred (see plans/in-process-transport-plan.html). Interim correctness fix already landed.

Decision

  • The transport for a graph edge is chosen by provable colocation of its endpoints on the same worker slot/node, and the choice is made by the scheduler — not by whether the edge is internal to a composite.
  • Kafka remains the default transport and the only transport for streams that cross nodes or that must be durable, replayable, discoverable, tap-able, or recordable. Composite input/output ports, top-level edges, and any stream a viewer/session/train node consumes stay on Kafka.
  • An in-process message queue may carry an edge only when the scheduler proves both endpoints run in the same process and the edge is private (not exposed as a composite port, not tapped by a viewer/sink, not recorded or replayed).
  • Composite grouping is a UI construct. Grouping, ungrouping, or regrouping a subgraph must never change its transport semantics or its runtime correctness.
  • Intra-graph input-topic resolution must not depend on Kafka broker metadata. Topic names are deterministic; the runtime resolves an upstream node's output topic from what it already knows, not by waiting for the first frame to materialize the topic.

Context

A user-reported failure exposed a startup race in chained transforms. The stream-graph runtime starts nodes in topological order, and each transform resolved its input topic by scanning live Kafka broker metadata (findTransformSourceTopicForStream → getAllStreams). A transform's output topic does not appear in that metadata until the worker has produced its first frame, but downstream workers are created microseconds after their upstream — before any data has flowed. Deep pipelines therefore failed at the first stage whose upstream had not yet produced, with “Could not locate a compatible JSON numeric channel topic for source_stream_id”, cascading into “Blocked: upstream node ... failed to start” for everything downstream.

Diagnosing that led to a broader question: should composite-internal edges bypass Kafka entirely and use a lighter transport? The instinct is sound — a 13-stage composite pays 13 broker round-trips of latency per frame and litters stream discovery with purely internal intermediate topics. But the cut “websocket for composite internals” is wrong on two counts, and the direction in ADR 001 constrains the answer: the project already assumes clustered workers and replayable Kafka-backed processing, and EMG transforms are migrating from in-process threads onto independently scheduled worker slots.

Why not transport-by-composite, and why not websockets

  • Composite membership is not colocation. Under ADR 001 a transform becomes an independently scheduled job on a worker slot, and slots may live on different nodes. A composite can be ungrouped, and nothing pins its internal nodes to one host. Keying transport off composite membership bakes in a colocation assumption the roadmap contradicts.
  • Websockets are the wrong second transport. Today the internal nodes are threads in one process, so a websocket between them is loopback networking — pure serialization and socket overhead over what an in-process queue does for free. If the endpoints are genuinely on different nodes, the needed cross-node data plane (discovery, backpressure, replay) is exactly what Kafka already provides; adding websockets would reimplement it and fight the replayable-Kafka principle.
  • The race is not a transport problem. Topic names are deterministic and the upstream worker is already known to the runtime; resolving from that removes the race on any transport. Transport choice and startup correctness are separate concerns and must stay separate.

What in-process transport buys, and what it must not cost

PropertyKafka edgeIn-process edge (private, colocated)
Latency / overheadBroker round-trip + JSON serialize per hopDirect in-memory handoff
Cross-nodeYesNo — same process only
Durable / replayableYesNo
Discoverable / tap-able by a viewerYesNo
Recordable by a session nodeYesNo
Topic clutter in stream discoveryOne topic per intermediateNone

Because tap-ability, recording, and replay are lost on an in-process edge, an edge must be promoted back to Kafka the moment it is exposed as a composite port or consumed by a viewer, sink, session, or train node. This ADR’s very motivating graph exposes an internal node (the linear envelope) as a second output port — a reminder that the internal/external line is porous and must be enforced at edge-classification time, not assumed from composite structure.

Interim state (already implemented)

To unblock users immediately and decouple correctness from the transport decision, intra-graph input resolution no longer depends on Kafka metadata. When broker discovery cannot yet see an upstream transform/combine output topic, the runtime resolves that node's deterministic output BasicTopicInformation directly from the in-process worker registries (findGraphInternalOutputTopicForStream in StreamViewerWebSocket.cpp). Kafka discovery remains the path for genuine hardware stream_source inputs. Deep pipelines now start deterministically without racing the first frame through each stage.

Consequences

  • A transport-selection responsibility is added to the scheduler, gated on a colocation proof. Until that lands, all edges remain on Kafka and the interim fix keeps them correct.
  • Edge classification (private vs published) becomes a first-class concept the runtime must compute, and must react to graph edits that expose a previously private edge.
  • In-process edges need a bounded-buffer backpressure policy; unlike Kafka they have no broker-side buffering. See the plan for the drop-vs-block decision.
  • This ADR refines, and does not replace, ADR 001. It defines the transport boundary that ADR 001’s Phase 4 (moving EMG transforms onto workers) will have to honor.
