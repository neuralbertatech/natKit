natKit ADR 003 · auth · sqlite · June 30 2026

Shared SQLite Auth Store Across Browser-Facing Backends

Status: accepted for the current multi-process local stack.

Decision

  • Store site users and browser sessions in a shared SQLite database instead of backend-local JSON or process memory.
  • Use the same cookie name and session records across the Drogon backend and the ML control plane.
  • Derive ML control-plane browser principal identity from the authenticated session username instead of a free-form text field.
  • Keep the separate worker-session protocol for external worker processes and maintenance scripts.

Why

The site already spans at least two browser-facing processes: the Drogon backend on 7409 and the ML control plane on 8786. Local-only auth state in one process does not establish identity in the other, which leaves principal ownership on the ML side disconnected from real site users.

Shape

  • auth_users: username, display name, password hash data, admin flag, enabled flag, timestamps.
  • auth_sessions: opaque session token, username, creation time, expiry time.
  • The browser session cookie is sent to both ports because the cookie is scoped by host and path rather than port.
  • The ML control plane reads the shared SQLite state directly for browser session validation.
  • Non-browser worker and operator clients authenticate by reusing a shared session token, either supplied directly or obtained by logging in through the main backend first.

Limitations

  • This is still a local deployment solution, not the final clustered identity architecture.
  • The ML control plane keeps a compatibility path for non-browser worker and operator clients that do not participate in browser cookie auth.
  • Authorization is still coarse: authenticated user versus admin, plus existing slot/job ownership checks.
